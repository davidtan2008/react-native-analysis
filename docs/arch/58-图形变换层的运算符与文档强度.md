## 2. 【核心 XX-1】`at(int i, int j)`：`noexcept` 且无边界检查

### 2.1 实现全文

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:437-443
Float& Transform::at(int i, int j) noexcept {
  return matrix[(i * 4) + j];
}

const Float& Transform::at(int i, int j) const noexcept {
  return matrix[(i * 4) + j];
}
```

### 2.2 声明处的注释

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.h:156-160
  /*
   * Matrix subscript.
   */
  Float &at(int i, int j) noexcept;
  const Float &at(int i, int j) const noexcept;
```

**注释只有 3 个词：`Matrix subscript.`**

| 缺失的说明 | 影响 |
| --- | --- |
| 合法索引范围 | 调用方不知 `i`、`j` 只能是 `[0,4)` |
| 越界行为 | **无任何说明** |

### 2.3 三处风险叠加

| # | 事实 | 后果 |
| --- | --- | --- |
| ① | 无 `assert` / `react_native_assert` | 越界不会被发现 |
| ② | 标了 **`noexcept`** | 越界导致的任何问题都不能通过异常传播 |
| ③ | 直接 `operator[]` | `std::array` 的 `operator[]` **本身也不检查**（除 `_DEBUG` 下的 MSVC STL） |

**即：越界访问会静默读到相邻内存。**

### 2.4 实际调用方的索引都是字面量

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:488-501
Vector operator*(const Transform& transform, const Vector& vector) {
  return {
      .x = vector.x * transform.at(0, 0) + vector.y * transform.at(1, 0) +
          vector.z * transform.at(2, 0) + vector.w * transform.at(3, 0),
```

**`at` 的全部调用点都在 `Transform.cpp` 内部，且索引是 `0..3` 的字面量。**

| 调用点 | 索引范围 |
| --- | --- |
| `Transform.cpp:488-501`（`Vector` 变换，16 处） | `0..3` |
| `Transform.cpp:503-504`（`Size` 变换，2 处） | `(0,0)`、`(1,1)` |

> **即当前没有越界风险** ——
> 但**这是一个「靠调用方自律」的边界**，没有任何机制阻止后续传入 `i = 4`。
>
> **与 53 文档 SS-2 对照**：那处的哈希/相等不一致也有「间接不变量」兜底
> （`ComponentDescriptorRegistry` 的断言）；
> **本处的「不变量」（索引必须是 0..3）没有任何兜底。**

## 3. 【核心 XX-2】四则运算符的文档与实现：三种不一致方向

### 3.1 头文件的声明与注释（逐字）

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.h:193-216
/*
 * Applies transformation to the given point.
 */
Point operator*(const Point &point, const Transform &transform);

/*
 * Applies transformation to the given size.
 */
Size operator*(const Size &size, const Transform &transform);

/*
 * Applies transformation to the given rect.
 * ONLY SUPPORTS scale and translation transformation.
 */
Rect operator*(const Rect &rect, const Transform &transform);

/*
 * Applies transformation to the given EdgeInsets.
 * ONLY SUPPORTS scale transformation.
 */
EdgeInsets operator*(const EdgeInsets &edgeInsets, const Transform &transform);

Vector operator*(const Transform &transform, const Vector &vector);
```

**四则运算符的注释长度：1 行、1 行、2 行、2 行。**
**即「文档长短」与「实现复杂度」无关 —— 最复杂的 `Rect` 实现只有两行注释。**

### 3.2 逐个对照：实现做了什么 vs 文档说了什么

| 运算符 | 实现的关键一行 | 实现实际支持 | 文档声明 | **方向** |
| --- | --- | --- | --- | --- |
| `Point` | `transform * Vector{..., .z = 0, .w = 1}` | **全 4×4（含旋转/透视）** | 「Applies transformation」（无限制） | ✅ 一致 |
| `Size` | `abs(transform.at(0,0) * size.width)` | **仅对角线（= 仅 scale）** | 「Applies transformation」（**无限制**） | ❌ **文档比实现宽松** |
| `Rect` | **4 角变换 + `boundingRect`** | **全变换（旋转取包围盒）** | `ONLY SUPPORTS scale and translation` | ⚠️ **文档比实现保守** |
| `EdgeInsets` | `matrix[0]` / `matrix[5]` | 仅对角线（= 仅 scale） | `ONLY SUPPORTS scale transformation` | ✅ 一致 |

**四种方向各出现一次**，构成一组完整的对照样本。

### 3.3 `Size` 的实现：只取对角线

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:501-511
Size operator*(const Size& size, const Transform& transform) {
  if (transform == Transform::Identity()) {
    return size;
  }

  auto result = Size{};
  result.width = std::abs(transform.at(0, 0) * size.width);
  result.height = std::abs(transform.at(1, 1) * size.height);

  return result;
}
```

**只读 `at(0,0)` 与 `at(1,1)` 两个元素**，非对角线项（`at(1,0)`、`at(0,1)` 等）被完全忽略。

| 变换 | `at(0,0)` | `at(1,1)` | 结果是否正确 |
| --- | --- | --- | --- |
| `scale(2)` | 2 | 2 | ✅ |
| `translate(10)` | 1 | 1 | ✅（Size 不受平移影响，正确） |
| `rotate(45°)` | 0.707 | 0.707 | ⚠️ 巧合正确（缩放因子 = cos45） |
| `skewX(30°)` | 1 | 1 | ❌ **错误**（结果与未变换相同） |
| `scale(2,3) rotate(45°)` | — | — | ❌ **错误**（忽略交叉项） |

**而头文件的注释对这三点只字未提。**

### 3.4 `Rect` 的实现：4 角 + 包围盒（比文档更强）

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:460-479
Rect Transform::applyWithCenter(const Rect& rect, const Point& center) const {
  auto a = Point{.x = rect.origin.x, .y = rect.origin.y} - center;
  auto b = Point{.x = rect.getMaxX(), .y = rect.origin.y} - center;
  auto c = Point{.x = rect.getMaxX(), .y = rect.getMaxY()} - center;
  auto d = Point{.x = rect.origin.x, .y = rect.getMaxY()} - center;

  auto vectorA = *this * Vector{.x = a.x, .y = a.y, .z = 0, .w = 1};
  auto vectorB = *this * Vector{.x = b.x, .y = b.y, .z = 0, .w = 1};
  auto vectorC = *this * Vector{.x = c.x, .y = c.y, .z = 0, .w = 1};
  auto vectorD = *this * Vector{.x = d.x, .y = d.y, .z = 0, .w = 1};
```

**四个角各自做完整 4×4 变换，再取包围盒**：

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:476-479
  return Rect::boundingRect(
      transformedA, transformedB, transformedC, transformedD);
```

**这是几何上正确的做法** —— 旋转后的矩形用轴对齐包围盒近似。

**但头文件写的是 `ONLY SUPPORTS scale and translation transformation.`**

> **即实现能做旋转，文档说不能。**
>
> **这类「文档比实现保守」的偏差通常比相反方向安全**
> —— 调用方读了文档会以为不能用旋转，
> 于是不会依赖它；**但一旦有人发现实现其实支持，就可能误用而无人提醒**。
>
> **与 `EdgeInsets` 的情况正好相反**：
> 那里文档与实现一致（都只支持 scale），
> **但 `Size` 那里文档最宽松、实现最严格** —— **风险最高的一格。**

### 3.5 三个运算符的实际调用方（实测）

| 运算符 | 声明处 | 实现在 | **生产调用方** |
| --- | --- | --- | --- |
| `Point` | `Transform.h:197` | `Transform.cpp:445` | 本文件内 + `Transform.cpp:468-471` |
| `Rect` | `Transform.h:208` | `Transform.cpp:455` | **`core/LayoutableShadowNode.cpp:290`、`:298`** |
| **`Size`** | `Transform.h:202` | `Transform.cpp:501` | **0** |
| **`EdgeInsets`** | `Transform.h:214` | `Transform.cpp:480` | **0** |

**即「文档最宽松、实现最严格」的 `Size` 与「一致」的 `EdgeInsets` 都没有生产调用方。**

### 3.6 唯一有生产调用方的 `Rect`：命中测试


**这是触摸命中测试** —— 即 **47 文档 MM-1 记录的无障碍/触摸路径的更深一层**。

| 观察 | 含义 |
| --- | --- |
| 变换在**命中测试之前**应用 | 旋转的 View 的触摸区域按变换后计算 ✅ |
| 溢出框也做同样变换 | `overflowInset` 路径一致 ✅ |
| **用 4 角包围盒** | 旋转 45° 的按钮，实际可点区域是其**轴对齐包围盒**（比视觉略大） |

> 一个旋转 45° 的 100×100 按钮，其可点区域是 141×141 的正方形（不是菱形）。
> **对用户而言这意味着旋转按钮的「角上空白区也可点」。**
>
> **这是有意的近似**（`boundingRect` 是唯一可用的返回类型），
> **不是 bug**；但头文件的 `ONLY SUPPORTS scale and translation` 让它更不明显。

## 4. `operator==`：矩阵与操作序列都要相同

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:342-357
bool Transform::operator==(const Transform& rhs) const noexcept {
  for (auto i = 0; i < 16; i++) {
    if (matrix[i] != rhs.matrix[i]) {
      return false;
    }
  }
  if (this->operations.size() != rhs.operations.size()) {
    return false;
  }
  for (size_t i = 0; i < this->operations.size(); i++) {
    if (this->operations[i] != rhs.operations[i]) {
      return false;
    }
  }
  return true;
}
```

**相等要求 16 个矩阵元素 + 操作序列的**长度与逐项**都相同。**

**这比 53 文档记录的 `LayoutMetrics` 严格得多** —— 那里用 `= default` 逐字段比较；
这里**额外比较了 `operations` 序列**。

| 后果 | 说明 |
| --- | --- |
| 矩阵相同但操作序列不同的两个 `Transform` | **判为不等** |
| 典型场景 | `translate(0,0)` 与空序列 |
| 影响 | `operator*` 的恒等短路（`:360`）在这两种情况下**不成立**，会走完整矩阵乘法 |

> **`:360` 的短路依赖这个「更严格」的相等**：
> ```cpp
> Transform Transform::operator*(const Transform &rhs) const {
>   if (*this == Transform::Identity()) {
>     return rhs;
>   }
> ```
> **注意格式差异**：`.cpp` 的签名是 `const Transform& rhs`（`&` 前无空格），
> 而 `.h` 的声明是 `const Transform &rhs`（有空格）——
> **两个文件的 clang-format 风格不一致**，引用时需分别照抄。
>
> **即「相等」被用作性能短路。**
> 若相等判定放宽，这个短路会漏判。
> **当前是正确的依赖方向**（严格的相等保证短路不被误触发）。

### 4.1 `operator*` 同时维护两套状态

```cpp
// packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:359-378
Transform Transform::operator*(const Transform& rhs) const {
  if (*this == Transform::Identity()) {
    return rhs;
  }

  const auto& lhs = *this;
  auto result = Transform{};
  for (const auto& op : this->operations) {
    if (op.type == TransformOperationType::Identity &&
        !result.operations.empty()) {
      continue;
    }
    result.operations.push_back(op);
  }
  for (const auto& op : rhs.operations) {
    if (op.type == TransformOperationType::Identity &&
        !result.operations.empty()) {
      continue;
    }
    result.operations.push_back(op);
  }
```

**乘法同时算两样东西**：新的操作序列（去掉中间的 Identity）与新的 16 元素矩阵。

**Identity 消除规则有一个不对称**：

| 条件 | 行为 |
| --- | --- |
| `op.type == Identity` **且** `!result.operations.empty()` | 跳过该操作 |
| `op.type == Identity` **且** `result.operations.empty()` | **保留** |

> **即「开头的 Identity 不被消除，中间的被消除」。**
> 这在数学上无害（`Identity × M = M`），
> **但意味着 `operations` 的长度依赖操作的书写顺序** ——
> 这正是 §4 的 `operator==` 需要逐项比较 `operations` 的原因之一。
>
> **注释缺失**：这段消除逻辑没有注释说明为何只消除「非首位」的 Identity。

## 5. 已发现的问题

| 编号 | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| **XX-1** | **【核心】`at(int i, int j)` 标 `noexcept` 且无边界检查、无断言，注释仅 3 个词（`Matrix subscript.`）** | `packages/react-native/ReactCommon/react/renderer/graphics/Transform.cpp:437-443`；`Transform.h:156-160` | **当前调用方全在文件内且索引是 0..3 字面量，故无实际越界**；但该边界「靠调用方自律」，无任何机制阻止后续传入 `i=4` |
| **XX-2** | **【核心】四个运算符的文档/实现强度四种方向并存**：`Size` 文档无限制而实现仅对角线（风险最高）、`Rect` 文档声明 `ONLY SUPPORTS scale and translation` 而实现是 4 角包围盒（更强）、`Point` 一致、`EdgeInsets` 一致 | `Transform.h:193-216` vs `Transform.cpp:445-511` | **`Size` 的限制完全未文档化**；调用方可能误以为支持 skew/旋转 |
| **XX-3** | `Size` 的实现只读 `at(0,0)`/`at(1,1)`，忽略全部交叉项 | `Transform.cpp:503-504` | skewX(30°) 下结果与未变换相同 |
| XX-4 | `Rect` 变换用轴对齐包围盒近似旋转后的矩形 | `Transform.cpp:476-479` | 旋转 45° 的 100×100 按钮的可点区域是 141×141 正方形；**对用户可感知（角上空白可点）** |
| XX-5 | `operator==` 要求 `operations` 序列逐项相同，**比矩阵相等更严格** | `Transform.cpp:342-357` | `translate(0,0)` 与空序列判为不等 —— 严格的相等被 `operator*` 用作性能短路（`:360`），**依赖方向正确** |
| XX-6 | `operator*` 的 Identity 消除只作用于「非首位」，**该规则无注释** | `Transform.cpp:364-377` | `operations` 长度依赖书写顺序；这是 `operator==` 需要逐项比较的直接原因，但因果关系未写在任何地方 |
| XX-7 | `Size` 与 `EdgeInsets` 两个运算符**零生产调用方** | `Transform.h:202`、`:214` | XX-2/XX-3 的实际暴露面为零；**唯一有调用方的 `Rect` 是实现最强的那一个** |

### XX-2 的适用范围声明

| 运算符 | 平台 | 架构 | 暴露面 |
| --- | --- | --- | --- |
| `Rect` | 全平台 | Fabric | ✅ **命中测试在用** |
| `Point` | 全平台 | Fabric | ✅ 本文件内 + 内部调用 |
| `Size` | 全平台 | Fabric | ❌ **零调用方** |
| `EdgeInsets` | 全平台 | Fabric | ❌ **零调用方** |

**即：文档与实现不一致最严重的那两个（`Size`、`EdgeInsets`）恰好没有生产调用方；
有生产调用方的 `Rect` 的偏差方向是「文档比实现保守」，风险最低。**

> **必须公允说明**：这不是「隐藏的 bug」，
> 而是**一组文档准确性参差不齐的公开 API**。
> 若未来有人使用 `Size` 运算符做带 skew/旋转的布局，会得到错误结果且无从得知。
