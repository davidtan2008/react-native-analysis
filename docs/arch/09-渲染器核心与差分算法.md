# 09 · 渲染器核心：ShadowNode 不可变模型与差分算法

> **模块**：A1（`ReactCommon/react/renderer/core` + `mounting` + `scheduler` + `uimanager` + `runtimescheduler`，167 个非测试文件）
> **基线**：react-native @ `9b131e42`
> **前置**：[07 文档](./07-Fabric组件层与Props体系.md) 讲了 Props/Descriptor，[08 文档](./08-组件注册表与惰性注册.md) 讲了 Descriptor 从哪来。本文讲**节点本身与差分**。

---

## 1. ShadowNode：不可变 + 禁拷贝

`core/ShadowNode.h:82-86`：

```cpp
/*
 * Not copyable.
 */
ShadowNode(const ShadowNode &shadowNode) noexcept = delete;
ShadowNode &operator=(const ShadowNode &other) noexcept = delete;
```

**ShadowNode 禁止拷贝构造与拷贝赋值**。这意味着：

- 任何「修改」都必须走 `clone()`（`:93`）产生新节点
- 旧的 `shared_ptr` 指向的对象**永不改变**，可以安全地被并发读取
- 这是 COW（copy-on-write）模型：React 的不可变性保证与 C++ 生命周期管理在这里合流

克隆必须**经过 ComponentDescriptor**（`ShadowNode.h:90-93`）：

```cpp
/*
 * Clones the shadow node using the ShadowNode's ComponentDescriptor.
 */
std::shared_ptr<ShadowNode> clone(const ShadowNodeFragment &fragment) const;
```

原因见 [07 文档 §4.1](./07-Fabric组件层与Props体系.md)：`cloneProps` 有「返回对象不得与入参指针相等」的契约，只有 Descriptor 知道具体类型与 Props。

### 1.1 克隆构造的不可变字段

`ShadowNode.h:74-80` 的注释：

```
 * Note: `tag`, `surfaceId`, and `eventEmitter` cannot be changed.
 */
ShadowNode(const ShadowNode &sourceShadowNode, const ShadowNodeFragment &fragment);
```

**`tag` / `surfaceId` / `eventEmitter` 在克隆中保持不变**。这三者共同定义了一个节点在原生侧的「身份」，变更它们等同于换了一个节点。

## 2. 树操作：三个粒度的克隆

`ShadowNode.h:95-117` 提供了三种克隆，对应不同的更新范围：

| 方法 | 范围 | 用途 |
| --- | --- | --- |
| `clone(fragment)` | 单个节点 | 最常见的属性更新 |
| `cloneTree(family, callback)` | **某节点的子树** | 状态更新导致的局部重渲染 |
| `cloneMultiple(familiesToUpdate, callback)` | **多个不相连节点** | 批量更新 |

`cloneMultiple` 的注释说明了它的价值（`:106-112`）：

```cpp
/*
 * Clones the nodes (and the subtree containing all the nodes) by
 * replacing the `oldShadowNode` for every `shadowNodeFamily` from
 * `familiesToUpdate` with a node that `callback` returns.
 *
 * Returns `nullptr` if the operation cannot be performed successfully.
 */
```

**这避免了「为了更新 N 个不连续的节点而重克隆整棵树」**。React 的多根更新（一个组件返回 Fragment 且有 key）会走到这里。

**注意两个 `cloneTree` / `cloneMultiple` 都可能返回 `nullptr`** —— 调用方必须处理失败，源码没有提供异常。

## 3. RSNRU：运行时引用的转移

这是 Fabric 中最精巧也最容易出错的部分。

`ShadowNode.h:200-216` 三个方法构成完整协议：

```cpp
/*
 * Bind the runtime reference to this `ShadowNode` with a weak pointer,
 * allowing to update the reference to this `ShadowNode` when cloned.
 */
void setRuntimeShadowNodeReference(const std::shared_ptr<ShadowNodeWrapper> &runtimeShadowNodeReference) const;

/*
 * Update the runtime reference to point to the provided shadow node.
 */
void updateRuntimeShadowNodeReference(const std::shared_ptr<const ShadowNode> &destinationShadowNode) const;

/*
 * Transfer the runtime reference based on the fragment instructions.
 */
void transferRuntimeShadowNodeReference(
    const std::shared_ptr<const ShadowNode> &destinationShadowNode,
    const ShadowNodeFragment &fragment) const;
```

**问题背景**：JS 侧持有组件实例的引用（如 `useRef` 拿到的实例、事件回调捕获的实例）。当 React 克隆节点后，JS 侧这个引用**本该指向新节点**，否则会出现「ref 指向已被卸载的旧节点」。

**解法**：JS 侧持有的是一个 `ShadowNodeWrapper`（稳定壳），内部用**弱指针**指向真正的 `ShadowNode`。克隆发生时，新节点把壳里的弱指针改指向自己。

调用点在 `ConcreteComponentDescriptor::cloneShadowNode`（见 [07 文档 §5.1](./07-Fabric组件层与Props体系.md)）：

```cpp
auto shadowNode = std::make_shared<ShadowNodeT>(sourceShadowNode, fragment);
shadowNode->completeClone(sourceShadowNode, fragment);
sourceShadowNode.transferRuntimeShadowNodeReference(shadowNode, fragment);
```

第三行的 `transferRuntimeShadowNodeReference` 在**源节点**上调用 —— 因为壳是源节点持有的。

**内存意义**：`ShadowNodeWrapper` 用弱指针，所以**壳不会延长任何 ShadowNode 的寿命**。这是 [03 文档 RSNRU 部分](./03-核心技术原理.md) 与 `LeakChecker` 能工作的基础 —— 若这里用强指针，每次克隆都会泄漏整条路径。

## 4. 挂载副作用的唯一出口

`ShadowNode.h:187-192`：

```cpp
/*
 * Performs all side effects associated with mounting/unmounting in one place.
 * This is not `virtual` on purpose, do not override.
 * `EventDispatcher::DispatchMutex()` must be acquired before calling.
 */
void setMounted(bool mounted) const;
```

三条约束：

1. **所有挂载/卸载副作用集中在这一个非虚函数**
2. **故意不设 `virtual`** —— 防止子类覆盖导致副作用丢失
3. **调用前必须持有 `EventDispatcher::DispatchMutex()`** —— 与事件分发互斥

`getHasBeenPromoted()`（`:194-198`）用于判断节点是否已晋升为下一棵待挂载树。

## 5. 差分算法：`Differentiator.cpp`

`mounting/Differentiator.cpp:1361` 是入口：

```cpp
ShadowViewMutation::List calculateShadowViewMutations(...)
```

这是整个渲染管线中**最重**的函数，复杂度直接决定 React 更新的性能。

### 5.1 核心剪枝：指针相等则跳过

`Differentiator.cpp:945-949`：

```cpp
// Recursively update tree if ShadowNode pointers are not equal
if (!oldChildPair.flattened &&
    (oldChildPair.shadowNode != newChildPair.shadowNode ||
     adjustedOldCullingContext != adjustedNewCullingContext)) {
```

**只要新旧节点的 `shared_ptr` 相同，就不递归下去。**

这依赖 ShadowNode 的不可变性（§1）—— 指针相同即内容必然相同，因为内容不可能被改。这条剪枝是整个差分算法性能的基石：未变化的子树**完全不会被遍历**。

第二个条件 `cullingContext` 单独比较，是因为即使节点指针相同，**裁剪上下文变化也需要重新下发**（例如父级 `overflow: hidden` 改变会改变子树的可见性计算）。

### 5.2 扁平化：处理 reparent

`Differentiator.cpp:216` / `:255` / `:724` / `:742` 反复出现：

```cpp
// Flatten old tree into new list
...
// Unflatten old list into new tree
```

Flat List 是 React 的经典算法（`delete`、`insert` 跨层级移动节点）。源码在 `:239` 解释了扁平化的必要性：

```cpp
// + zIndex: the children could be listed before the parent,
```

即带 `zIndex` 的子节点在渲染顺序上可能排在父节点之前，扁平化后按最终顺序处理。

`:1252` 还有一条防重排的保护：

```cpp
// list to make sure that a node was not reparented into an unflattened
```

**reparent（把已有节点移到新父节点下）在树式 diff 中极难表达**，Flat List 是标准解法。

### 5.3 尾部快速路径

`Differentiator.cpp:1011-1014`：

```cpp
} else if (index == oldChildPairs.size()) {
  // If we don't have any more existing children we can choose a fast path
  // since the rest will all be create+insert.
  for (; index < newChildPairs.size(); index++) {
```

**旧子节点用尽后，剩下的新子节点一律是 create+insert，无需再做配对比较。** 这是常见场景（列表尾部追加）下的 O(n) 而非 O(n²) 保证。

### 5.4 变异顺序

`Differentiator.cpp:1330`：

```cpp
// All mutations in an optimal order:
```

差分结果不是简单收集，而是**按最优顺序排列** —— 删除要在插入前完成，否则原生侧会短暂创建重复节点。

### 5.5 规模无上限（已在 06 文档记录）

`Differentiator.cpp` 中 `mutations.reserve(256)` 只是**容量提示**，无上限、不分片。10 万节点的树 diff 会在单个 transaction 中产生 10 万元素的 `ShadowViewMutation::List`。详见 [06 文档](./06-问题清单与优化建议.md)。

## 6. ShadowNodeFamily：跨版本的身份

`core/ShadowNodeFamily.h:88`：

```cpp
SurfaceId getSurfaceId() const;
```

`ShadowNodeFamily` 是**跨越所有克隆版本的身份标识**。React 的一个组件实例在每次更新后都是新的 `ShadowNode`，但它们共享同一个 `ShadowNodeFamily`。

类的自我定义写得很明确（`core/ShadowNodeFamily.h:41-45`）：

```cpp
/*
 * Represents all things that shadow nodes from the same family have in common.
 * To be used inside `ShadowNode` class *only*.
 */
class ShadowNodeFamily final : public jsi::NativeState {
```

`To be used inside ShadowNode class *only*` —— 它**不是通用容器**，外部不应直接依赖。

### 6.1 它承载的四类跨版本数据

| 数据 | 接口 | 生命周期含义 |
| --- | --- | --- |
| **组件身份** | `getComponentHandle()` / `getComponentName()` / `getComponentDescriptor()`（`:69-75`） | 整个实例生命周期不变 |
| **原生句柄** | `getTag()` / `getInstanceHandle()` / `setInstanceHandle()`（`:125-129`） | 挂载后固定，指向原生视图 |
| **State** | `getMostRecentState()` / `setMostRecentState()` / `dispatchRawState()`（`:101-112`） | State 随**实例**而非随节点 |
| **父链** | `setParent()` / `getAncestors()`（`:64, 86`） | 支持 `zIndex` 与事件冒泡查找 |

**关键推论**：State 挂在 Family 上而非 Node 上。所以「组件重渲染」会产生新 Node 但复用 State；反之，「同一个 Node 换组件」会产生新 Family 也就重置了 State。

`setParent` 的注释坦承了线程安全的妥协（`:59-64`）：

```cpp
/*
 * Sets the parent.
 * This is not technically thread-safe, but practically it mutates the object
 * only once (and the model enforces that this first call is not concurrent).
 */
void setParent(const ShadowNodeFamily::Shared &parent);
```

**"practically thread-safe" 而非 thread-safe** —— 依赖「模型保证首次调用不并发」这一外部约定，属于契约型线程安全。

### 6.2 泄漏检测的挂钩点

`ShadowNodeFamily.h:131-135`：

```cpp
/**
 * Override destructor to call onUnmountedFamilyDestroyedCallback() for
 * ShadowViews that were preallocated but never mounted on the screen.
 */
~ShadowNodeFamily();
```

配合 `:96` 的注册接口：

```cpp
void onUnmountedFamilyDestroyed(std::function<void(const ShadowNodeFamily &family)> callback);
```

**这正是内存泄漏检测的接入点** —— 「已预分配但从未挂载」的节点，其 Family 销毁时触发回调。
具体检测实现在 `ReactCommon/react/renderer/leakchecker/`，详见 [05 文档 §5](./05-监控检测原理与流程.md)。

### 6.3 一处显式的技术债

`ShadowNodeFamily.h:114-120`：

```cpp
/*
 * Holds currently applied native props. `nullptr` if setNativeProps API is
 * not used. It is used to backport setNativeProps API from the old
 * architecture and will be removed in the future.
 */
mutable std::unique_ptr<folly::dynamic> nativeProps_DEPRECATED;
mutable std::mutex nativePropsMutex;
```

旧架构 `setNativeProps` 的兼容层，**源码明确写「will be removed in the future」**。
变量名带 `_DEPRECATED` 后缀 + 配一把独立 mutex，是 A1 模块中唯一为兼容单个 API 而存在的成员。

## 6A. 状态更新如何触发一次 commit

`ShadowNodeFamily::dispatchRawState`（`:112`）把更新塞进 `EventQueue`，
真正的执行发生在 `statePipe` 这条链上。

### 6A.1 队列的合并语义

`core/EventQueue.cpp:64-84`：

```cpp
void EventQueue::enqueueStateUpdate(
    StateUpdate&& stateUpdate,
    UpdateMode updateMode) const {
  {
    std::scoped_lock lock(queueMutex_);
    if (!stateUpdateQueue_.empty()) {
      const auto position = stateUpdateQueue_.back();
      if (stateUpdate.family == position.family) {
        stateUpdateQueue_.pop_back();
      }
    }
    stateUpdateQueue_.push_back(std::move(stateUpdate));
  }

  if (updateMode == UpdateMode::unstable_Immediate) {
    flushStateUpdates();
  } else {
    onEnqueue();
  }
}
```

**关键：入队时按 `family` 合并。** 若队尾已是同一 `family` 的更新，旧的那条被弹出丢弃。

这是 `setState` 多次调用只触发一次渲染的**队列层保证** —— 与 React 侧 `useState` 的批处理是两套独立机制，
一条管 C++ `StateUpdate`，一条管 JS hooks。

> **注意合并只看队尾**：只有「连续的同 family 更新」会被合并。
> 若队列是 `[A, B]` 再入 `A'`，`A` 不会被合并，因为队尾是 `B`。
> 这是 O(1) 的常见优化，而非全表去重。

### 6A.2 `unstable_Immediate` 不切线程

`UpdateMode` 的定义（`core/EventQueue.h:32-41`）：

```cpp
  /* The update mode is used to inform how to apply changes. */
  enum class UpdateMode {
    /** Apply the update off the main thread. */
    Asynchronous,
    /**
     * Apply the update on the main thread.
     * The immediate update mode will **immediately** block the executing thread
     * applying updates.
     */
    unstable_Immediate,
  };
```

注释说 "Apply the update **on the main thread**"。但顺着调用链看：

`EventQueue.cpp:115-129` → `EventQueueProcessor.cpp:132-137`：

```cpp
void EventQueueProcessor::flushStateUpdates(
    std::vector<StateUpdate>&& states) const {
  for (const auto& stateUpdate : states) {
    statePipe_(stateUpdate);
  }
}
```

`statePipe_` 的实际实现（`scheduler/Scheduler.cpp:105-107`）：

```cpp
  auto statePipe = [uiManager](const StateUpdate& stateUpdate) {
    uiManager->updateState(stateUpdate);
  };
```

`UIManager::updateState`（`uimanager/UIManager.cpp:410-452`）**直接调用 `shadowTree.commit(...)`，全程无线程跳转、无线程断言**。

**结论**：`unstable_Immediate` 是在**调用者所在线程**同步跑完整个 commit，
「on the main thread」描述的是**调用约定**（你应当从主线程调用它），而非框架保证的线程切换。
若从非主线程误用，框架不会拦截。

> 这正是文档中 `unstable_` 前缀的用意 —— 该 API 语义仍可能变化。

## 7. 本模块的设计要点

| 设计 | 收益 | 代价 / 风险 |
| --- | --- | --- |
| ShadowNode 禁拷贝 | 不可变性由类型系统保证，并发读安全 | 任何更新都要克隆，节点数 = 版本数 |
| 克隆必经 Descriptor | 类型安全的 downcast | 一次克隆 = 一次虚调用链 |
| RSNRU 弱指针壳 | JS 引用能跟随克隆，且不延长寿命 | 弱壳增加一层间接 |
| `setMounted` 非虚 | 挂载副作用无法被意外覆盖 | 子类无法扩展挂载行为 |
| diff 指针相等剪枝 | 未变子树零遍历 | 完全依赖不可变性；cullingContext 需单独比较 |
| Flat List | 支持 reparent | 比朴素树 diff 更复杂 |
| 尾部快速路径 | 追加场景 O(n) | 依赖「旧子节点先耗尽」这一顺序 |

## 8. 已发现的问题

| 编号 | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| A1-1 | 单次 diff 的 mutation 列表无上限、不分片 | `Differentiator.cpp:1361` | 大列表更新时内存尖峰与长阻塞（已在 06 文档记录） |
| A1-2 | `cloneTree` / `cloneMultiple` 可返回 `nullptr` | `ShadowNode.h:100-101, 111-112` | 失败时调用方若不判空会解引用空指针 |
| A1-3 | `unstable_Immediate` 不切线程，但注释暗示会切到主线程 | `EventQueue.h:36-39` vs `Scheduler.cpp:105-107` | 非主线程误用时无人拦截，直接在错误线程上 commit |
| A1-4 | StateUpdate 合并只看队尾 | `EventQueue.cpp:68-75` | 非连续的同 family 更新不会合并，批次内可能重复渲染 |
| A1-5 | `setParent` 契约型线程安全 | `ShadowNodeFamily.h:61-63` | 依赖「首次调用不并发」的外部约定，模型被绕过时无保护 |
| A1-6 | `componentDescriptorRegistries_` 弱引用条目不清理 | `ComponentDescriptorProviderRegistry.cpp:34-41` | 长生命周期进程中累积（已在 08 文档记录为 E1-2） |
