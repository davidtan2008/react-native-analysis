# 04 · 崩溃日志的捕获、收集、处理、上传

> **先说结论（重要）**：React Native **不包含崩溃日志的上传（upload）实现**。
>
> 它的职责边界是：**捕获 → 结构化 → 分发**。真正的「收集 + 上传」由宿主 App 或第三方 APM SDK 通过框架提供的扩展点完成。
>
> 本文会先讲清完整的捕获链路，再单独用一节说明 OSS 仓库里**实际存在的**上传通道（只有 DevTools 通道，且仅 Debug 可用），以及生产环境应当如何接入。

## 2. 捕获层：四道防线

RN 的错误捕获不是单点，而是分层兜底。**任意一层单独失效都还有下一层**。

### 2.1 第 1 层：JS 运行时全局兜底

`Libraries/Core/setUpErrorHandling.js:13-37`：

```js
if (global.RN$useAlwaysAvailableJSErrorHandling !== true) {
  const ExceptionsManager = require('./ExceptionsManager').default;
  ExceptionsManager.installConsoleErrorReporter();

  if (!global.__fbDisableExceptionsManager) {
    const handleError = (e: unknown, isFatal: boolean) => {
      try {
        ExceptionsManager.handleException(e, isFatal);
      } catch (ee: unknown) {
        const error = toError(ee);
        console.log('Failed to print error: ', error.message);
        throw e;   // ← 报告器自己挂了，就让原始异常继续传播
      }
    };
    const ErrorUtils = require('../vendor/core/ErrorUtils').default;
    ErrorUtils.setGlobalHandler(handleError);
  }
}
```

两个关键点：
1. `global.__fbDisableExceptionsManager` 是一个**逃生开关** —— App 可以完全关闭这套机制，接自己的错误处理。
2. `handleError` 里 `throw e` 的设计很重要：如果连错误报告都失败了，**必须让原始异常继续向上抛**，绝不能因为「报告器 bug」而吞掉真正的错误。

`ErrorUtils` 本身是全局对象（`Libraries/vendor/core/ErrorUtils.js` 最后一行 `export default global.ErrorUtils as ErrorUtils;`），必须在任何 `require` 之前设置 handler，否则被 guard 包装的模块不会走这套逻辑（该文件顶部注释有详细说明）。

### 2.2 第 2 层：Promise rejection

`Libraries/promiseRejectionTrackingOptions.js` 末尾：

```js
ExceptionsManager.handleException(
  new Error(
    `Uncaught (in promise, id: ${id})${message ? `: "${message}"` : ''}`,
    { cause: rejection },
  ),
  false /* isFatal */,
);
```

注意 `isFatal = false` —— **未处理的 Promise rejection 在 RN 中被降级为非致命错误**。原始 rejection 通过 `cause` 传递，最终会出现在 `extraData.stackSymbols` / `stackReturnAddresses` / `stackElements`（`JsErrorHandler.cpp:298-313`）。

### 2.3 第 3 层：console.error 拦截

`Libraries/Core/ExceptionsManager.js:182-268` `reactConsoleErrorHandler`。

这是最微妙的一段，源码 `:189-217` 有一大段注释解释「为什么需要防重入标志」。核心场景：

- `console.error` 被**多层 monkey patch**：本模块一次，DevTools 的 HMR 转发一次（`packages/react-native/Libraries/Core/setUpDeveloperTools.js:24-43`）。
- patch 顺序不可靠。
- 如果不加防重入，`handleException → console.error → reactConsoleErrorHandler → reportException → console.error → ...` 会死循环并重复上报。

防重入判据（`:188`）：

```js
if (inExceptionHandler || global.RN$inExceptionHandler?.()) {
  return;
}
```

其中 `inExceptionHandler` 是 JS 侧局部变量，`global.RN$inExceptionHandler` 是 C++ 侧的对应实现（见 2.4）。

还有两个细节：
- `:251-258`：`message.startsWith('Warning: ')` 的 React 警告**不上报到 native**（只显示）。这段逻辑在 `packages/polyfills/console.js` 中被**复制了一份**（`:612-649`），并留有 TODO `T206796580` 说明是等 C++ 管线全量落地后删除重复实现。
- `console.reportErrorsAsExceptions === false` 可让 App 关掉这个拦截（`:185-187`）。

### 2.4 第 4 层：C++ 侧三处兜底

全部汇聚到 `JsErrorHandler`：

| 位置 | 触发场景 |
| --- | --- |
| `ReactInstance.cpp:99-108` | `RuntimeExecutor` 执行任意 JS 回调时的 `catch` |
| `ReactInstance.cpp:154-159` | `RuntimeScheduler` 的 `onTaskError`（task 执行抛错） |
| `ReactInstance.cpp:531-568` | JS 主动调用 `global.RN$handleException` |

其中 `RuntimeScheduler_Modern::handleTaskError`（`RuntimeScheduler_Modern.cpp:498-504`）会**先清空所有队列**再上报：

```cpp
void RuntimeScheduler_Modern::handleTaskError(jsi::Runtime& runtime, jsi::JSError& error) {
  clearQueues();
  onTaskError_(runtime, error);
}
```

`clearQueues()`（`:506-515`）丢弃 `taskQueue_`、`pendingRenderingUpdates_`、`surfaceIdsWithPendingRenderingUpdates_` —— 避免在已崩溃的运行时上继续调度。

## 3. 处理层：`JsErrorHandler` 双管线

`ReactCommon/jserrorhandler/JsErrorHandler.{h,cpp}` 是全平台唯一的错误处理中枢。

### 3.1 `ProcessedError` 数据结构

`JsErrorHandler.h:20-38`：

```cpp
struct ProcessedError {
  struct StackFrame {
    std::optional<std::string> file;
    std::string methodName;
    std::optional<int> lineNumber;
    std::optional<int> column;
  };
  std::string message;
  std::optional<std::string> originalMessage;
  std::optional<std::string> name;
  std::optional<std::string> componentStack;
  std::vector<StackFrame> stack;
  int id;
  bool isFatal;
  jsi::Object extraData;
};
```

**这是 RN 错误系统的统一数据契约**。三端（iOS ObjC、Android Kotlin、JS）都把它映射成各自的字典 / Map，字段一一对应（见 §5）。

### 3.2 管线选择逻辑

`JsErrorHandler.cpp:229-254`：

```cpp
void JsErrorHandler::handleError(jsi::Runtime& runtime, jsi::JSError& error,
                                 bool isFatal, bool logToConsole) {
  if (!ReactNativeFeatureFlags::useAlwaysAvailableJSErrorHandling() && _isRuntimeReady) {
    try {
      handleJSError(runtime, error, isFatal);     // JS 管线
      return;
    } catch (jsi::JSError& ex) {
      logErrorWhileReporting("handleError(): Error raised while reporting using js pipeline. "
                             "Using c++ pipeline instead.", ex, error);
      _hasHandledFatalError = false;              // 重置，允许 C++ 管线重新上报
    }
  }
  handleErrorWithCppPipeline(runtime, error, isFatal, logToConsole);
}
```

**开关是 `_isRuntimeReady`**，它只在 bundle 求值完成后才置真（`ReactInstance.cpp:301-303`）：

```cpp
// TODO(T183610671): We need a safe/reliable way to enable the js
// pipeline from javascript. ...
if (!jsErrorHandler->hasHandledFatalError()) {
  jsErrorHandler->setRuntimeReady();
}
```

原因是：JS 管线依赖全局 `ErrorUtils`，而 `ErrorUtils` 由 bundle 里的 `setUpErrorHandling` 安装。**bundle 之前发生的错误（语法错误、初始化异常）无法走 JS 管线**，只能走 C++ 管线。这也解释了为什么 `_isRuntimeReady` 为假时，message 会被加上前缀（`JsErrorHandler.cpp:330`）：

```cpp
.message = _isRuntimeReady ? message : ("[runtime not ready]: " + message),
```

### 3.3 JS 管线

`ReactCommon/jserrorhandler/ErrorUtils.cpp:12-40`：

```cpp
void handleJSError(jsi::Runtime& runtime, const jsi::JSError& error, bool isFatal) {
  auto errorUtils = runtime.global().getProperty(runtime, "ErrorUtils");
  if (errorUtils.isUndefined() || !errorUtils.isObject() ||
      !errorUtils.getObject(runtime).hasProperty(runtime, "reportFatalError") ||
      !errorUtils.getObject(runtime).hasProperty(runtime, "reportError")) {
    throw jsi::JSError(runtime,
        "ErrorUtils is not set up properly. Something probably went wrong trying to load "
        "the JS bundle. Trying to report error " + error.getMessage(), error.getStack());
  }
  if (isFatal) { ... call reportFatalError ... }
  else          { ... call reportError ... }
}
```

**这里 `throw` 是刻意设计** —— `ErrorUtils` 缺失恰好意味着「bundle 加载失败」，这正是「JS 管线不可用」的信号，上层 catch 到就自动回退到 C++ 管线。

JS 管线的价值：可以通过 `RN$registerExceptionListener` 注册 JS 侧监听器，且 `extraData` 中可携带 `__getBundleMetadata()` 返回的任意 JS 对象（`JsErrorHandler.cpp:96-122`）。

### 3.4 C++ 管线

`JsErrorHandler.cpp:256-405`，按顺序做 8 件事：

**③ 组装 extraData**（`:280-313`）

> **⚠ extraData 在致命错误场景下可能整个丢失。**
> `extraData` 是一个 `jsi::Object`，跨 JNI 序列化回 Java 时需要读取 runtime 中的值。
> 当 runtime 已因致命错误进入坏状态时，读取会抛 `jsi::JSIException`。
> Android 侧为此专门写了两层兜底，源码注释直言
> *"an escaping exception aborts the whole process"*：
> 见 [18 文档 §3.3](./18-Android-JNI胶水层与异常穿透.md)。
>
> **对上报方的含义**：收到 `extraData == null` 或
> `extraData.extraDataMarshallingError` 时，说明这次错误发生在 runtime 异常状态，
> **这本身就是一个高价值的归因信号**（比正常错误的优先级更高）。

`getBundleMetadata`（`:96-122`）调用 JS 全局 `__getBundleMetadata`，**这是把「哪个 bundle 版本出的错」塞进错误上报的标准位置**。它被 try/catch 包裹，失败只记日志不阻断。

**④ 解析 stack**（`:323-324`）
```cpp
auto isHermes = runtime.global().hasProperty(runtime, "HermesInternal");
auto stackFrames = StackTraceParser::parse(isHermes, error.getStack());
```
Hermes 与 JSC 的 stack 格式不同，解析器在 `jserrorhandler/StackTraceParser.cpp`。

**⑤ 分配 id 并构造 ProcessedError**（`:326-338`）
```cpp
auto id = nextExceptionId();   // 静态局部变量，进程内单调递增
```

**⑥ 桥接回 JS + 可选 console 输出**（`:340-359`）
```cpp
auto data = bridging::toJs(runtime, processedError);
data.setProperty(runtime, "isComponentError", isComponentError);
if (logToConsole) { console.error(processedError.message); }
```

**⑦ 分发给 errorListeners，支持 `preventDefault()`**（`:361-390`）
```cpp
data.setProperty(runtime, "preventDefault", preventDefault);
for (auto& errorListener : _errorListeners) {
  try { errorListener(runtime, jsi::Value(runtime, data)); }
  catch (jsi::JSError& ex) { logErrorWhileReporting(...); }   // 一个 listener 坏不影响其它
}
if (*shouldPreventDefault) { return; }
```

**这是 RN 提供的最重要的业务扩展点**：JS 层可以 `global.RN$registerExceptionListener(fn)`，在 `fn` 中检查 `data.extraData`，如果判定为「自己已经处理了」（例如某个可预期的业务异常），调用 `data.preventDefault()` 即可**完全阻断**这次上报（包括阻断 native redbox 和崩溃）。

**⑧ fatal 去重 + 最终分发**（`:392-404`）
```cpp
auto errorType = errorObj.getProperty(runtime, "type");
auto isWarn = isEqualTo(runtime, errorType, "warn");
if (isFatal || !isWarn) {
  if (isFatal) {
    if (_hasHandledFatalError) { return; }   // 只上报第一个致命错误
    _hasHandledFatalError = true;
  }
  _onJsError(runtime, processedError);
}
```

两点：
- `type === 'warn'` 的错误**不上报到 native**（只在 DevTools 显示）。
- fatal **只上报一次**。`notifyOfFatalError()`（`:424-426`）供 JS 侧主动标记「已处理」。

### 3.5 JS 侧镜像逻辑

`Libraries/Core/ExceptionsManager.js:104-135` 做了对称的处理：DEV 下进 LogBox，PROD 下调 NativeExceptionsManager：

```js

  if (reportToConsole) {
    LogBox.addException({...data, isComponentError: !!e.isComponentError});
  }
} else if (isFatal || e.type !== 'warn') {
  const NativeExceptionsManager = require('./NativeExceptionsManager').default;
  if (NativeExceptionsManager) {
```

注意 `if (NativeExceptionsManager)` —— **在某些宿主环境下该模块可能不存在，此时错误会被静默吞掉**（这是一个可以改进的点，见 `06`）。

### 3.6 异常装饰器

`ExceptionsManager.js:36-54` 提供 `unstable_setExceptionDecorator`，允许在报错前给错误附加额外数据：

```js
function unstable_setExceptionDecorator(exceptionDecorator) {
  userExceptionDecorator = exceptionDecorator;
}

function preprocessException(data) {
  if (userExceptionDecorator && !inUserExceptionDecorator) {
    inUserExceptionDecorator = true;
    try { return userExceptionDecorator(data); }
    catch { /* Fall through */ }
    finally { inUserExceptionDecorator = false; }
  }
  return data;
}
```

**防重入做得很到位**（装饰器内部若再触发异常不会无限递归），但注释 `:25-28` 明确警告：

> data passed using this method should be strictly contained, as data that's not serializable/too large may cause issues with passing the error to the native code.

## 4. Source Map 符号化（仅 Debug）

生产环境的 stack 是 Hermes 字节码偏移，没法直接定位。符号化在 Debug 下走一条完全独立的 HTTP 链路：

```
LogBoxLog.handleSymbolicate()                       LogBoxLog.js:104-140
  → LogBoxSymbolication.symbolicate(stack, extraData) LogBoxSymbolication.js:52-61
      → symbolicateStackTrace(stack, extraData)      Libraries/Core/Devtools/symbolicateStackTrace.js:32-51
          → getDevServer()                          Libraries/Core/Devtools/getDevServer.js
          → POST {devServer.url}symbolicate
          body: JSON.stringify({stack, extraData})
```

`symbolicateStackTrace.js:36-39` 有硬前提：

```js
const devServer = getDevServer();
if (!devServer.bundleLoadedFromServer) {
  throw new Error('Bundle was not loaded from Metro.');
}
```

**即：非 Metro 加载的 bundle（生产包）完全无法符号化。** 这也是为什么生产环境的 `ProcessedError.extraData` 里特意放了 `rawStack`（`JsErrorHandler.cpp:293`）—— 留原始栈让后端配合上传的 source map 做符号化。

`getDevServer.js` 通过解析 `NativeSourceCode.getConstants().scriptURL` 得到 dev server 地址，失败则回落 `http://localhost:8081/`。

### 4.1 LogBox 中的符号化时序

`LogBoxData.js:156-186` 对 fatal 级别做了特殊处理：

```js
if (newLog.level === 'fatal') {
  // If possible, to avoid jank, we don't want to open the error before
  // it's symbolicated. To do that, we optimistically wait for
  // symbolication for up to a second before adding the log.
  const OPTIMISTIC_WAIT_TIME = 1000;
  ...

```

即「最多等 1 秒拿 symbolication 结果，避免为了显示错误而掉帧」。

### 4.2 符号化缓存

`LogBoxSymbolication.js:18`：

```js
const cache: Map<Stack, Promise<SymbolicatedStackTrace>> = new Map();
```

key 是 Stack **数组对象本身**（引用相等），而每次报错都会 `parseErrorStack` 产生新数组 —— 因此这个缓存**几乎不命中，且永不回收**（见 `06` 问题 P7）。

## 5. 平台分发与最终结局

### 5.1 iOS

**入口**：`RCTInstance.mm:587-640` `_handleJSError:withRuntime:`，逐字段转成 ObjC 字典后：

```objc
if (![_delegate instance:self
        didReceiveJSErrorStack:errorData[@"stack"] message:... isFatal:... extraData:...]) {
  JS::NativeExceptionsManager::ExceptionData jsErrorData{errorData};
  id<NativeExceptionsManagerSpec> exceptionsManager = [_turboModuleManager moduleForName:@"ExceptionsManager"];
  [exceptionsManager reportException:jsErrorData];
}
```

**关键契约**：`RCTInstanceDelegate` 的 `instance:didReceiveJSErrorStack:...` 返回 `YES` 表示「我处理了」，返回 `NO` 表示「请走默认逻辑」。

`RCTHost.mm:496-522` 是这一层的转发：

```objc
- (BOOL)instance:(RCTInstance *)instance didReceiveJSErrorStack:(...)stack message:(NSString *)message ... {
  if (![_hostDelegate respondsToSelector:@selector(host:didReceiveJSErrorStack:message:...)]) {
    return NO;      // App 没实现 → 回落到 ExceptionsManager
  }
  [_hostDelegate host:self didReceiveJSErrorStack:...];
  return YES;
}
```

该 API 在 `RCTHost.h:43-53` 已标记 `__attribute__((deprecated))`，注释写明 `// TODO(T205780509): Remove this api in react native v0.78` 以及「未来 bridgeless 的 JS 错误处理 API 将直接调用 exceptionsmanager」。

**终点**：`React/CoreModules/RCTExceptionsManager.mm`

### 7.3 生产环境接入 APM 的正确姿势

基于上面的扩展点，完整的生产上报方案应该是：

```
                      ┌──────────────────────────────────────┐
  JS Error ──────────►│ RN$registerExceptionListener         │
                      │   检查 extraData.bundleMetadata /    │
                      │   业务自定义字段                       │
                      │   不关心的调 preventDefault()          │
                      └──────────────┬───────────────────────┘
                                     │
  Native Fatal ──────────────────────►│ RCTInstanceDelegate                │
                                      │  instance:didReceiveJSErrorStack: │
                                      │  返回 YES 即完全接管（不再回落）  │
                                      │  （iOS，API 已 deprecated）        │
                                      └──────────────┬───────────────────┘
  Android ───────────────────────────►│ RedBoxHandler.handleRedbox(...)   │
                                      │  ReactNativeHost.getRedBoxHandler │
                                      └──────────────┬───────────────────┘
  全部错误 ──────────────────────────►│ unstable_setExceptionDecorator    │
                                      │  ExceptionsManager.js:36          │
                                      │  统一附加用户ID/设备ID/会话ID等   │
                                      └──────────────┬───────────────────┘
                                                     ▼
                                          自研 APM SDK（网络上传）
```

需要注意的坑：
1. **iOS 的 delegate API 已标记 deprecated**（`RCTHost.h:43-53`，计划 0.78 移除），届时会直接走 ExceptionsManager。届时需要迁移到 `RN$registerExceptionListener` + `unstable_setExceptionDecorator`。
2. `preventDefault()` 会阻断**全部**后续处理，包括 native 侧。如果你只是想「额外上报一份」而不是「接管」，**不要调用** `preventDefault()`。
3. `extraData` 必须是**可序列化的、小的**。源码注释 `ExceptionsManager.js:25-28` 明确警告：不可序列化 / 过大可能导致传递到 native 失败。
4. Android 的 `reportException` 在 fatal 时会 **throw**。如果你的自定义 `ExceptionsManager` 实现吞掉了这个异常，`ReactInstance.kt:300-305` 的 catch 逻辑会走不下去，RedBox 和 host 销毁都不会发生。
5. `extraData` 在 JNI marshalling 时可能为 `null`（`JReactExceptionManager.cpp:56-86` 的防御），Kotlin 侧字段是 `ReadableMap?`（`ReactJsExceptionHandler.kt:36-38` 有注释说明），消费时必须判空。
6. `bundleMetadata` 依赖 bundle 里有 `__getBundleMetadata` 全局。生产 bundle 如果没注入这个全局，字段会是 `null`（`JsErrorHandler.cpp:96-103`）。
