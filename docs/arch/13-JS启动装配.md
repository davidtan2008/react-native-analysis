# 13 · JS 启动装配：setup-env 的执行顺序与触发机制

> **模块**：A5（`Libraries/Core` + `src/private/setup` + `Libraries/ReactNative`）
> **基线**：react-native @ `9b131e42`（submodule `react-native/`，本文路径基准 = 该 submodule 根）
> **前置**：[11 文档](./11-运行时与错误桥.md) 讲了 C++ 侧 `ReactInstance::initializeRuntime` 注入的 `RN$*` 全局。
> 本文讲 **JS 侧**的对偶问题：谁、在什么时机、按什么顺序执行那十几个 `setUp*`。

## 1. 三段式入口

JS 环境的装配入口是一条**三跳委托链**，最终落到一个带幂等保护的函数。

```
① Metro 配置注入
   packages/metro-config/src/index.flow.js:63  ─┐
   community-cli-plugin/.../loadMetroConfig.js:63 ─┤
                                          ↓
② react-native/setup-env      src/setup-env.js:22
                                          ↓ require
③ setUpDefaultReactNativeEnvironment
   src/private/setup/setUpDefaultReactNativeEnvironment.js:13
```

### 1.1 Metro 的「主模块之前执行」钩子

`packages/metro-config/src/index.flow.js:61-65`：

```js
    serializer: {
      // NOTE: Overridden in community-cli-plugin
      getModulesRunBeforeMainModule: () => [
        require.resolve('react-native/setup-env'),
      ],
```

社区 CLI 插件会覆盖它（`packages/community-cli-plugin/src/utils/loadMetroConfig.js:60-72`）：

```js
    serializer: {
      // We can include multiple copies of setup-env here because Metro will
      // only add ones that are already part of the bundle
      getModulesRunBeforeMainModule: () => [
        require.resolve('react-native/setup-env', {
          paths: [ctx.root],
        }),
        ...outOfTreePlatforms.map(platform =>
          require.resolve(
            `${ctx.platforms[platform].npmPackageName}/setup-env`,
            {paths: [ctx.root]},
          ),
        ),
```

**「out-of-tree 平台」也能注册自己的 `setup-env`**（如 react-native-windows / react-native-macos）。
用 `{paths: [ctx.root]}` 从项目根解析，避免解析到 RN 内部的副本。

> **这里有一个易踩的坑，源码注释专门解释了**（`Libraries/Core/InitializeCore.js:30-36`）：
>
> ```
> // NOTE: This delegates to the `'react-native/setup-env'` entry point (rather
> // than calling `setUpDefaultReactNativeEnvironment` directly) so that
> // `src/setup-env.js` is pulled into the module graph. Metro's
> // `getModulesRunBeforeMainModule` only runs modules that are already part of
> // the bundle, and `InitializeCore` is a guaranteed graph entry (via
> // `ReactNativePrivateInitializeCore`). This keeps `'react-native/setup-env'`
> // reachable so it runs before the main module.
> ```
>
> **`getModulesRunBeforeMainModule` 只执行「已经在 bundle 图里」的模块。**
> 如果直接 `require('setUpDefaultReactNativeEnvironment')`，
> `setup-env` 就不在图里，Metro 找不到它可执行 —— 于是改为委托给 `setup-env`，
> 让它**因为被 InitializeCore 引用而必然入图**。

### 1.2 委托链

`packages/react-native/src/setup-env.js:22`：

```js
require('./private/setup/setUpDefaultReactNativeEnvironment').default();
```

`Libraries/Core/InitializeCore.js:37`（整个文件的有效内容）：

```js
require('../../src/setup-env');
```

> **`InitializeCore.js` 有 37 行，但只有 1 行代码。**
> 其余是文件头注释与 `@deprecated Since 0.87. Use 'react-native/setup-env' instead.`（`:25`）。
> 它保留下来是为了兼容老代码路径 —— 本身不再做任何工作。

## 2. 幂等保护

`src/private/setup/setUpDefaultReactNativeEnvironment.js:11-20`：

```js
let initialized = false;

export default function setUpDefaultReactNativeEnvironment(
  enableDeveloperTools: boolean = true,
) {
  if (initialized) {
    return;
  }

  initialized = true;
```

**用模块级 `let` 变量做一次性守卫**，且**在执行任何 require 之前就置位**。

两个细节：

| 细节 | 后果 |
| --- | --- |
| `initialized = true` 早于第一个 `require` | 即使某个 `setUp*` 抛异常，**重试也不会重跑**（部分初始化状态被固化） |
| 无返回值、无异常 | 初始化失败对调用方不可见 |

> **注意参数 `enableDeveloperTools` 的失效问题**：
> 首次调用若传 `false`，则 DevTools / LogBox / `checkNativeVersion` 都不会装（见 §3），
> **且后续再传 `true` 也无效** —— 因为 `initialized` 已是 `true`。
> 参数只对**第一次**调用有效，且失败是静默的。

## 3. 完整执行顺序（23 个 require）

`packages/react-native/src/private/setup/setUpDefaultReactNativeEnvironment.js:22-61` 的实际顺序。

**先看门控分布（实测）**：

| 门控 | `require` 次数 | 说明 |
| --- | --- | --- |
| 无条件 | **13** | `:22-25, 30-36, 43` |
| `__DEV__ && enableDeveloperTools` | **4** | `:28, 38-40` |
| Feature Flag（三个 Observer） | **3** + 3 次 Flag 求值 | `:48, 54, 60`，`require` 写在条件表达式里 |
| **合计** | **23** | |

> **注意 Flag 门控那 3 行**：`require('../../../src/private/featureflags/ReactNativeFeatureFlags')`
> 出现在 `if` 的条件表达式中（`:46, 52, 58`），
> 因此每个 Observer 实际产生 **2 次 `require` 调用**（1 次取 Flag + 1 次装模块），
> 但后一次在 Flag 关闭时**不会执行**，故上表按「执行次数」计为 3。

逐项顺序：

| # | require | 装了什么 | 条件 |
| --- | --- | --- | --- |
| 1 | `Libraries/Core/setUpGlobals` | 全局变量 | 总是 |
| 2 | `src/private/setup/setUpDOM` | DOM 兼容层 | 总是 |
| 3 | `src/private/setup/setUpPerformance` | `performance` | 总是 |
| 4 | `Libraries/Core/polyfillPromise` | `Promise` | 总是 |
| 5 | `Libraries/Core/setUpTimers` | `setTimeout` 等 | 总是 |
| 6 | `Libraries/Core/setUpReactDevTools` | DevTools 钩子 | `__DEV__ && enableDeveloperTools` |
| 7 | `Libraries/Core/setUpErrorHandling` | 错误处理 | 总是 |
| 8 | `Libraries/Core/setUpRegeneratorRuntime` | `async` 转译 | 总是 |
| 9 | `Libraries/Core/setUpXHR` | `XMLHttpRequest` | 总是 |
| 10 | `Libraries/Core/setUpAlert` | `alert` | 总是 |
| 11 | `Libraries/Core/setUpNavigator` | `navigator` | 总是 |
| 12 | `Libraries/Core/setUpBatchedBridge` | 批处理桥 | 总是 |
| 13 | `Libraries/Core/setUpSegmentFetcher` | 分段加载 | 总是 |
| 14 | `Libraries/Core/checkNativeVersion` | 版本检查 | `__DEV__ && enableDeveloperTools` |
| 15 | `Libraries/Core/setUpDeveloperTools` | 开发者工具 | `__DEV__ && enableDeveloperTools` |
| 16 | `Libraries/LogBox/LogBox` `.install()` | LogBox | `__DEV__ && enableDeveloperTools` |
| 17 | `Libraries/ReactNative/AppRegistry` | 应用注册表 | 总是 |
| 18 | `src/private/setup/setUpIntersectionObserver` | `IntersectionObserver` | Feature Flag |
| 19 | `src/private/setup/setUpMutationObserver` | `MutationObserver` | Feature Flag |
| 20 | `src/private/setup/setUpResizeObserver` | `ResizeObserver` | Feature Flag |

> 源文件用 `require(...)` 而非 `import`，**因为顺序即语义** ——
> 每个 `setUp*` 都往全局对象上挂东西，顺序错了就会读到未初始化的值。
> 静态 `import` 会被 bundler 提升，破坏这个顺序保证。

### 3.1 两个 Dev 分支

`:27-29` 与 `:37-41`：

```js
  if (__DEV__ && enableDeveloperTools) {
    require('../../../Libraries/Core/setUpReactDevTools');
  }
```

```js
  if (__DEV__ && enableDeveloperTools) {
    require('../../../Libraries/Core/checkNativeVersion');
    require('../../../Libraries/Core/setUpDeveloperTools');
    require('../../../Libraries/LogBox/LogBox').default.install();
  }
```

**共 4 个模块受 `__DEV__` 门控**，其中 `LogBox.install()` 是唯一带 `.default.install()` 形态的
（其余都是纯 `require` 副作用模块）。

`LogBox` 在**第 16 位**，晚于 `setUpErrorHandling`（第 7 位）——
**错误处理先就绪，LogBox 后装载**，这样初始化期间的错误也能被 LogBox 捕获。

### 3.2 三个 Feature Flag 门控

`:45-61`：

```js
  if (
    require('../../../src/private/featureflags/ReactNativeFeatureFlags').enableIntersectionObserverByDefault()
  ) {
    require('./setUpIntersectionObserver').default();
  }
```

三个 Observer 各自一个 Flag，**`require` 被写进条件表达式里**
（而不是顶部 import）—— 只有 Flag 开启才会把模块拉进 bundle。

| Observer | Flag | 状态 |
| --- | --- | --- |
| `IntersectionObserver` | `enableIntersectionObserverByDefault` | 默认关闭 |
| `MutationObserver` | `enableMutationObserverByDefault` | 默认关闭 |
| `ResizeObserver` | `enableResizeObserverByDefault` | 默认关闭 |

这三个是 Web API 兼容层（对应 manifest 里的 **B7** 模块）。

> **注意 Flag 的读取方式**：`require(...)` 出现在条件里，
> 意味着**每次调用 `setUpDefaultReactNativeEnvironment` 都会重新求值**。
> 但因为有 `initialized` 守卫，实际只会执行一次 —— 这个写法是为了**惰性求值**：
> Flag 关闭时模块根本不入 bundle，节省体积。

## 4. 顺序为什么重要

### 4.1 `setUpGlobals` 必须第一

它定义 `__DEV__`、`__BUNDLE_START_TIME__` 之类的编译期/启动期常量。
后面 13 个无条件执行的模块中有多个直接读 `__DEV__`，**顺序颠倒会读到 `undefined`**。

### 4.2 `polyfillPromise` 在 `setUpErrorHandling` 之前

`:25` 的 `polyfillPromise` 早于 `:30` 的 `setUpErrorHandling`。
错误处理链路（含 11 文档描述的 `RN$handleException` 桥接）大量依赖 Promise，
**必须先有 Promise 再装错误处理**。

### 4.3 `setUpTimers` 早于一切可能用定时器的模块

`:26`。`setUpSegmentFetcher`（`:36`）、`LogBox`（`:40`）都可能在初始化期间就用到定时器。

### 4.4 `AppRegistry` 放在 DevTools 之后

`:43`。AppRegistry 是业务代码的挂载点，放在最后意味着
**所有基础设施就绪后**业务才可能跑起来。

## 5. 与 C++ 侧的衔接

11 文档记录的 `ReactInstance::initializeRuntime`（`react/runtime/ReactInstance.cpp`）
在 C++ 侧注入 `RN$*` 全局并调用 `bindingsInstallFunc(runtime)`。

**两侧的时序关系**：

```
原生侧                                    JS 侧
─────────────────────────────────────────────────────────────
ReactInstance::initializeRuntime
  ├─ defineReadOnlyGlobal(RN$*)  ────────►  可被 JS 读取
  ├─ timerManager_->attachGlobals ───────►  定时器原生实现就位
  └─ bindingsInstallFunc(runtime)
       └─ 安装 TurboModule / BindingInstaller
─────────────────────────────────────────────────────────────
evaluateJavaScript(bundle)
  ├─ Metro 注入的 polyfills
  ├─ getModulesRunBeforeMainModule
  │    └─ react-native/setup-env  ◄────── 本文 §1-3 的全部内容
  └─ 业务主模块（AppRegistry.runApplication）
─────────────────────────────────────────────────────────────
setRuntimeReady()   ← 仅当 hasHandledFatalError() 为 false
```

**关键点**：`setup-env` 的执行发生在 `evaluateJavaScript` **内部**，
因此**必然早于 `setRuntimeReady()`**（`ReactInstance.cpp:301-303`）。

**所以 JS 启动装配阶段发生的任何未捕获错误，都会被标记为 `[runtime not ready]`**
（11 文档 §3.2）—— 这是一条对上报方可直接利用的归因信号。

## 6. 启动耗时视角

对「启动速度变慢」这个监控主题（05 文档），本模块提供的事实：

| 事实 | 对启动耗时的影响 |
| --- | --- |
| 23 个 `require` 全同步，无异步分片 | **全部在主线程串行执行**，无法与其他工作交错 |
| 4 个模块受 `__DEV__` 门控 | Release 下省去 DevTools/LogBox 的解析与执行 |
| 3 个 Observer 受 Feature Flag 且惰性 require | Release 下不进 bundle |
| 1 次 `Metro` 序列化期注入 | 在 bundling 期完成，运行期零成本 |
| `enableDeveloperTools` 一次性生效 | 传入 `false` 可跳过 4 个 Dev 模块 |

**没有任何 `setUp*` 是异步的或可延后的** —— 这是当前实现的形态，
也是 06 文档中「启动优化」类建议的着手点。

## 7. 本模块的设计要点

| 设计 | 收益 | 代价 / 风险 |
| --- | --- | --- |
| `setup-env` 作为唯一入口 | Metro 钩子与 App 代码共用一条路径 | 需要 `InitializeCore` 拉它入图（易踩坑） |
| 模块级 `initialized` 守卫 | 幂等，重复调用安全 | **部分初始化失败无法重试**；`enableDeveloperTools` 只生效一次 |
| 全同步 `require` | 顺序确定，无竞态 | 23 个 `require` 串行，无法分片 |
| `__DEV__` 门控 | Release 省 4 个模块 | Dev 与 Prod 行为分叉，问题可能只在 Dev 复现 |
| Feature Flag 惰性 require | 不启用则不入 bundle | Flag 读三次（三个 if 各一次） |
| 支持 out-of-tree 平台 | Windows/macOS 可扩展 | 需各自维护 `setup-env` |
| `InitializeCore` 保留为薄壳 | 兼容老路径 | 自身已无逻辑，易被误认为仍在做事 |

## 8. 已发现的问题

| 编号 | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| BOOT-1 | `initialized = true` 早于任何 `require`，失败后不可重试 | `src/private/setup/setUpDefaultReactNativeEnvironment.js:20` | 任一 `setUp*` 抛异常 → 环境半初始化且静默 |
| BOOT-2 | `enableDeveloperTools` 仅首次调用有效，无警告 | 同上 `:13-20` | 首次传 `false` 后再传 `true` 无效，无从诊断 |
| BOOT-3 | 初始化失败无返回值、无异常 | 同上（整个函数无 return） | 调用方无法判断装配是否成功 |
| BOOT-4 | 23 个 `require` 全同步串行（13 无条件 + 4 `__DEV__` + 3 FeatureFlag + 3 次 Flag 求值） | 同上 `:22-61` | 直接贡献启动耗时，无法与其他工作交错 |
| BOOT-5 | 三个 Feature Flag 各自 `require` 求值一次 | 同上 `:46, 52, 58` | 同一模块重复求值（实际被 `initialized` 掩盖） |
| BOOT-6 | `InitializeCore.js` 37 行仅 1 行代码 | `Libraries/Core/InitializeCore.js:37` | 搜索代码时易误判为装配入口 |
| BOOT-7 | `getModulesRunBeforeMainModule` 只跑已在图中的模块 | `packages/metro-config/src/index.flow.js:63-65` | 直接 require 实现会静默失效（源码已用注释警告） |
