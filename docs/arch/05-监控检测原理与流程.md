# 05 · 监控与检测的原理、流程（崩溃 / OOM / 白屏 / 启动变慢 / 内存泄漏 / 内容增长过快）

> **本文的核心目的是把「RN 实际有什么」和「业界默认以为 RN 有什么」区分开。**
>
> 每一节的结构：
> 1. **检测原理** —— 框架用什么机制发现这类问题
> 2. **采集流程** —— 数据从哪里来、怎么流转
> 3. **上报通道** —— 数据最终能到哪
> 4. **源码中的缺口** —— 明确指出不存在 / 失效的部分
>
> **交互式架构图**：[监控与检测能力全景：有什么、缺什么](./diagrams/05-monitoring.html)
> （主题与数据出口成对呈现，底部三张卡片直接给出「真正可用 / 部分覆盖 / 明确缺失」的结论）
>
> 结论速览：
>
> | 能力 | RN 是否有 | 成熟度 |
> | --- | --- | --- |
> | JS 崩溃捕获 | ✅ 有 | **完整可用**，全链路分层兜底 |
> | 原生崩溃捕获 | ❌ 无 | 只有 `RCTFatal` 主动抛；无信号/未捕获异常钩子 |
> | OOM / 内存压力响应 | ⚠️ 部分 | 有响应机制，**无 OOM 本身检测** |
> | 白屏检测 | ❌ 无 | 只有 `ActivityIndicator`，无看门狗 |
> | 启动耗时测量 | ⚠️ 部分 | 有 marker，**TTI 起点缺失、so 加载无测量** |
> | 内存泄漏检测 | ⚠️ 仅 Debug | `LeakChecker` 只在 `REACT_NATIVE_DEBUG` 编译 |
> | 内容增长监控 | ❌ 无 | 只有虚拟化窗口，**无增长速率监控** |
> | 卡顿 / 掉帧检测 | ⚠️ 仅 Dev | `longtask` 阈值 50ms；`FrameRateLogger` 原生模块已删 |

## 1. 崩溃监控

> 详细链路见 `04` 文档。此处只做监控视角的归纳。

### 1.1 检测原理

RN 对崩溃的「检测」本质是**异常传播链上的拦截**，而非主动探测：

| 拦截点 | 位置 | 捕获类型 |
| --- | --- | --- |
| JS 全局 handler | `setUpErrorHandling.js:24-35` | 未捕获异常 |
| Promise rejection tracker | `promiseRejectionTrackingOptions.js` | 未处理 rejection（非 fatal） |
| `console.error` 拦截 | `ExceptionsManager.js:182` | React 错误边界、警告 |
| `RuntimeExecutor` catch | `ReactInstance.cpp:99-108` | JS 回调 + **非 JS 的 std::exception** |
| `RuntimeScheduler` `onTaskError` | `ReactInstance.cpp:154-159` | 事件循环 task 抛错 |
| `MessageQueueThreadHandler` | Android `bridge/queue/MessageQueueThreadHandler.kt:19-25` | 队列线程异常（Android 独有） |
| `RCTLog` 原生日志 | iOS `RCTLog.mm:252-326` | `RCTLogError` 及以上 |

### 1.2 采集流程

```
异常发生
  → 归一化为 ProcessedError（11 个字段，见 04 §3.1）
  → 附加 extraData:
       jsEngine / rawStack / __DEV__ / bundleMetadata
       + cause 链的 stackSymbols / stackReturnAddresses / stackElements
  → 分配进程内单调递增的 id（nextExceptionId）
  → 分发
```

### 1.3 上报通道

| 通道 | 可用性 | 说明 |
| --- | --- | --- |
| `RCTHostDelegate`（iOS） | 可用，**已 deprecated** | 返回 YES 即接管 |
| `ReactJsExceptionHandler`（Android） | 可用 | JNI 回调，实现在 App 侧 |
| `RedBoxHandler`（Android） | 可用 | `ReactNativeHost.getRedBoxHandler()` |
| `RN$registerExceptionListener` | 可用 | JS 侧，支持 `preventDefault()` |
| `unstable_setExceptionDecorator` | 可用 | 全局附加字段 |
| DevTools CDP | **仅 Debug** | 实时流，无持久化 |

### 1.4 缺口

1. **无原生崩溃捕获**：全仓库无 `NSSetUncaughtExceptionHandler`、无 `signal(SIG*)`、无 `std::set_terminate`。C++ 崩溃（`std::terminate` / segfault）完全由系统处理，RN 拿不到任何结构化信息。
2. **iOS / Android 终局不一致**：
   - iOS Release：reload 耗尽后 `RCTFatal` → `@throw NSException` → **进程崩溃**
   - Android Release：`RedBox` + `ReactHost.destroy()` → **不崩溃**
   这会导致同一份代码在两端的崩溃率统计口径不同。
3. **bundle 加载失败行为不一致**：
   - iOS `RCTInstance.mm:468-484` → **无条件 `RCTFatal`**，必然崩溃
   - Android `DevSupportManagerBase.kt:819-827` → 只显示红框，**不崩溃**
4. **fatal 去重只有第一次**（`JsErrorHandler.cpp:396-401`），后续 fatal 被丢弃。对「雪崩式连续崩溃」场景会低估。
5. **无崩溃聚合 / 去重 / 采样**：每次都是完整 `ProcessedError`，全量上报。线上高频崩溃场景需要 App 侧自行做聚合限流。
6. **`extraData` 可能静默丢失**：JNI marshalling 失败时降级为 `null`（`JReactExceptionManager.cpp:56-86`），字段是 `ReadableMap?`。
7. **JS 侧 `if (NativeExceptionsManager)` 静默吞错**（`ExceptionsManager.js:125`）：模块不存在时错误直接消失。

## 2. OOM / 内存压力

### 2.1 检测原理：RN 只能「响应」压力，不能「检测」OOM

RN 订阅的是**系统内存压力通知**，而不是 OOM 本身。

**Android**：`ComponentCallbacks2.onTrimMemory(level)`。`MemoryPressureRouter.kt:17-57`：

```kotlin
public class MemoryPressureRouter(context: Context) : ComponentCallbacks2 {
  private val listeners = CopyOnWriteArrayList<MemoryPressureListener>()
  init { context.applicationContext.registerComponentCallbacks(this) }
  public fun destroy(context: Context) { context.applicationContext.unregisterComponentCallbacks(this) }
  override fun onTrimMemory(level: Int) { dispatchMemoryPressure(level) }
  @Deprecated("onLowMemory is deprecated, use onTrimMemory instead.")
  override fun onLowMemory(): Unit = Unit
  private fun dispatchMemoryPressure(level: Int) { for (l in listeners) l.handleMemoryPressure(level) }
}
```

注意在 **application 级别**注册，所以整个进程共享一个 router（`ReactHostImpl.kt:124`）。

**iOS**：`UIApplicationDidReceiveMemoryWarningNotification`。全仓库共 6 个观察者：

| 观察者 | 位置 | 动作 |
| --- | --- | --- |
| `RCTAppState` | `React/CoreModules/RCTAppState.mm:97-100` | 发 JS 事件 `memoryWarning` |
| `RCTInstance` | `RCTInstance.mm:154-157`（注册）/ `:166-168`（dealloc 移除） | 触发 Hermes GC |
| `RCTComponentViewRegistry` | `React/Fabric/Mounting/RCTComponentViewRegistry.mm:34-37` | `_recyclePool.clear()` |
| `RCTImageCache` | `Libraries/Image/RCTImageCache.mm:49-52` | `[_decodedImageCache removeAllObjects]` |
| `RCTAnimatedImage` | `Libraries/Image/RCTAnimatedImage.mm:52-55` | `CGImageSourceRemoveCacheAtIndex` |
| `RCTUIImageViewAnimated` | `Libraries/Image/RCTUIImageViewAnimated.mm:63-66` | 取消图片抓取队列 |

`RCTImageCache` 还在 `UIApplicationWillResignActiveNotification` 时清缓存（`RCTImageCache.mm:53-56`）。

### 2.2 采集流程：压力等级 → 是否 GC

`ReactCommon/react/runtime/ReactInstance.cpp:652-721` 是决策核心：

```cpp
void ReactInstance::handleMemoryPressureJs(int pressureLevel) {
  // The level is an enum value passed by the Android OS to an onTrimMemory
  // event callback. Defined in ComponentCallbacks2.
  enum AndroidMemoryPressure {
    TRIM_MEMORY_BACKGROUND = 40,          TRIM_MEMORY_COMPLETE = 80,
    TRIM_MEMORY_MODERATE = 60,            TRIM_MEMORY_RUNNING_CRITICAL = 15,
    TRIM_MEMORY_RUNNING_LOW = 10,         TRIM_MEMORY_RUNNING_MODERATE = 5,
    TRIM_MEMORY_UI_HIDDEN = 20,
  };
  switch (pressureLevel) {
    case TRIM_MEMORY_RUNNING_LOW:
    case TRIM_MEMORY_RUNNING_MODERATE:
    case TRIM_MEMORY_UI_HIDDEN:
      // For non-severe memory trims, do nothing.
      LOG(INFO) << "Memory warning (pressure level: " << levelName
                << ") received by JS VM, ignoring because it's non-severe";
      break;
    case TRIM_MEMORY_BACKGROUND:
    case TRIM_MEMORY_COMPLETE:
    case TRIM_MEMORY_MODERATE:
    case TRIM_MEMORY_RUNNING_CRITICAL:
      // For now, pressureLevel is unused by collectGarbage.
      LOG(INFO) << "Memory warning (pressure level: " << levelName
                << ") received by JS VM, running a GC";
      runtimeScheduler_->scheduleWork([=](jsi::Runtime& runtime) {
        TraceSection s("ReactInstance::handleMemoryPressure");
        runtime.instrumentation().collectGarbage(levelName);
      });
      break;
```

**iOS 硬编码为最严重的等级**（`RCTInstance.mm:642-649`）：

```objc
- (void)_handleMemoryWarning {
  if (_valid) {
    // Memory Pressure Unloading Level 15 represents TRIM_MEMORY_RUNNING_CRITICAL.
    static constexpr int unloadLevel = 15;
    _reactInstance->handleMemoryPressureJs(unloadLevel);
  }
}
```

### 2.3 内存数据采集：只有 `performance.memory`

`ReactCommon/react/nativemodule/webperformance/NativePerformance.cpp:266-274`：

```cpp
std::unordered_map<std::string, double> NativePerformance::getSimpleMemoryInfo(jsi::Runtime& rt) {
  auto heapInfo = rt.instrumentation().getHeapInfo(false);
  ...
}
```

JS 侧 `src/private/webapis/performance/Performance.js:96-118`：

```js
get memory(): MemoryInfo {
  const memoryInfo = NativePerformance.getSimpleMemoryInfo();
  if (memoryInfo.hasOwnProperty('hermes_heapSize')) {
    const { hermes_heapSize: totalJSHeapSize, hermes_allocatedBytes: usedJSHeapSize } = memoryInfo;
    return new MemoryInfo({ jsHeapSizeLimit: null, totalJSHeapSize, usedJSHeapSize });
  } else {
    // JSC and V8 has no native implementations for memory information in JSI::Instrumentation
    return new MemoryInfo();
  }
}
```

**注意 `jsHeapSizeLimit: null` —— Hermes 不通过 JSI 暴露堆上限**，所以无法据此做「接近 OOM」的预测。

### 2.4 上报通道

JS `performance.memory` → App 自定义上报。原生侧**没有任何**内存数值上报通道。

### 2.5 缺口

| 缺口 | 证据 |
| --- | --- |
| **Android 上 `memoryWarning` 事件根本不存在** | 检索 `memoryWarning` 在 `ReactAndroid/src/main`（`.kt`/`.java`）下**0 命中**；`DeviceEventManagerModule.kt` 里只有 `emitHardwareBackPressed` / `emitNewIntentReceived` / `invokeDefaultBackPressHandler`（`:36, 44, 55`），**没有任何 memory warning 派发方法**。JS 侧 `AppState.addEventListener('memoryWarning', ...)`（`Libraries/AppState/AppState.js:139-142`）在 Android 上是永久 no-op —— 不是「空实现」，是**连实现都不存在**。仅 iOS 有：`React/CoreModules/RCTAppState.mm:79` 声明事件名、`:112` 实际派发 |
| **C++ 侧有分级 GC 响应，JS 侧不可见** | `ReactInstance::handleMemoryPressureJs`（`ReactCommon/react/runtime/ReactInstance.cpp:652-720`）按等级分流：`TRIM_MEMORY_RUNNING_LOW`(10) / `MODERATE`(5) / `UI_HIDDEN`(20) 显式忽略，四档「严重」等级才调 `runtime.instrumentation().collectGarbage()`。**但这个分级只对 Android 有效** —— iOS 侧 `RCTInstance.mm:645-646` 硬编码 `unloadLevel = 15`（= `RUNNING_CRITICAL`），**每次内存警告都做全量 GC**。且两端的分级结果都**不进 JS**（详见 [19 文档 §4](./19-iOS平台层与Surface生命周期.md)） |
| **无 OOM 检测能力** | 只能被动收到系统压力通知；系统不通知的 OOM（如 V8/Hermes 堆溢出）RN 完全无感 |
| **无堆快照接口** | `jsi::Instrumentation` 定义了 `createSnapshotToFile` / `createSnapshotToStream` / `startHeapSampling` / `startTrackingHeapObjectStackTraces` / `getRecordedGCStats` / `dumpOpcodeStats`（`ReactCommon/jsi/jsi/instrumentation.h:26-129`），但 **RN 自身 C++ 代码中一个调用点都没有**。仅 Fantom 测试框架用了 `saveJSMemoryHeapSnapshot`（`src/private/testing/fantom/specs/NativeFantom.js:125`） |
| **无原生内存数值采集** | 无 RSS / PSS / native heap 读取接口。`ImageTelemetry`（`imagemanager/ImageTelemetry.h:21-36`）**没有 `memorySize` 字段**，只记 `willRequestUrlTime_` + `surfaceId` |
| **JSC 完全不支持内存统计** | `JSCRuntime.cpp:1451-1453` `setExternalMemoryPressure` 是空实现；`Performance.js:114-117` 明确返回空 `MemoryInfo` |
| **压力等级判定硬编码** | iOS 恒为 15（CRITICAL），无法区分真实严重程度；Android 侧 5/10/20 三个等级直接忽略 |
| **Android `UIManagerModule.MemoryTrimCallback` 是死代码** | `UIManagerModule.kt:540-547` 三个方法全是 `Unit`，注释却仍写着 "Listener that drops the CSSNode pool on low memory"，且仍在 `:96` 实例化、`:138/:152` 注册/注销 |
| **图片缓存无字节上限** | `RCTImageCache.mm:21-22` 只有 `RCTMaxCacheableDecodedImageSizeInBytes = 2MB`（单图上限）和 `RCTImageCacheTotalCostLimit = 20MB`（NSCache cost limit），逻辑正确但 20MB 是写死的静态量，App 需自己调 `RCTSetImageCacheLimits` |
| **无 in-flight 图片请求数上限** | `ImageFetcher.h:24-46` 的 `items_` 无并发上限；iOS `RCTImageLoader` 用串行 queue 但不限制 `NSURLSession` 任务数。背压完全依赖底层图片管线 |

## 3. 白屏检测

### 3.1 结论：RN 没有任何白屏检测

对 `blank` / `whiteScreen` / `blankScreen` / `watchdog` / `startupTimeout` / `firstRenderTimeout` / `ANR` 全仓库搜索，**框架代码中零命中**。

框架在这个问题上的态度是：**「用转圈圈遮住」，而不是「检测并上报」**。

### 3.2 现有的唯一手段：Loading View

`React/Base/RCTRootView.h:135-140`：

```objc
/**
 * A view to display while the JavaScript is loading, so users aren't presented
 * with a blank screen. By default this is nil, but you can override it with
 * (for example) a UIActivityIndicatorView or a placeholder image.
 */
@property (nonatomic, strong, nullable) UIView *loadingView;
```

`packages/react-native/React/Base/Surface/SurfaceHostingView/RCTSurfaceHostingView.mm:49, 226-245`：

```objc
// packages/react-native/React/Base/Surface/SurfaceHostingView/RCTSurfaceHostingView.mm:49
self.backgroundColor = [UIColor whiteColor];   // ← RN 自己就是那个白屏

// :226-245
- (void)_updateViews {
  self.isSurfaceViewVisible = RCTSurfaceStageIsRunning(_stage);
  self.isActivityIndicatorViewVisible = _autoHideDisabled || RCTSurfaceStageIsPreparing(_stage);
}
```

`dealloc`（`:55-58`）做 `[_surface stop]`，是唯一的自动拆卸。

### 3.3 为什么框架自己检不出来

`SurfaceHandler.cpp:37-62` `start()` 的执行顺序：

```cpp
link_.uiManager->startSurface(std::move(shadowTree), std::move(parameters.moduleName), ...);
// 或
link_.uiManager->startEmptySurface(std::move(shadowTree));

link_.status = Status::Running;      // ← 状态在这里就变成 Running
applyDisplayMode(parameters.displayMode);
```

`link_.status = Running` 发生在 `startSurface` 之后立刻执行，**早于第一帧真正挂载**。

iOS 侧的映射（`RCTFabricSurface.mm:160-164`）只把这个状态映射成 `RCTSurfaceStageRunning`，于是 `surface:didChangeStage:` 报的 "Running" **不代表内容已可见**。

**更关键的是：`RCTSurfaceStage.h:15-42` 定义的 8 个细分 bit 位（`SurfaceDidInitialRendering` / `InitialLayout` / `InitialMounting`）在 Fabric 中全是死代码** —— `RCTFabricSurface` 只产出两个聚合值。框架能表达「第一帧渲染了」这个信息，但从来没实现过。

### 3.4 最接近「内容已出现」的信号

**Android**：`ReactMarkerConstants.CONTENT_APPEARED`

`ReactRootView.java:525-529`：

```java
if (mShouldLogContentAppeared) {
  mShouldLogContentAppeared = false;
  String jsModuleName = getJSModuleName();
  ReactMarker.logMarker(ReactMarkerConstants.CONTENT_APPEARED, jsModuleName, mRootViewTag);
}
```

在 `runApplication()`（`:774`）置位、`onViewAdded` 触发。**但它测的是「第一个子 view 被加进来」，不是「用户看到了内容」**。视图树可能是空的、或者内容在屏幕外。

**iOS**：`RCTSurfaceHostingProxyRootView.mm:118-131`

```objc
- (void)surface:(RCTSurface *)surface didChangeStage:(RCTSurfaceStage)stage {
  [super surface:surface didChangeStage:stage];
  if (RCTSurfaceStageIsRunning(stage)) {
    [_bridge.performanceLogger markStopForTag:RCTPLTTI];
```

### 3.5 阻塞式等待：唯一的「强制等到出画面」API

`RCTFabricSurface.mm:262-277`：

```objc
- (BOOL)synchronouslyWaitFor:(NSTimeInterval)timeout {
  auto mountingCoordinator = _surfaceHandler->getMountingCoordinator();
  if (!mountingCoordinator) { return NO; }
  if (!mountingCoordinator->waitForTransaction(std::chrono::duration<NSTimeInterval>(timeout))) {
    return NO;
  }
  [_surfacePresenter.mountingManager scheduleTransaction:mountingCoordinator];
  return YES;
}
```

这是 opt-in 的、会阻塞的辅助方法，不是看门狗。

### 3.6 渲染调度无超时

`RuntimeScheduler_Modern.cpp:204-211`：

```cpp
void RuntimeScheduler_Modern::scheduleRenderingUpdate(
    SurfaceId surfaceId, RuntimeSchedulerRenderingUpdate&& renderingUpdate) {
  TraceSection s("RuntimeScheduler::scheduleRenderingUpdate");
  surfaceIdsWithPendingRenderingUpdates_.insert(surfaceId);
  pendingRenderingUpdates_.push(renderingUpdate);
}
```

**无超时、无 deadline、无取消。** 排在队列里的渲染更新只会在**下一个 tick 的 update the rendering 阶段**被排空（`:354-405`）。

`Scheduler.cpp:299-322` 中如果 `delegate_ == nullptr`，mounting coordinator 会被**静默丢弃**——无日志、无重试。

唯一有界的地方是 microtask 排空（`RuntimeScheduler_Modern.cpp:456-479`）：

```cpp
const static unsigned int kRetriesBound = 255;
while (retries < kRetriesBound) { if (runtime.drainMicrotasks()) { break; } retries++; }
if (retries == kRetriesBound) { throw std::runtime_error("Hits microtasks retries bound."); }
```

**这是防「微任务死循环」而非防「白屏」**。而且它抛出的 `std::runtime_error` 会被 `RuntimeExecutor` 的 `catch (std::exception& ex)` 捕获（`ReactInstance.cpp:104-108`），转成 `"Non-JS exception: ..."` 走错误上报。

### 3.7 缺口总结

| 缺口 | 影响 |
| --- | --- |
| 无「首帧渲染成功」信号 | 无法区分「白屏」与「正在加载」与「内容确实为空」 |
| 无渲染超时看门狗 | JS 卡死 / surface 从未 complete 时无任何信号 |
| `RCTSurfaceStage` 细分 bit 位未实现 | 框架有能力表达但没实现 |
| `completeSurface` 无失败路径 | `UIManager.cpp:195-227` 中 `shadowTreeRegistry_.visit` 在 surface 已 stop 时静默 no-op |
| `renderApplication.js` 无 error boundary 兜底 | 根组件抛错 → surface 什么都不显示（Dev 下有 LogBox，Prod 下静默） |
| Surface 启动被延迟执行 | `RCTHost.mm:437-438` `[weakSurface start]` 放在 `BufferedRuntimeExecutor` 中；App 的 loading view 若在此之前隐藏，必然白屏 |
| **`loadingView` 无默认值** | iOS `RCTSurfaceHostingView` 的「准备中」兜底 UI 来自宿主注入的 `activityIndicatorViewFactory`（`RCTSurfaceHostingView.mm:147-151`）；未注入时 `_activityIndicatorView` 为 nil，`intrinsicContentSize` 返回 `CGSizeZero` → **真白屏**。框架不提供默认 spinner（见 [19 文档 §3.1](./19-iOS平台层与Surface生命周期.md)） |
| `RCTFabricSurface` 观察者未移除 | `RCTFabricSurface.mm:71-74` 注册了 `UIContentSizeCategoryDidChangeNotification`，全文件无对应 `removeObserver` |

**自建方案建议**：
1. 用 `onLayout` / `UIManagerMountHook::shadowTreeDidMount`（`UIManager.cpp:707`）自建首帧信号。
2. Android 可用 `CONTENT_APPEARED` marker + `ReactRootView` 的 `getChildCount()` 组合判断。
3. 加载视图的显隐必须由业务控制，不要依赖 `RCTSurfaceHostingView` 的自动切换（因为 `stage` 语义不可靠）。

## 4. 启动速度变慢

### 4.1 采集原理：ReactMarker 双通道

`ReactCommon/cxxreact/ReactMarker.h:19-37` 定义了 17 个 marker：

```cpp
enum ReactMarkerId {
  APP_STARTUP_START,            APP_STARTUP_STOP,
  INIT_REACT_RUNTIME_START,      INIT_REACT_RUNTIME_STOP,
  NATIVE_REQUIRE_START,         NATIVE_REQUIRE_STOP,
  RUN_JS_BUNDLE_START,          RUN_JS_BUNDLE_STOP,
  CREATE_REACT_CONTEXT_STOP,
```

**① 注册阶段**（`UIManager.cpp:106-110`）：

**② 检测阶段**（`LeakChecker.cpp:25-41`）：

```cpp
void LeakChecker::stopSurface(SurfaceId surfaceId) {
  if (previouslyStoppedSurface_ > 0) {
    // Dispatch the check onto JavaScript thread to make sure all other
    // cleanup code has had chance to run.
    runtimeExecutor_([previouslyStoppedSurface = previouslyStoppedSurface_, this](jsi::Runtime& runtime) {
      runtime.instrumentation().collectGarbage("LeakChecker");
      // For now check the previous surface because React uses double
      // buffering which keeps the surface that was just stopped in
      // memory. This is a documented problem in the last point of
      // https://github.com/facebook/react/issues/16087
      checkSurfaceForLeaks(previouslyStoppedSurface);
    });
  }
  previouslyStoppedSurface_ = surfaceId;
}
```

**检查的是「上一个」surface**，源码注释明确说明这是因为 React 双缓冲机制（引用 facebook/react#16087）导致刚 stop 的 surface 还在内存里。**这意味着：最后一个 stop 的 surface 永远不会被检查。**

**③ 判定与上报**（`:43-58`）：

```cpp
void LeakChecker::checkSurfaceForLeaks(SurfaceId surfaceId) const {
  auto weakFamilies = registry_.weakFamiliesForSurfaceId(surfaceId);
  unsigned int numberOfLeaks = 0;
  for (const auto& weakFamily : weakFamilies) {
    auto strong = weakFamily.lock();
    if (strong) { ++numberOfLeaks; }
  }
  if (numberOfLeaks > 0) {
    LOG(ERROR) << "[LeakChecker] Surface with id: " << surfaceId
               << " has leaked " << numberOfLeaks << " components out of " << weakFamilies.size();
  }
  registry_.removeFamiliesWithSurfaceId(surfaceId);
}
```

**上报方式：`glog` 的 `LOG(ERROR)`，仅进 logcat/syslog。没有结构化上报通道，没有 JS 可见性，App 拿不到。**

## 7. 附：卡顿 / 掉帧（补充）

虽不在需求列表内，但与「启动变慢」「内存泄漏」强相关，一并记录。

### 7.1 Long Task：唯一可用的 jank 近似

`ReactCommon/react/performance/timeline/PerformanceEntryReporter.h:29-33`：

```cpp
// Aligned with maxBufferSize implemented by browsers
// https://w3c.github.io/timing-entrytypes-registry/#registry
constexpr size_t EVENT_BUFFER_SIZE = 150;
constexpr size_t LONG_TASK_BUFFER_SIZE = 200;
constexpr size_t RESOURCE_TIMING_BUFFER_SIZE = 250;
constexpr HighResDuration LONG_TASK_DURATION_THRESHOLD = HighResDuration::fromMilliseconds(50);
```

`RuntimeScheduler_Modern.cpp:482-496`：

```cpp
void RuntimeScheduler_Modern::reportLongTasks(const Task&, HighResTimeStamp startTime, HighResTimeStamp endTime) {
  auto reporter = performanceEntryReporter_;
  if (reporter == nullptr) { return; }
  if (longestPeriodWithoutYieldingOpportunity_ >= LONG_TASK_DURATION_THRESHOLD) {
    reporter->reportLongTask(startTime, endTime - startTime);
  }
}
```

在每个 tick 末尾调用（`:339-341`）：

```cpp
auto taskEndTime = now_();
markYieldingOpportunity(taskEndTime);
reportLongTasks(task, taskStartTime, taskEndTime);
```

**注意它的判定依据是「距上次让出机会的最长间隔」，而不是「本 task 自身耗时」**。这更接近「主线程连续繁忙时长」而非 Web 规范的 longtask 语义。
