## 2. 【核心 FFF-1】同一条 entry 流，两条消费路径：一条有界、一条无界

### 2.1 五个缓冲的形态对照

| --- | --- | --- | --- |

### 2.2 无界的那两个：逐字实现

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryKeyedBuffer.h:34-38
 private:
  std::unordered_map<std::string, std::vector<PerformanceEntry>> entryMap_{};
```

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryKeyedBuffer.cpp:12-22
void PerformanceEntryKeyedBuffer::add(const PerformanceEntry& entry) {
  auto name =
      std::visit([](const auto& entryData) { return entryData.name; }, entry);

  auto node = entryMap_.find(name);

  if (node != entryMap_.end()) {
    node->second.push_back(entry);
  } else {
    entryMap_.emplace(name, std::vector<PerformanceEntry>{entry});
  }
}
```

**两层都无界**：

| 维度 | 是否受限 | 说明 |
| --- | --- | --- |
| **同一条目的条目数** | **无** | `node->second.push_back(entry)` —— **永不淘汰** |
| **条目总数（name 的种类数）** | **无** | `entryMap_.emplace(name, ...)` —— 每个新 name 一个 vector |

**对比环形缓冲的淘汰逻辑**：

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/CircularBuffer.h:44-57
  bool add(const T &el)
  {
    if (entries_.size() < maxSize_) {
      // Haven't reached max buffer size yet, just add and grow the buffer
      entries_.emplace_back(el);
      return false;
    } else {
      // Overwrite the oldest (but already consumed) element in the buffer
      entries_[position_] = el;
      position_ = (position_ + 1) % entries_.size();
      return true;
    }
  }
```

**环形缓冲满了会覆盖最旧的并返回 `true`（表示「丢弃了一条」）**；**keyed 缓冲永远不会返回 `true`**。

### 2.3 完整的可达性链条

| 步骤 | 位置 | 证据 |
| --- | --- | --- |
| ① JS 调用 `performance.mark(name)` | `packages/react-native/Libraries/Performance/`（JS 侧） | — |
| ② TurboModule 入口 | `packages/react-native/ReactCommon/react/nativemodule/webperformance/NativePerformance.cpp` | `NativePerformance` 是 `performance` 对象的绑定 |
| ③ 进入 C++ reporter | `packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryReporter.cpp:198` | `markBuffer_.add(entry);` |
| ④ 进入无界容器 | `packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryKeyedBuffer.cpp:17` | `node->second.push_back(entry);` |

**`measure` 同理**（`PerformanceEntryReporter.cpp:219` `measureBuffer_.add(entry);`）。

### 2.4 每条 entry 占多少内存

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntry.h:24-28
struct AbstractPerformanceEntry {
  std::string name;
  HighResTimeStamp startTime;
  HighResDuration duration = HighResDuration::zero();
};
```

| 字段 | 大小（量级） |
| --- | --- |
| `std::string name` | **≥ 32 字节**（libstdc++ SSO 容量）+ 堆分配（若 > 15 字符） |
| `startTime` | 8 字节 |
| `duration` | 8 字节 |
| `PerformanceEntry` 本身 | **`std::variant`**，取最大成员的大小 |

**即每条 mark/measure 至少约 **50–60 字节**，加上 `name` 的堆分配。**

**触发条件的量级**：一个每帧调用 60 次 `performance.mark()` 的动画 → **每秒 60 条 → 每分钟 3,600 条 → 每小时约 21 万条 → 约 12 MB**。
**且永不释放，直到显式调用 `performance.clearMarks()` / `clearMeasures()`。**

### 2.5 存在清理 API —— 但默认不调用

```cpp
// packages/react-native/ReactCommon/react/nativemodule/webperformance/NativePerformance.cpp:185-206
void NativePerformance::clearMarks(...)
    ... PerformanceEntryReporter::getInstance()->clearEntries(...)
void NativePerformance::clearMeasures(...)
    ... PerformanceEntryReporter::getInstance()->clearEntries(...)
```

**即 JS 侧有 `performance.clearMarks()` / `clearMeasures()`** ✓ —— **有出口，但默认不调用**。

**这也意味着：这不是「无法清理」，而是「默认不清理且无上限」** —— 与「缓存无界」的判定需要区分：
**若调用方从不清理，就是无界增长；若每次测量后清理，就没问题。**

**因此本文的准确表述是**：
**「无上限 + 默认不清理 + 无丢弃可见性」三者叠加才构成风险**（见 §3）。

### 2.6 对照：CDP 上报路径是**流式零缓冲**的

```cpp

/**
 * [Experimental] Reports CDP interaction events via the

```

```cpp

/**
 * [Experimental] Reports new Performance Issues via the
 * "__react_native_perf_issues_reporter" runtime binding.
 *

```

| | 缓冲路径（timeline） | 上报路径（cdpmetrics） |
| --- | --- | --- |
| **存储** | `PerformanceEntryBuffer`（环形/无界） | **无存储**（listener 收到即报） |
| **内存** | 三个有界 + **两个无界** | **零** |
| **生命周期** | 直到显式 `clear` | 即用即弃 |
| **用途** | `performance.getEntries()` 等 JS API | DevTools 的实时指标 |

**即：同一个 `PerformanceEntry` 流的另一条消费路径是「零缓冲」的** ——
**说明 RN 团队完全知道「上报不该缓冲」这个原则**，
**只是 timeline 那条路径出于「JS 可回查历史」的需求而选择了缓冲**，
**而这个需求没有配套的上限**。

## 3. 【核心 FFF-2】监控盲区：`getDroppedEntriesCount(MARK|MEASURE)` 恒为 `0`

### 3.1 丢弃计数的定义

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryBuffer.h:27-38
class PerformanceEntryBuffer {
 public:
  HighResDuration durationThreshold = DEFAULT_DURATION_THRESHOLD;
  size_t droppedEntriesCount{0};
  ...
  virtual void add(const PerformanceEntry &entry) = 0;
```

**`droppedEntriesCount` 在基类里，初值 0。**

### 3.2 只有环形缓冲会递增它

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryCircularBuffer.cpp:10-14
void PerformanceEntryCircularBuffer::add(const PerformanceEntry& entry) {
  if (buffer_.add(entry)) {
    droppedEntriesCount += 1;
  }
}
```

**`PerformanceEntryKeyedBuffer::add` 里没有任何 `droppedEntriesCount` 操作** —— 实测确认：

| 文件 | `droppedEntriesCount` 出现次数 |
| --- | --- |
| `packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryCircularBuffer.cpp` | **2**（读 + 写） |
| `packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryKeyedBuffer.cpp` | **0** |

### 3.3 对外的查询接口

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceEntryReporter.cpp:111-117
uint32_t PerformanceEntryReporter::getDroppedEntriesCount(
    PerformanceEntryType entryType) const noexcept {
  std::shared_lock lock(buffersMutex_);

  return (uint32_t)getBuffer(entryType).droppedEntriesCount;
}
```

**即 `getDroppedEntriesCount(MARK)` 与 `getDroppedEntriesCount(MEASURE)` **恒返回 0**。**

### 3.4 这构成一条真实的监控盲区

| 观测维度 | 环形缓冲（EVENT/LONGTASK/RESOURCE） | keyed 缓冲（MARK/MEASURE） |
| --- | --- | --- |
| **条目数有上限** | ✅ 150 / 200 / 250 | ❌ 无 |
| **丢弃可见** | ✅ `droppedEntriesCount` 递增 | ❌ **恒为 0** |
| **能否据此发现增长** | ✅ 能（丢弃数 > 0 说明在滚动） | ❌ **不能** |

> **即：唯一能反映「缓冲区正在被填满」的指标，恰好在最需要它的两个类型上恒为 0。**
>
> **监控指标不仅没覆盖这条无界增长，反而给出了「一切正常」的假象** ——
> 这比「没有指标」更危险。
>
> **与 05 文档「源码中的缺口」的对应**：05 文档指出 RN 的监控多为**扩展点**而非实现；
> **本文补上一个「有实现但指标失真」的新形态**。

### 3.5 修复方向（低成本）

| 方案 | 说明 |
| --- | --- |
| **A. 给 keyed 缓冲加上限** | 与环形缓冲对齐（如每个 name 限 N 条、总条数限 M 条），满了同样递增 `droppedEntriesCount` |
| **B. 至少让 `droppedEntriesCount` 反映真实条目数** | 把 `getDroppedEntriesCount` 改成返回「当前条目数」而非「丢弃数」，或加一个 `size()` 接口 |
| **C. 在 `PerformanceEntryReporter` 里对 keyed 缓冲做总量统计** | 上报一个「mark/measure 总条目数」指标 |

## 4. 【核心 FFF-3】`CircularBuffer` 的两个边界：实测一次 SIGSEGV

### 4.1 `operator[]` 在空缓冲上是整数除零

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/CircularBuffer.h:60-63
  T &operator[](size_t idx)
  {
    return entries_[(position_ + idx) % entries_.size()];
  }
```

**`entries_.size() == 0` 时 → `% 0` → 整数除零 → 未定义行为。**

**实测（`-O0`）**：

```
构造后 size=0
访问 operator[0] ...
得到 0
  → 退出码=0
```

**注意实测结果是「不崩」—— 这恰恰是 UB 的危险之处**：
x86 的 `div` 指令除零会触发 `#DE` → SIGFPE，**但编译器在 UB 下可以生成任何代码**
（本次 `-O0` 下它生成了返回 0 的代码）。

> **因此不能把「实测没崩」当作「安全」** ——
> **换一个编译器版本或优化级别就可能变成 SIGFPE。**

### 4.2 `maxSize_ == 0` 时 `add()` **确定崩溃**

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/CircularBuffer.h:44-57
    if (entries_.size() < maxSize_) {   // 0 < 0 → false
      entries_.emplace_back(el);
      return false;
    } else {
      entries_[position_] = el;        // ← 空 vector 的 operator[] → 越界
      position_ = (position_ + 1) % entries_.size();   // ← 又是 % 0
      return true;
    }
```

**实测**：

```
CircularBuffer(0) 后 add() ...
  → 退出码=139        ← SIGSEGV
```

**注意两条路径都坏了**：
① `entries_[position_]` —— **空 `std::vector` 的 `operator[]` 是确定的越界访问** → SIGSEGV；
② `position_ = (position_ + 1) % entries_.size()` —— 又是 `% 0`。

**这是「确定崩溃」而非 UB 的不确定形态** —— 因为 `std::vector::operator[]` 的越界是确定的内存访问。

### 4.3 当前是否可达

| 检查 | 结果 |
| --- | --- |
| `maxSize_ == 0` 的构造 | **不可达** —— 三个缓冲都是常量 **150 / 200 / 250**（`PerformanceEntryReporter.h:29-31`） |
| `operator[]` 在空缓冲上的调用 | **生产代码零调用方** —— `CircularBuffer::operator[]` 只在 `clear(predicate)` 内部被用到，而那里的循环条件 `i < entries_.size()` 保证非空 |
| `clear()` 之后访问元素 | `clear()` 会清空 `entries_` 并把 `position_` 归零；此后 `add()` 走 `emplace_back` 分支（不碰 `operator[]`）✓ |

| 项 | 判定 |
| --- | --- |
| **当前是否造成功能问题** | **否** |
| **风险类型** | **结构脆弱** —— 构造函数不校验 `maxSize > 0`；`operator[]` 不校验非空 |
| **修复成本** | 极低：`add()` 里加 `if (maxSize_ == 0) return false;`，`operator[]` 加 `assert(!entries_.empty())` |

### 4.4 一个正面细节：`reserve` 保证指针稳定

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/CircularBuffer.h:30-33
  explicit CircularBuffer(size_t maxSize) : maxSize_(maxSize)
  {
    entries_.reserve(maxSize_);
  }
```

（出处：`packages/react-native/ReactCommon/react/performance/timeline/CircularBuffer.h:30-33`）

**注释说明了原因**：

```
 * Note that the space for maxSize elements is reserved on construction. This
 * ensures that pointers to elements remain stable across add() operations.
```

**即「预留容量以保证指针稳定」是一个被显式设计并解释过的取舍** ✓ —— **这与 63 文档 §3.5 的 `MapBuffer` 单写语义同源**。

**但要注意**：`reserve(maxSize_)` 在 `maxSize_` 很大时会**立即分配**整块内存 ——
**对 `CircularBuffer(0)` 无害（reserve(0) 不分配）**，对 `CircularBuffer(150)` 会预分配 150 个 `PerformanceEntry`（约 9 KB）✓ 可接受。

## 5. 【核心 FFF-4】`RAMBundleRegistry` 完全无锁，且有 TOCTOU

### 5.1 实现全文的关键部分

```cpp
// packages/react-native/ReactCommon/cxxreact/RAMBundleRegistry.cpp:36-62
JSModulesUnbundle::Module RAMBundleRegistry::getModule(
    uint32_t bundleId,
    uint32_t moduleId) {
  if (m_bundles.find(bundleId) == m_bundles.end()) {
    if (!m_factory) {
      throw std::runtime_error(
          "You need to register factory function in order to "
          "support multiple RAM bundles.");
    }

    auto bundlePath = m_bundlePaths.find(bundleId);
    if (bundlePath == m_bundlePaths.end()) {
      throw std::runtime_error(
          "In order to fetch RAM bundle from the registry, its file "
          "path needs to be registered first.");
    }
    m_bundles.emplace(bundleId, m_factory(bundlePath->second));
  }

  auto module = getBundle(bundleId)->getModule(moduleId);
```

### 5.2 三处问题

| # | 问题 | 说明 |
| --- | --- | --- |
| ① | **完全无锁** | `m_bundles` / `m_bundlePaths` 是普通成员（`RAMBundleRegistry.h`），`registerBundle` / `getModule` / `getBundle` **都不加锁** |
| ② | **TOCTOU** | `m_bundles.find(bundleId)` 检查后，`m_bundles.emplace(...)` 写入 —— **中间有窗口**；而 `getBundle` 里又用 `.at()` 查一次 |
| ③ | **`emplace` 可能不插入** | 若并发下另一个线程已插入同一 `bundleId`，`emplace` **不覆盖**（返回 false）—— 但 `m_factory` **已经被调用了**（副作用浪费：文件已读入内存又被丢弃） |

### 5.3 与同模块的对照：`PerformanceObserverRegistry` **有锁** ✓

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserverRegistry.cpp:11-35
void PerformanceObserverRegistry::addObserver(
    std::shared_ptr<PerformanceObserver> observer) {
  std::lock_guard guard(observersMutex_);
  observers_.insert(observer);
}
...
void PerformanceObserverRegistry::queuePerformanceEntry(
    const PerformanceEntry& entry) {
  std::lock_guard lock(observersMutex_);

  for (auto& observer : observers_) {
    observer->handleEntry(entry);
  }
}
```

**三个方法全部持锁** ✓ —— **同一个模块里，一个有锁一个没锁**。

> **对照 64 文档 DDD-1**：那里是「写路径没有独占锁」；
> **这里是「整个类没有锁」** —— **64 文档的「有锁但用错」比这里的「完全没锁」好得多**。

### 5.4 影响范围与现状

| 项 | 说明 |
| --- | --- |
| **所在条件** | `#ifndef RCT_REMOVE_LEGACY_ARCH` —— **legacy 架构关闭时整个文件被编译掉** |
| **调用方** | `JSModulesUnbundle` 的多 bundle 场景（Metro RAM bundle 分包） |
| **当前是否造成功能问题** | **未确认** —— 需要确认 `registerBundle` 与 `getModule` 是否真在不同线程 |
