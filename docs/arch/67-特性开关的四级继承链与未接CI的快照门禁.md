## 3. 【核心 GGG-1 / GGG-2】Stable 档与 `config.js` 的声明脱钩

### 3.1 手写 Stable 文件只覆写了 **1 个** flag

```cpp
// packages/react-native/ReactCommon/react/featureflags/ReactNativeFeatureFlagsOverridesOSSStable.h:16-22
class ReactNativeFeatureFlagsOverridesOSSStable : public ReactNativeFeatureFlagsDefaults {
 public:
  bool useNativeViewConfigsInBridgelessMode() override
  {
    return true;
  }
};
```

**全文只覆写这一个。**

### 3.2 而 `config.js` 里声明为 `'stable'` 档的是**另外 3 个**

**实测**（逐个从 `config.js` 解析）：

| flag | `defaultValue` | `expectedReleaseValue` | `ossReleaseStage` | `purpose` | 声明行 |
| --- | --- | --- | --- | --- | --- |
| `enableBridgelessArchitecture` | `true` | `true` | **`'stable'`** | `release` | `:216` |
| `fuseboxAssertSingleHostState` | `true` | `true` | **`'stable'`** | `operational` | `:670` |
| `fuseboxScreenshotCaptureEnabled` | `true` | `true` | **`'stable'`** | `experimentation` | `:701` |
| **`useNativeViewConfigsInBridgelessMode`** | **`false`** | `true` | **`'canary'`** | `experimentation` | `:903` |

### 3.3 逐项核对实际行为（实测 `ReactNativeFeatureFlagsDefaults.h`）

| flag | Defaults 的返回值 | Stable 档实际值 | 与声明是否一致 |
| --- | --- | --- | --- |
| `enableBridgelessArchitecture` | `true`（`:352` 附近同类写法） | **true**（继承 Defaults） | ✅ 一致 |
| `fuseboxAssertSingleHostState` | `true` | **true** | ✅ 一致 |
| `fuseboxScreenshotCaptureEnabled` | `true` | **true** | ✅ 一致 |
| **`useNativeViewConfigsInBridgelessMode`** | **`false`** | **true**（被 Stable 手写覆写） | ❌ **与 `'canary'` 声明相反** |

**即**：

| 结论 | 说明 |
| --- | --- |
| **3 个 `'stable'` flag 行为正确** | 因为它们的 `defaultValue` 恰好就等于 stable 档应取的值 → **Stable 文件不需要覆写它们** → **手写文件「漏了」它们反而是对的** |
| **1 个 `'canary'` flag 行为与声明相反** | `useNativeViewConfigsInBridgelessMode` 在 OSS Stable 档**已经开启**，而声明说它属于 Canary 档、默认 `false` |

### 3.4 后果：Stable 档比声明更激进

| 档位 | `useNativeViewConfigsInBridgelessMode` 的实际值 | 按声明应为 |
| --- | --- | --- |
| OSS **Stable** | **`true`** | `false`（`'canary'` 档，默认 false） |
| OSS **Canary** | `true` | `true` ✓ |
| OSS **Experimental** | `true` | `true` ✓ |

**开发者视角**：在 OSS Stable 档（`ReactNativeFeatureFlagsOverridesOSSStable`）下，
**`useNativeViewConfigsInBridgelessMode` 已经生效** —— 而按 `config.js` 的声明，
它应该只在 Canary/Experimental 档生效。

### 3.5 且这个 override 在继承链上被写了**两次**

```cpp
// packages/react-native/ReactCommon/react/featureflags/ReactNativeFeatureFlagsOverridesOSSCanary.h:52-54
  bool useNativeViewConfigsInBridgelessMode() override {
    return true;
  }
```

**Stable（手写）与 Canary（生成）各有一份完全相同的 override** ——
**Canary 继承 Stable，所以 Canary 那份永远遮蔽 Stable 那份（值相同，无害）**。

**即：Stable 的手写版本在继承链上是「死代码」** ——
**它唯一的实际作用是把 Stable 档本身的行为改成 `true`。**

### 3.6 最可能的成因（**推测，非断言**）

| 可能 | 依据 | 强度 |
| --- | --- | --- |
| 作者手写 Stable 时想开启该 flag，之后 config 把它改成 `'canary'` 但**没回头改手写文件** | Stable 文件无生成标记 → 无工具会提示同步 | **中** |
| 该 flag 本就该在 Stable 开启，`ossReleaseStage: 'canary'` 是后来加的 | 同上 | **中** |
| 有意为之，但漏了注释 | 手写文件里**零注释**说明为什么 | **弱** |

**本轮无法判定** —— **但可以确定的是：这个偏差不会被任何机制发现**（见 §4）。

### 3.7 GGG-1 / GGG-2 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **平台** | 双端（C++ 层的档位类；JS/Android 侧由生成器产出对应代码） |
| **架构** | 与架构无关 |
| **影响范围** | **仅 OSS 档位**（`ReactNativeFeatureFlagsOverridesOSS*`）；Meta 内部另有 provider 机制 |
| **可观测性** | `useNativeViewConfigsInBridgelessMode` 在 OSS Stable 档生效 |
| **是否确认为缺陷** | **行为与 `config.js` 声明不符是确定的**；**「是否有意」无法判定** |
| **是否可被工具发现** | **否** —— 见 §4 的三重失守 |

## 4. 【核心 GGG-3】三重失守：生成产物的快照门禁从未接上 CI

### 4.1 第一重：`@generated SignedSource<<hash>>` 无任何校验

**实测**：9 个生成文件都带这个标记：

```cpp
// packages/react-native/ReactCommon/react/featureflags/ReactNativeFeatureFlagsOverridesOSSCanary.h:10
 * @generated SignedSource<<c26b8f81fcc99469d0535a89bac18280>>
```

**全仓检索 `SignedSource` 的校验实现**（排除 `node_modules`）：

| 位置 | 用途 |
| --- | --- |
| `scripts/releases/utils/dotslash-utils.js:161` | **发布资产 URL 处理**（`const PATTERN = new RegExp(...)`）—— **与 feature flags 无关** |
| `scripts/releases/utils/__tests__/dotslash-utils-test.js` | 上述的测试 |

**即：没有任何代码把文件内容与 `SignedSource` 里的哈希做比对。**

**后果**：**手改任何一个生成文件，哈希不会变，也没有任何检查会失败。**

### 4.2 第二重：CI 里没有任何 feature flags 任务

**实测**：检索 `.github/` 全目录（38 个 workflow 文件）：

（检索命令：全 `.github/` 目录，模式 `featureflags` / `feature-flags` / `feature_flags` / `FeatureFlags`）

**结果：零命中。**

**对照**：仓库里**确实有**两个同类快照门禁的 workflow：

| workflow | 作用 |
| --- | --- |
| `.github/workflows/validate-cxx-api-snapshots.yml` | 校验 C++ 公开 API 快照（**49 文档记录的单向门禁**） |
| `.github/workflows/validate-dotslash-artifacts.yml` | 校验 dotslash 产物 |

**即：「生成产物的快照校验」这件事在本仓库有成熟范式（两个现成 workflow），唯独 feature flags 没接。**

### 4.3 第三重：工具本身是完备的，只是没被调用

**工具支持 `--verify-unchanged` 模式**：

```javascript
// packages/react-native/scripts/featureflags/index.js:18-20
  } else if (process.argv.includes('--verify-unchanged')) {
    command = 'verify-unchanged';
```

**其实现是完整的逐字节比对**：

```javascript
// packages/react-native/scripts/featureflags/generateFiles.js:57-82
  if (generatorOptions.verifyUnchanged) {
    const existingModules: {[string]: string} = {};
    for (const moduleName of Object.keys(generatedFiles)) {
      const existingModule = fs.readFileSync(moduleName, 'utf8');
      existingModules[moduleName] = existingModule;
    }

    const changedFiles = [];
    for (const moduleName of Object.keys(generatedFiles)) {
      const module = generatedFiles[moduleName];
      const existingModule = existingModules[moduleName];

      if (module !== existingModule) {
        changedFiles.push(moduleName);
      }
    }

    if (changedFiles.length > 0) {
      ...
      throw new Error(
        `Detected changes in generated files for feature flags:\n${changedFilesStr}\n\n` +
          'Please rerun `yarn featureflags --update` and commit the changes.',
      );
```

**即：重新生成 → 逐字节比对 → 有差异就抛错并列出文件。** —— **这是一个完全正确的快照门禁实现**。

| 项 | 判定 |
| --- | --- |
| **门禁实现是否正确** | ✅ **完全正确**（逐字节比对 + 明确报错信息 + 修复指引） |
| **门禁是否接上 CI** | ❌ **没有** |
| **缺口大小** | **一行 workflow 配置** |

### 4.4 与 49 文档 `cxx-api` 单向门禁的对照

| | 49 文档 `cxx-api` 快照门禁 | 本文 feature flags 快照门禁 |
| --- | --- | --- |
| **门禁是否存在** | ✅ 存在（`.github/workflows/validate-cxx-api-snapshots.yml`） | ✅ **实现存在**，❌ **CI 未接** |
| **方向性问题** | **单向**（只拦删除不拦新增） | **无**（逐字节双向比对） |
| **失效原因** | 门禁本身设计如此 | **门禁被实现了却没人调用** |
| **可修复性** | 需改门禁逻辑 | **只需加一个 workflow** |

> **这是「门禁的两个失效方向」的完整枚举**：
> | 方向 | 案例 | 修复成本 |
> | --- | --- | --- |
> | **太紧** | `cxx-api` 单向门禁（拦住了不该拦的） | 改门禁逻辑 |
> | **太松 / 未接** | **本文**（门禁没接 CI） | **加一个 workflow** |
> | **恒惰性** | 62 文档的三档 Guard（`RN_STRICT_API` 全仓未定义） | 需要消费方 opt-in |
> | **不被验证** | 64 文档 DDD-3（`MapBuffer` 的信任假设零文档） | 加断言 |

### 4.5 为什么这个缺口特别值得修：它同时覆盖了三个已记录的发现

| 若接上 CI，则能发现 | 出处 |
| --- | --- |
| **手改生成文件**（`SignedSource` 哈希不会变，但内容比对会失败） | GGG-3 第一重 |
| **`OSSStable.h` 与生成声明脱钩**（若把它加入生成目标列表，生成器会立刻报出冲突） | GGG-1 / GGG-2 |
| **Java/JS 侧生成产物被手改** | 同第一重 |

**且 `OSSStable.h` 的修复成本极低**：把它加入 `generateCommonCxxModules.js` 的目标列表，
生成器会按 `ossReleaseStage: 'stable'` 自动产出那 3 个 flag 的 override，
**手写版本的那 1 个 `'canary'` override 会立刻变成「重复定义」而被暴露**。

## 5. 附带发现：`rewrite_feature_flag_defaults.py` 依赖 Meta 内部工具链


**并依赖 `tree_sitter_cpp`**：


| 项 | 说明 |
| --- | --- |
| `fbpython` | **Meta 内部的 Python 解释器** —— **OSS 用户没有** |
| `tree_sitter_cpp` | 第三方 C++ 解析器（tree-sitter）—— 可安装，但**不是标准依赖** |
| 用途 | 「重写 `ReactNativeFeatureFlagsDefaults.h` 里的默认返回值」—— 即**批量改生成产物的默认值** |
| 失败行为 | 脚本自述：`Fails with a non-zero exit code if any requested flag is not found.` ✓ |

**即：一个用于批量修改生成产物的内部工具，被放在了公开的 `ReactCommon/` 目录里，
但 OSS 用户无法运行它。**

**与 65 文档 EEE-7 的对照**：`REACT_NATIVE_PRODUCTION` 也是「定义了但从不被使用」——
**本仓库存在一类「半公开」的内部机制**：定义在公开目录，但只有内部工具链能用。

## 7. 适用范围声明

| 维度 | GGG-1 / GGG-2 | GGG-3 |
| --- | --- | --- |
| **平台** | 双端（C++ 档位类；JS/Android 侧由生成器产出） | 全平台 |
