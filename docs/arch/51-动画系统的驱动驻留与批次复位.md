# 51 · 动画系统：一个永不清除的 `activeAnimations`、一个缺 `try/finally` 的批次包装，与一个无上界的回调表

> `packages/react-native/Libraries/Animated/nodes/AnimatedValue.js`、
> `packages/react-native/src/private/animated/NativeAnimatedHelper.js`、
> `ReactCommon/react/renderer/animations/LayoutAnimationKeyFrameManager.cpp`
>
> **基线**：react-native @ `9b131e42` · 双端 · **新旧架构共用**
>
> **前置**：[42 文档](./42-Android内存压力与View回收池.md) 记录 Android 内存压力与回收池；

> 「**分配点明确 + 释放点不存在**」的判定标准：
> ① **`dropAnimatedNode` 不停驱动也不清 `activeAnimations`** ——
> 驱动只在 `hasFinished` 时才被移除（`:591-615`），

> 一次抛异常就让 `queueOperations` **永久为 true**；
> ③ **`eventListenerGetValueCallbacks` 是单调无上界的表**。

## 2. 【核心发现 QQ-1】`dropAnimatedNode` 不停驱动，`activeAnimations` 永不清除

### 2.1 三张表，卸载只清两张

```kotlin
// packages/react-native/ReactAndroid/src/main/java/com/facebook/react/animated/NativeAnimatedNodesManager.kt:136-139
  public fun dropAnimatedNode(tag: Int) {
    animatedNodes.remove(tag)
    updatedNodes.remove(tag)
  }
```

**`dropAnimatedNode` 清 2 张表，第三张没动**：

| 表 | 声明 | 类型 | `dropAnimatedNode` 是否清理 |
| --- | --- | --- | --- |
| `animatedNodes` | — | tag → 节点 | ✅ `remove(tag)` |
| `updatedNodes` | — | 待更新队列 | ✅ `remove(tag)` |
| **`activeAnimations`** | **`:52`** | **`SparseArray<AnimationDriver>`** | ❌ **完全未提及** |

```kotlin
// packages/react-native/ReactAndroid/src/main/java/com/facebook/react/animated/NativeAnimatedNodesManager.kt:52
  private val activeAnimations = SparseArray<AnimationDriver>()
```

### 2.2 唯一会移除它的条件是 `hasFinished`

```kotlin
// packages/react-native/ReactAndroid/src/main/java/com/facebook/react/animated/NativeAnimatedNodesManager.kt:588-616
    // Cleanup finished animations. Iterate over the array of animations and override ones that has
    // finished, then resize `mActiveAnimations`.
    if (hasFinishedAnimations) {
      var events: WritableArray? = null
      for (i in activeAnimations.size() - 1 downTo 0) {
        val animation = activeAnimations.valueAt(i)
        if (animation.hasFinished) {
          ...
          activeAnimations.removeAt(i)
        }
      }
```

**`removeAt(i)` 在 `if (animation.hasFinished)` 内 —— 且整个循环还被
`if (hasFinishedAnimations)` 包住。**

> **即移除条件只有一个：动画自己跑完。**
> **没有任何一处会因为「节点被卸载」而移除驱动。**

### 2.3 完整推导：卸载一个仍在跑的动画会发生什么

| 步 | 位置 | 动作 | 后果 |
| --- | --- | --- | --- |
| ① | `:250` | `activeAnimations.put(animationId, animation)` | 驱动入表，**强引用 `animatedValue`** |
| ② | JS 侧卸载组件 | — | View 与 JS 节点都不再被业务引用 |
| ③ | `:136-139` | `dropAnimatedNode(tag)` | `animatedNodes`/`updatedNodes` 清掉 |
| ④ | `:576-579` | 每帧仍 `runAnimationStep(frameTimeNanos)` + `runUpdateNodeList.add(valueNode)` | **驱动仍在每帧执行** |
| ⑤ | `:593` | `if (animation.hasFinished)` | 若动画未跑完，**不移除** |
| ⑥ | 之后每帧 | 重复 ④⑤ | **永久驻留** |

**被强引用的对象**：

```kotlin
// packages/react-native/ReactAndroid/src/main/java/com/facebook/react/animated/NativeAnimatedNodesManager.kt:577
        animation.animatedValue?.let { valueNode -> runUpdateNodeList.add(valueNode) }
```

**`animation.animatedValue` 是 `AnimatedNode?`，`activeAnimations` 强持有 `AnimationDriver`，
`AnimationDriver` 强持有 `animatedValue`** —— **即被卸载的 `AnimatedNode` 及其整条依赖链被强引用住。**

### 2.4 后果的三个维度

| 维度 | 后果 | 是否随时间自行恢复 |
| --- | --- | --- |
| **内存** | 被卸载的 `AnimatedNode` 子树被强引用，**不随 GC 回收** | ❌ **否**（除非动画恰好跑完） |
| **CPU** | 每帧执行一次 `runAnimationStep` + `updateNodes` | ❌ **否** |
| **Choreographer** | `hasActiveAnimations()` 恒为真 → 帧回调持续重挂 | ❌ **否** |

```kotlin
// packages/react-native/ReactAndroid/src/main/java/com/facebook/react/animated/NativeAnimatedNodesManager.kt:88
  public fun hasActiveAnimations(): Boolean = activeAnimations.size() > 0 || updatedNodes.size() > 0
```

**`hasActiveAnimations()` 的两个条件里 `activeAnimations.size() > 0` 会因 QQ-1 长期为真。**

> **这是「帧驱动被永久占用」的完整链条**：
> 内存不释放 → CPU 每帧消耗 → 帧回调永不休眠。
> **三者互为因果，是同一个缺陷的三个面。**
>
> **与 42 文档记录的 `ViewManager` 回收池对照**：
> 那里的回收池**无 size 上限**但 View 会被回收；
> **这里的 `activeAnimations` 连元素都不会被移除**——
> **性质更严重，因为它是「每帧工作」而不只是「占用内存」。**

### 2.5 与 iOS 侧的结构对照

| 维度 | Android | iOS |
| --- | --- | --- |
| 卸载入口 | `NativeAnimatedNodesManager.kt:136-139` | `RCTNativeAnimatedNodesManager.mm:180-187` |
| 是否停驱动 | ❌ | ❌ |
| 驱动容器 | `SparseArray<AnimationDriver>` | 同型 |

> **两端结构同型 —— 即这不是某一端的疏忽，而是共同的设计缺口。**
>
> **能修的方式也同型**：在卸载时遍历 `activeAnimations`，
> 停掉引用该 tag 的驱动并 `removeAt`。

### 2.6 QQ-1 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **平台** | Android 为主；**iOS 结构同型**（`:180-187`） |
| **架构** | 新旧架构共用（`animatedNodes`/`activeAnimations` 不区分 Paper/Fabric） |
| **触发条件** | 组件在**动画未结束时被卸载**（快速滑走列表项、路由跳走、条件渲染移除） |
| **是否可观测** | 表现为「滑动越久越慢」与内存单调上升；**无任何日志或断言** |
| **严重性** | **随时间累积，不自行恢复** |

> **最易触发的场景**：长列表中每一项都有一个循环动画
> （骨架屏 shimmer、呼吸灯），滑过即卸载 ——
> **每次滑动都在 `activeAnimations` 里留下一项永不消失的驱动。**

## 3. 【核心发现 QQ-2】`_executeAsAnimatedBatch` 缺 `try/finally`

### 3.1 批次包装的全文

```javascript
// packages/react-native/Libraries/Animated/nodes/AnimatedValue.js:73-77
function _executeAsAnimatedBatch(id: string, operation: () => void) {
  NativeAnimatedAPI.setWaitingForIdentifier(id);
  operation();
  NativeAnimatedAPI.unsetWaitingForIdentifier(id);
}
```

**7 行，3 条语句，中间没有任何异常处理。**

### 3.2 `setWaitingForIdentifier` 把全局标志置真

```javascript
// packages/react-native/src/private/animated/NativeAnimatedHelper.js:302-308
  setWaitingForIdentifier(id: string): void {
    if (shouldSignalBatch) {
      return;
    }

    waitingForQueuedOperations.add(id);
    queueOperations = true;
```

**`queueOperations` 是模块级 `let`**（`:52`：`let queueOperations = false;`）。

### 3.3 唯一复位它在批次末尾

```javascript
// packages/react-native/src/private/animated/NativeAnimatedHelper.js:341-349
  unsetWaitingForIdentifier(id: string): void {
    if (shouldSignalBatch) {
      return;
    }

    waitingForQueuedOperations.delete(id);
    ...
    queueOperations = false;
```

**复位在 `:349`，只有 `unsetWaitingForIdentifier` 会做。**

### 3.4 后果：一次抛异常即永久排队

| 步 | 事件 | `queueOperations` |
| --- | --- | --- |
| ① | `_executeAsAnimatedBatch(id, op)` 进入 | — |
| ② | `setWaitingForIdentifier(id)` → `:308` | **`true`** |
| ③ | `operation()` **抛出异常** | **`true`（未变）** |
| ④ | `:76` 的 `unsetWaitingForIdentifier` **被跳过** | **永久 `true`** |

**之后的行为**：

```javascript
// packages/react-native/src/private/animated/NativeAnimatedHelper.js:148
        if (queueOperations || queue.length !== 0) {
```

**`queueOperations` 永久为 true → 所有 native 操作不再直发，一律进 `queue` 等待批次结束。**

| 后果 | 说明 |
| --- | --- |
| **动画不再启动** | `queue` 只在批次末尾才 flush，而批次因 `waitingForQueuedOperations` 非空而不结束 |
| **无自愈** | 没有任何 try/catch/finally 会复位该标志 |
| **无日志** | 异常由上层捕获后，标志已脏 |

> **同一缺陷在 `AnimatedColor.js` 重复出现**（`:184` → `:219`）——
> **同一个模式被复制到多个节点类型。**
>
> **这与 49 文档 OO-12 记录的「4 个 format 脚本复制同一段逻辑」同源**：
> **共享的模式被复制，缺陷也被复制。**

### 3.5 QQ-2 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **平台** | 双端（JS 层） |
| **架构** | 新旧架构共用 |
| **触发条件** | `operation()` 抛异常 —— **而抛异常本身不需要是「错误」**，业务代码里任何 throw 都会触发 |
| **是否可观测** | **无**；表现为「某次之后所有原生动画都失效」 |
| **可恢复性** | **需重启 JS 运行时**（或下一次成功走到 `:76` 才复位 —— 但 `:76` 只在无异常时执行） |

> **注意 `:303` 的 `shouldSignalBatch` 早退**：
> 若 `shouldSignalBatch` 为真，`:308` 不会执行，**因此该缺陷只在特定模式下出现** ——
> **这解释了为何该问题难以复现。**

## 4. 【核心发现 QQ-3】`eventListenerGetValueCallbacks` 单调无上界

### 4.1 表的声明

```javascript
// packages/react-native/src/private/animated/NativeAnimatedHelper.js:62-64
const eventListenerGetValueCallbacks: {
  [number]: (value: number) => void,
} = {};
```

**不是 `Map`，是 Flow 标注的对象字面量** —— 键是 number（tag），值是单参回调。

> **一处 `$FlowExpectedError[incompatible-type]` 就在写入点**
> （`:273`），说明**类型标注与实际写入不完全一致**，已被显式压制。

### 4.2 写入点唯一，删除点在事件回调里

| 操作 | 行号 | 触发时机 |
| --- | --- | --- |
| **写入** | `:273` | `eventListenerGetValueCallbacks[tag] = saveValueCallback` |
| **读取** | `:369` | 事件回调内 `const callback = eventListenerGetValueCallbacks[tag]` |
| **删除** | `:376` | **`delete eventListenerGetValueCallbacks[tag]`（在回调执行之后）** |

**删除的 4 行上下文**：

```javascript
// packages/react-native/src/private/animated/NativeAnimatedHelper.js:366-378
    params => {
      const {tag} = params;
      const callback = eventListenerGetValueCallbacks[tag];
      /* $FlowFixMe[constant-condition] Error discovered during Constant
       * Condition roll out. See https://fburl.com/workplace/1v97vimq. */
      if (!callback) {
        return;
      }
      callback(params.value);
      delete eventListenerGetValueCallbacks[tag];
    },
```

**三处早期返回/异常会让删除被跳过**：

| # | 位置 | 条件 | 结果 |
| --- | --- | --- | --- |
| ① | `:371-373` | `if (!callback) return` | 该 tag 无回调（已被删）—— 此时删与不删等价 |
| ② | 事件从不到达 | 原生未发事件 | **条目永不删除** |
| ③ | 原生抛异常 | 见下 | **条目永不删除** |

> **`:369` 与 `:376` 之间隔着一个函数调用 `callback(params.value)`（`:375`）** ——
> **若回调本身抛异常，`:376` 的 `delete` 不会执行**，条目同样留存。

**对应原生侧的行为**：

| 位置 | 行为 |
| --- | --- |
| `animated/NativeAnimatedNodesManager.kt` 的节点查找失败分支 | **抛 `JSApplicationIllegalArgumentException`**（如 `:123-126`、`:166-170`），而非发事件 |

### 4.4 QQ-3 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **平台** | 双端（JS 层） |
| **触发条件** | 原生侧节点已消失（卸载竞态）→ 抛异常 → JS 侧条目不删 |
| **增长形态** | **单调递增**，与「卸载竞态发生次数」成正比 |
| **严重性** | 内存缓慢增长；单条仅一个 number 键 + 一个闭包 |

> **与 QQ-1 的区别**：
> QQ-1 是「一个条目永不消失且每帧工作」（**高 CPU + 内存**）；
> QQ-3 是「条目随竞态次数单调增长」（**仅内存，无 CPU**）。
>
> **两者都缺少上界。**

## 6. 三类缺陷的共同结构

| 缺陷 | 表/标志 | 写入点 | 释放点 | 缺失的形态 |
| --- | --- | --- | --- | --- |
| **QQ-1** | `activeAnimations` | `:250` put | `:286` `removeAt`（`stopAnimationsForNode`）／`:593` `removeAt`（仅 `hasFinished`） | **机制已存在，但 `dropAnimatedNode` 未调用** |
| **QQ-2** | `queueOperations` | `:308` `= true` | `:349` `= false` | **缺 `finally`** |
| **QQ-3** | `eventListenerGetValueCallbacks` | `:273` 赋值 | `:376` `delete`（在 `:375` 调用之后） | **缺「原生异常/回调抛错」路径 + 缺上界** |

> **三者是同一个模式的三次重复**：
> **「有置位点、有复位点，但复位点覆盖不全」**。
>
> | | 复位条件 | 覆盖缺口 |
> | --- | --- | --- |
> | QQ-1 | 动画跑完 **或显式 `stopAnimationsForNode`** | **卸载时两者都不触发** |
> | QQ-2 | 无异常走到末尾 | 抛异常不复位 |
> | QQ-3 | 原生发回事件 | 原生抛异常不复位 |
>
> **三条都是「异常/时序路径未被覆盖」** ——
> **正常路径全对，边界路径全漏。**
>
> **这与 49 文档 OO-1 的成因不同**（那是「恒失效」），
> **但与 46 文档 `dirty()` 的 TODO 同型**（自认的边界条件未处理）。
