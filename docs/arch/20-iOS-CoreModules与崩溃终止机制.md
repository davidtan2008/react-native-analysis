## 2. `reportSoft` 与 `reportFatal` 的对称结构

`CoreModules/RCTExceptionsManager.mm:39-55`（soft）：

```objc
- (void)reportSoft:(NSString *)message
              stack:(NSArray<NSDictionary *> *)stack
        exceptionId:(double)exceptionId
    extraDataAsJSON:(nullable NSString *)extraDataAsJSON
{
  if (RCTRedBoxGetEnabled()) {
    RCTRedBox *redbox = [_moduleRegistry moduleForName:@"RedBox"];
    [redbox showErrorMessage:message withStack:stack errorCookie:(int)exceptionId];
  }

  if (_delegate != nullptr) {
    [_delegate handleSoftJSExceptionWithMessage:message
                                          stack:stack
                                    exceptionId:[NSNumber numberWithDouble:exceptionId]
                                extraDataAsJSON:extraDataAsJSON];
  }
}
```

`reportFatal`（`:57-87`）前 22 行与 soft **完全对称**，然后多出终止逻辑：

```objc
  static NSUInteger reloadRetries = 0;
  if (!RCT_DEBUG && reloadRetries < _maxReloadAttempts) {
    reloadRetries++;
    RCTTriggerReloadCommandListeners(@"JS Crash Reload");
  } else if (!RCT_DEV) {
    NSString *description = [@"Unhandled JS Exception: " stringByAppendingString:message];
    NCDictionary *errorInfo = @{
      NSLocalizedDescriptionKey : description,
      RCTJSStackTraceKey : stack == nil ? (id)kCFNull : stack,
      RCTJSExtraDataKey : extraDataAsJSON == nil ? (id)kCFNull : extraDataAsJSON
    };
    RCTFatal([NSError errorWithDomain:RCTErrorDomain code:0 userInfo:errorInfo]);
  }
```

**两条终止路径**：

| 条件 | 行为 |
| --- | --- |
| `!RCT_DEBUG && reloadRetries < _maxReloadAttempts` | **自动 reload**（最多 N 次） |
| 否则 `!RCT_DEV` | `RCTFatal(...)` → 进程终止 |

注意 `RCT_DEV` 条件下**什么都不做**（Dev 下只弹 RedBox，不终止）——
这是 Dev/Prod 的第三种行为差异。

## 3. `maxReloadAttempts`：iOS 独有的崩溃自动恢复

### 3.1 声明

`RCTExceptionsManager.h:43-44`：

```objc
@property (nonatomic, assign) NSUInteger maxReloadAttempts;
```

### 3.2 全仓库无人设置它

```bash
$ grep -rn "maxReloadAttempts" packages/ --include="*.m" --include="*.mm" | grep -v RCTExceptionsManager
（无输出）
```

**只有声明，没有赋值点。** `NSUInteger` 属性默认值为 0，
因此 `reloadRetries < _maxReloadAttempts` 恒为 `false` → **自动 reload 机制在 OSS 构建中实际不生效**。

> 这与 [08 文档](./08-组件注册表与惰性注册.md) E1-1、
> [16 文档](./16-Android-uimanager与旧架构掏空.md) AIM-1 是同一类问题：
> **机制存在但从未启用**，且无任何警告。

### 3.3 `reloadRetries` 是函数内 static

`:74` 的 `static NSUInteger reloadRetries = 0;` 在**函数内**，
意味着**该计数器在进程生命周期内永不重置**。

即使 `maxReloadAttempts` 被正确设置，App 也**无法重置计数**——
一旦用满，只能通过重启进程。

## 4. `RCTFatal`：iOS 终止进程的实现（04 文档缺失的一环）

`React/Base/RCTAssert.m:122-156`：

```objc
void RCTFatal(NSError *error)
{
  _RCTLogNativeInternal(RCTLogLevelFatal, NULL, 0, @"%@", error.localizedDescription);

  RCTFatalHandler fatalHandler = RCTGetFatalHandler();
  if (fatalHandler) {
    fatalHandler(error);
  } else {
#if DEBUG
    @try {
#endif
      NSString *name = [NSString stringWithFormat:@"%@: %@", RCTFatalExceptionName, error.localizedDescription];

      // Truncate the localized description to 175 characters to avoid wild screen overflows
      NSString *message = RCTFormatError(error.localizedDescription, error.userInfo[RCTJSStackTraceKey], 175);

      // Attach an untruncated copy of the description to the userInfo, in case it is needed
      NSMutableDictionary *userInfo = [error.userInfo mutableCopy];
      [userInfo setObject:RCTFormatError(error.localizedDescription, error.userInfo[RCTJSStackTraceKey], -1)
                   forKey:RCTUntruncatedMessageKey];

      // Expected resulting exception information:
      // name: RCTFatalException: <underlying error description>
      // reason: <underlying error description plus JS stack trace, truncated to 175 characters>
      // userInfo: <underlying error userinfo, plus untruncated description plus JS stack trace>
      @throw [[NSException alloc] initWithName:name reason:message userInfo:userInfo];
#if DEBUG
    } @catch (NSException *) {
    }
#endif
  }
}
```

### 4.1 `#if DEBUG` 造成的两重差异

`@try` / `@catch` 这对指令**只在 DEBUG 下存在**：

| 构建 | 编译结果 | 后果 |
| --- | --- | --- |
| **Debug** | `@try { @throw ... } @catch (NSException *) {}` | **自己抛自己接** —— 进程**不终止**，调用方继续执行 |
| **Release** | 仅 `@throw ...` | 异常**逃逸出函数** → UIKit 主线程默认处理 → 进程终止 |

Debug 下的 `catch` 体是**空的**（`RCTAssert.m:149-150`），
所以「自抛自接」之后**没有任何界面提示** ——
唯一的痕迹是 `RCTAssert.m:124` 那条 `RCTLogLevelFatal` 日志
（它经由 §5 的日志管线走，见 [23 文档 §5](./23-iOS基础工具层ConvertAssertLogUtils.md)）。

> **注意别把它读成「Debug 下会显示全屏错误屏」** —— 那个 `@catch` 什么都不做。
> 真正显示错误界面的是它之前 `RCTFatal` 链路上更早的 RedBox 调用
> （见 [22 文档](./22-iOS崩溃UI层RedBox与LogBox.md)），
> 而那条路径在 Debug 下也会因为 `RCTRedBoxGetEnabled() == YES` 而生效。
> 换言之：**错误界面已经显示过了，`RCTFatal` 的这次抛出只是为了把进程状态标记为「致命」**，
> 而 Debug 下连这一步都被自己吞掉。

`:135` 的注释解释了 175 字符截断的意图：

> Truncate the localized description to 175 characters to avoid wild screen overflows

这个截断只影响 `@throw` 时附在 `reason` 上的**短**副本；
`RCTAssert.m:138-141` 会把**未截断**的原文另存到 `RCTUntruncatedMessageKey`，
两者都挂在同一个 `NSException` 的 `userInfo` 上。

### 4.2 没有任何人注册 fatal handler

~~~bash
$ for s in RCTSetFatalHandler RCTSetFatalExceptionHandler; do
    echo "$s: $(grep -rn "$s" packages/ --include='*.m' --include='*.mm' \
      | grep -v 'RCTAssert\.' | wc -l | tr -d ' ') 处"
  done
RCTSetFatalHandler: 0 处
RCTSetFatalExceptionHandler: 0 处
~~~

两个注册接口（`RCTAssert.m:155, 225`）**全仓库 0 处外部调用**
（含头文件在内也只有定义处本身）。

同样的结论适用于 `RCTSetAssertFunction` / `RCTAddAssertFunction`
（`RCTAssert.m:36, 46`）—— 四个安装函数全部无人调用，
详见 [23 文档 §4.5](./23-iOS基础工具层ConvertAssertLogUtils.md)。

**所以 `RCTFatal` 的终止完全依赖「无人捕获的 `NSException` 由 iOS 运行时终止进程」这一默认行为。**

这与 04 文档的结论**完全一致**（`NSSetUncaughtExceptionHandler`：0 处），
但补上了因果链：

> **04 文档的「RN 不装崩溃处理器」是事实，
> 但它同时意味着：RN 的「主动崩溃」也走的是同一条系统默认路径。
> 框架无法拦截自己的 `RCTFatal`。**

### 4.3 链路的终止控制权在 App 手里

| App 行为 | 结果 |
| --- | --- |
| 调用 `RCTSetFatalHandler(fn)` | `fn` 代替 `@throw` —— **可阻止进程终止** |
| 设置 `maxReloadAttempts > 0` | 前 N 次 fatal 变成自动 reload |
| 什么都不做（默认） | Release 下逃逸 → 进程终止 |

**框架把「要不要崩」的决定权完全交给了 App**，且三个开关都**没有文档化的默认值说明**。

## 5. `reportException`：新链路（TurboModule）

`:105-162` 是 codegen 生成接口 `JS::NativeExceptionsManager` 的实现。

C++ struct → ObjC dict 的转换（`:107-145`）逐字段判空：

```objc
  NSMutableDictionary<NSString *, id> *mutableErrorData = [NSMutableDictionary new];
  mutableErrorData[@"message"] = data.message();
  if (data.originalMessage() != nullptr) {
    mutableErrorData[@"originalMessage"] = data.originalMessage();
  }
  if (data.name() != nullptr) {
    mutableErrorData[@"name"] = data.name();
  }
```

栈帧转换（`:123-137`）保留 `optional` 语义：

```objc
  for (auto frame : data.stack()) {
    NSMutableDictionary<NSString *, id> *frameDict = [NSMutableDictionary new];
    if (frame.column().has_value()) {
      frameDict[@"column"] = @(frame.column().value());
    }
    frameDict[@"file"] = frame.file();
    if (frame.lineNumber().has_value()) {
      frameDict[@"lineNumber"] = @(frame.lineNumber().value());
    }
```

**与 18 文档 §3.2 的 JNI 侧 `ProcessedErrorStackFrameImpl::create` 是同一套语义**：
`std::optional` → 可空对象，区分「无值」与「空值」。

### 5.1 唯一的 App 扩展点

`:148-150`：

```objc
  NCDictionary *errorData = mutableErrorData;
  if ([_delegate respondsToSelector:@selector(decorateJSExceptionData:)]) {
    errorData = [_delegate decorateJSExceptionData:errorData];
  }
```

**`decorateJSExceptionData:` 是 iOS 侧唯一的错误数据定制点** ——
App 可在转成最终上报格式前修改整个 errorData。

对照 Android 侧（18 文档 §3.4）：`ReactInstance.kt:294-305` **没有等价钩子**，
只有 `ExceptionsManagerModule.reportException` 直接 `throw` 或 `FLog`。

> **平台不对称**：
> | 能力 | iOS | Android |
> | --- | --- | --- |
> | 上报前修改 errorData | ✅ `decorateJSExceptionData:` | ❌ 无 |
> | RedBox UI | ✅ | ✅（Release 下为空实现） |
> | 自动 reload | ⚠️ 机制在、默认关闭 | ❌ 无此机制 |

### 5.2 fatal 分发

`:157-161`：

```objc
// packages/react-native/React/CoreModules/RCTExceptionsManager.mm:157-161
  if ([errorData[@"isFatal"] boolValue]) {
    [self reportFatal:message stack:stack exceptionId:exceptionId extraDataAsJSON:extraDataAsJSON];
  } else {
    [self reportSoft:message stack:stack exceptionId:exceptionId extraDataAsJSON:extraDataAsJSON];
  }
```

**新旧两条入口最终汇流到同一对 `reportSoft`/`reportFatal`**
（`reportException` 由 18 文档的 `RCTInstance.mm:636-637` 经 TurboModule 调用）。

## 6. iOS 崩溃链路全貌

```
JS 抛错
  → JsErrorHandler（C++，见 11 文档）
    → onJsError（Android 独有 JNI 回调 / iOS 走 RCTInstance.mm:636）
      → RCTExceptionsManager.reportException  [:105]
        → decorateJSExceptionData:（App 唯一钩子）  [:149]
          ├─ isFatal=false → reportSoft  [:39]  → RedBox（若启用）+ delegate
          └─ isFatal=true  → reportFatal [:57]
                ├─ RCT_DEBUG → 什么都不做（Dev 只弹 RedBox）
                ├─ !RCT_DEBUG && retries < maxReloadAttempts(默认0) → 恒不成立
                └─ !RCT_DEV → RCTFatal  [RCTAssert.m:122]
                      ├─ Debug:   @throw + @catch  → 进程不终止
                      └─ Release: @throw 逃逸       → 进程终止
                            （无 NSSetUncaughtExceptionHandler，靠系统默认行为）
```

## 7. 已发现的问题

| 编号 | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| CM-1 | `maxReloadAttempts` 无任何赋值点，默认 0 → **崩溃自动 reload 机制在 OSS 构建中恒不生效** | `RCTExceptionsManager.h:44`、`.mm:75` | 机制形同虚设；无人知道它默认关闭 |
| CM-2 | `reloadRetries` 是函数内 static，**进程内永不重置** | `CoreModules/RCTExceptionsManager.mm:74` | 即使启用了该机制，App 也无法恢复计数 |
| CM-3 | `RCTFatal` 的 `@throw` 被 `#if DEBUG` 包裹，**Debug 下自抛自接、不终止** | `React/Base/RCTAssert.m:130-152` | 同一段代码在 Dev/Prod 下语义相反，测试无法覆盖 Prod 行为 |
| CM-4 | `RCTSetFatalHandler` / `RCTSetFatalExceptionHandler` 全仓库 0 调用 | `RCTAssert.m:160, 225` | 终止行为完全依赖系统默认；App 若设置 handler 可**静默阻止崩溃** |
| CM-5 | `decorateJSExceptionData:` 是 iOS 独有的上报前钩子，Android 无对等 | `CoreModules/RCTExceptionsManager.mm:148-150` | 跨平台 APM 需分别实现 |
| CM-6 | 三个终止相关开关（`maxReloadAttempts` / `RCTSetFatalHandler` / `RCT_DEV`）组合出 4 种行为，无文档说明 | 综合 | 接入方难以预期崩溃行为 |
| CM-7 | `RCTRedBoxGetEnabled()` 门控 RedBox，但 fatal 路径不受其影响 | `CoreModules/RCTExceptionsManager.mm:44, 62` | 关掉 RedBox 后 fatal 仍会终止进程（符合预期，但易误解） |
