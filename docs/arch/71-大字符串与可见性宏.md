## 2. 【核心 KKK-1】两个 `isAscii()` 恒返回 `true`，而 Android 的主加载路径就走它

### 2.1 三个实现的 `isAscii()`

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:60-70
class JSBigStdString : public JSBigString {
 public:
  JSBigStdString(std::string str, bool isAscii = false) : m_isAscii(isAscii), m_str(std::move(str)) {}

  bool isAscii() const override
  {
    return m_isAscii;
  }
```

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:102-107
  bool isAscii() const override
  {
    return true;
  }
```

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:133-136
  bool isAscii() const override
  {
    return true;
  }
```

| 实现 | 承载内容 | `isAscii()` |
| --- | --- | --- |
| `JSBigStdString` | `std::string` | **由构造参数决定**（默认 `false`）✓ |
| `JSBigBufferString` | `new char[size + 1]` 堆缓冲 | **恒 `true`** ❌ |
| `JSBigFileString` | **mmap 的文件区域** | **恒 `true`** ❌ |

### 2.2 契约是什么

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:37-40
  virtual bool isAscii() const = 0;

  // This needs to be a \0 terminated string
  virtual const char *c_str() const = 0;
```

**`isAscii()` 是 `jsi::Buffer` 的接口**（`jsi::Buffer` 属外部依赖，**不在本仓库**）——
**它的精确契约本轮无法在本仓库内验证**（见 §2.5 的边界声明）。

### 2.3 Android 的主加载路径就走 `JSBigBufferString`

```cpp
// packages/react-native/ReactAndroid/src/main/jni/react/jni/JSLoader.cpp:74-76
      auto buf = std::make_unique<JSBigBufferString>(script->size());
      memcpy(buf->mutableData(), script->c_str(), script->size());
      return buf;
```

**即：Android 上每个非 Hermes-bytecode 的 JS bundle，都被读进 `JSBigBufferString` 并声明为「纯 ASCII」。**

### 2.4 实测：bundle 几乎必然含非 ASCII 字节

**实测**（`packages/react-native/Libraries` 全量扫描）：

| 指标 | 值 |
| --- | --- |
| JS 文件总数 | **459** |
| **含非 ASCII 字节的** | **18** |
| 样例 | `Libraries/Types/CoreEventTypes.js`、`Libraries/Core/ReactNativeVersion.js`、`Libraries/StyleSheet/StyleSheet.js` |

**即：仓库自己的 JS 源码里就有 18 个文件含非 ASCII 字节**（中文注释、字符串字面量等）——
**打包成 bundle 后必然带上这些字节**。

### 2.5 完整的事实链与边界

| # | 事实 | 可验证性 |
| --- | --- | --- |
| ① | `JSBigBufferString::isAscii()` **恒返回 `true`** | ✅ 本仓库可验证 |
| ② | **Android 的 bundle 主加载路径使用它** | ✅ 本仓库可验证 |
| ③ | 仓库的 JS 源码 **18/459 含非 ASCII 字节** | ✅ 实测可验证 |
| ④ | `jsi::Buffer::isAscii()` 的精确契约 | ❌ **外部依赖，不在本仓库** |
| ⑤ | Hermes 侧收到错误 `isAscii` 后的具体行为 | ❌ **外部依赖** |

**因此本文的准确表述是**：

> **C++ 侧对「这个 buffer 只含 ASCII」的断言与实际内容不符 —— 这是一个可验证的事实链的前三段。**
> **第 ④⑤ 段（契约与后果）依赖外部依赖 `jsi` 与 Hermes，本轮无法在本仓库内验证。**
>
> **本轮不断言「会导致字符串损坏」—— 只断言「断言与事实不符，且该断言在本仓库内无法被校验」。**

**这与 64 文档 DDD-3（`MapBuffer` 的信任假设零文档）同型**：
**一个跨越仓库边界的信任假设，既无文档也无机制守护。**

### 2.6 对照：`JSBigStdString` 的做法是正确的

`JSBigStdString` 用**构造参数**决定 `isAscii`，**默认 `false`**（保守）✓
—— **同一族里有一个实现做对了，另两个恒真**。

**即：「这个实现知道有 `isAscii` 这回事」—— 但只在 `std::string` 那一个实现里体现了。**

**唯一正确的那个**：

```cpp
#ifndef RN_EXPORT
#ifdef _MSC_VER
#define RN_EXPORT

```

### 3.2 全部用 `#ifndef` 守卫 → 展开取决于「谁先被 include」

| 情况 | 结果 |
| --- | --- |
| Windows 上，先 include `JSBigString.h` | `RN_EXPORT` 定义为**空** → 后续 9 个头的 `RN_EXPORT` 也是空 → **DLL 导出标记完全消失**（Windows 需要 `__declspec(dllexport)`） |
| Windows 上，先 include 其它 9 个之一 | `RN_EXPORT` = `__attribute__((visibility("default")))` → **MSVC 不支持该语法 → 编译错误** |
| 非 Windows | 无论谁先，展开相同 → **无影响** |

**即：在 Windows 上，两种 include 顺序都会导致问题**（一个编译不过、一个符号不导出）。

### 3.3 根本问题：**10 份重复定义（11 处 `#define`），没有单一真相源**

| 项 | 判定 |
| --- | --- |
| **影响平台** | **仅 Windows**（非 Windows 无影响） |
| **触发条件** | Windows 上编译 legacy 架构的相关目标 |
| **现状** | **未确认** —— RN 的 Windows 支持状态本轮未核实 |
| **修复成本** | **极低** —— 抽一个 `react/utils/RNExport.h` 作为唯一来源 |

> **这是「重复代码导致的不一致」的典型**：9 份拷贝里只有 1 份被更新过。
>
> **与 67 文档 GGG-1（`OSSStable.h` 手写 vs 生成）同型**：
> **「同一份定义被复制了 N 份，其中一份与其它不同」。**

## 4. 【核心 KKK-3】`JSBigString` 的注释说「move-only」，实现却不可移动

### 4.1 注释原文

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:26-32
// JSExecutor functions sometimes take large strings, on the order of
// megabytes.  Copying these can be expensive.  Introducing a
// move-only, non-CopyConstructible type will let the compiler ensure
// that no copies occur.  folly::MoveWrapper should be used when a
// large string needs to be curried into a std::function<>, which must
// by CopyConstructible.
```

### 4.2 实现

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:42-48
  // Not copyable or movable
  JSBigString(const JSBigString &) = delete;
  JSBigString &operator=(const JSBigString &) = delete;
  JSBigString(JSBigString &&) = delete;
  JSBigString &operator=(JSBigString &&) = delete;
```

### 4.3 矛盾点

| 项 | 注释 | 实现 |
| --- | --- | --- |
| 不可拷贝 | ✅ 明确 | ✅ 两个 delete |
| **可移动** | ✅ **「move-only」** | ❌ **移动构造与移动赋值都被 delete** |
| **类型自述** | `// Not copyable or movable` | 与代码一致 ✓ |

**即：注释说「引入一个 move-only 类型」，实现却是一个 **non-movable** 类型** ——
**注释描述的能力（可移动）不存在**。

**与 59 文档 YY-3（注释锚点失效）的对照**：
| | 59 文档 | 本文 |
| --- | --- | --- |
| 形态 | 引用的函数改名了 | **引用的能力从未实现** |
| 读者后果 | 找不到函数 | **以为可以移动** |
| **正确修法** | 改注释 | **改注释**（因为 non-movable 才是设计意图 —— 注释里的 `// Not copyable or movable` 已经说对了） |

**即：同一文件内两处注释互相矛盾**，而**代码旁的注释是对的**。

### 4.4 顺带：`JSBigBufferString` 的 `new char[size + 1]` 溢出

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:90-97
class RN_EXPORT JSBigBufferString : public JSBigString {
 public:
  JSBigBufferString(size_t size) : m_data(new char[size + 1]), m_size(size)
  {
    // Guarantee nul-termination.  The caller is responsible for
    // filling in the rest of m_data.
    m_data[m_size] = '\0';
  }
```

| 项 | 说明 |
| --- | --- |
| `size + 1` | 若 `size == SIZE_MAX` → **回绕为 0** → `new char[0]` 分配 0 字节 → 随后 `m_data[m_size] = '\0'` 是 **SIZE_MAX 偏移的越界写** → **堆破坏** |
| 实际可达性 | `size` 来自 `script->size()`（Android 的 bundle 大小）—— **不可能是 `SIZE_MAX`** |
| **是否有校验** | **无** |

**即：这是一个「理论上不可达、但无防御」的边界** —— 属**结构脆弱**（62 文档 DDD-3 同类）。

## 5. 附带发现：`RecoverableError` 丢失原异常类型、第二个弃用转发头

### 5.1 `runRethrowingAsRecoverable` 丢失原类型

```cpp
// packages/react-native/ReactCommon/cxxreact/RecoverableError.h:32-43
  template <typename E>
  inline static void runRethrowingAsRecoverable(std::function<void()> act)
  {
    try {
      act();
    } catch (const E &err) {
      throw RecoverableError(err.what());
    }
  }
```

| 项 | 说明 |
| --- | --- |
| **原异常类型 `E` 被丢弃** | 只保留 `err.what()` 的**文本** → **调用方无法按类型区分处理**，只能字符串匹配 |
| **异常链丢失** | 新的 `RecoverableError` **不持有原异常**（无 `std::exception_ptr`）→ **原始堆栈丢失** |
| **`std::function<void()> act` 按值传递** | 每次调用都要构造一个 `std::function`（可能堆分配）—— **在异常路径上** |
| **`m_what` 前缀拼接** | `"facebook::react::Recoverable: " + what_` → 每次构造多一次字符串分配 |

**与 41 文档（Android 崩溃与错误路径）的对照**：
**41 文档记录了「extraData 在 fatal 时可能为空」** —— **本文记录了「异常链在转换时丢失」** ——
**两者都是「错误信息在传递过程中被削减」**。

### 5.2 `ErrorUtils.h` 是**第二个**带 `#warning` 的弃用转发头

```cpp
// packages/react-native/ReactCommon/cxxreact/ErrorUtils.h:9-13
```

### 5.3 正向：`JSBigFileString::fromPath` 的错误处理是干净的

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.cpp:89-115
std::unique_ptr<const JSBigFileString> JSBigFileString::fromPath(
    const std::string& sourceURL) {
  int fd = folly::fileops::open(sourceURL.c_str(), O_RDONLY);

  if (fd == -1) {
    const std::string message =
        std::string("JSBigFileString::fromPath - Could not open file: ") +
        sourceURL;
    LOG(ERROR) << message;
    throw std::runtime_error(message.c_str());
  }

  struct stat fileInfo{};
  int res = ::fstat(fd, &fileInfo);

  if (res == -1) {
    const std::string message =
        "JSBigFileString::fromPath - fstat on bundle failed: " + sourceURL;
    LOG(ERROR) << message;
    folly::fileops::close(fd);
    throw std::runtime_error(message.c_str());
  }

  auto ptr = std::make_unique<const JSBigFileString>(fd, fileInfo.st_size);
  CHECK(folly::fileops::close(fd) == 0);
  return ptr;
}
```

| 特征 | 评价 |
| --- | --- |
| **`fstat` 失败时先 `close(fd)` 再抛** | ✓ **无 fd 泄漏** |
| **两条错误路径都 `LOG(ERROR)` + 抛异常** | ✓ 有可观测性 |
| **正常路径 `CHECK(close(fd) == 0)`** | ✓ |

**且头文件的注释把「调用方必须 catch」的责任写清楚了**：

```cpp
// packages/react-native/ReactCommon/cxxreact/JSBigString.h:145-149
  // Throws std::runtime_error when the file at sourceURL cannot be opened or
  // read (e.g. it is missing). Callers that load files which may legitimately
  // be gone at load time (such as an OS-purgeable / LRU-evictable cache) must
  // catch this and degrade gracefully rather than let it surface as an
  // unhandled exception.
```

**这是第一档注释** —— **说明了「抛什么异常」「谁该 catch」「不 catch 会怎样」**。
