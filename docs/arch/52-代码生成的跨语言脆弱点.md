## 2. 【核心发现 RR-1】同一个结构体，两种初始化方式

### 2.1 结构体的声明（只有两个字段）

```cpp
// packages/react-native/ReactCommon/react/nativemodule/core/ReactCommon/TurboModule.h:84-88
  struct MethodMetadata {
    size_t argCount;
    jsi::Value (*invoker)(jsi::Runtime &rt, TurboModule &turboModule, const jsi::Value *args, size_t count);
  };
  std::unordered_map<std::string, MethodMetadata> methodMap_;
```

**2 个字段：`argCount`（`size_t`）+ `invoker`（函数指针）。**

### 2.2 安全的写法：C++ spec 路径用指定初始化器

```javascript
// packages/react-native-codegen/src/generators/modules/GenerateModuleH.js:185-188
${methods
  .map(({methodName, paramCount}) => {
    return `    methodMap_["${methodName}"] = MethodMetadata {.argCount = ${paramCount}, .invoker = __${methodName}};`;
  })
```

**生成结果是**：

```cpp
methodMap_["foo"] = MethodMetadata {.argCount = 2, .invoker = __foo};
```

**指定初始化器（C++20 designated initializer）按字段名赋值** ——
**字段顺序变化不会影响语义。**

### 2.3 危险的写法：C++/JNI 路径用位置聚合初始化

```javascript
// packages/react-native-codegen/src/generators/modules/GenerateModuleObjCpp/source/serializeModule.js:142
        methodMap_["${methodName}"] = MethodMetadata {${argCount}, __hostFunction_${hasteModuleName}SpecJSI_${methodName}};
```

```javascript
// packages/react-native-codegen/src/generators/modules/GenerateModuleJniCpp.js:79
    return `  methodMap_["${propertyName}"] = MethodMetadata {${argCount}, __hostFunction_${hasteModuleName}SpecJSI_${propertyName}};`;
```

**两处生成的都是 `MethodMetadata {argCount, fn}` —— 纯位置。**

**生成结果的实测形态**（取自已提交的 Jest 快照）：

```
        methodMap_["getArrayBuffer"] = MethodMetadata {0, __hostFunction_NativeSampleTurboModuleSpecJSI_getArrayBuffer};
        methodMap_["voidArrayBuffer"] = MethodMetadata {1, __hostFunction_NativeSampleTurboModuleSpecJSI_voidArrayBuffer};
```

### 2.4 后果：字段重排即静默语义颠倒

| 若有人调整 `packages/react-native/ReactCommon/react/nativemodule/core/ReactCommon/TurboModule.h:85-86` 的字段顺序 | 位置初始化的结果 | 指定初始化的结果 |
| --- | --- | --- |
| 不动 | ✅ 正确 | ✅ 正确 |
| **调换两行** | ❌ **`argCount` 被赋成函数地址，函数被赋成整数** | ✅ **仍然正确** |
| **在中间插入新字段** | ❌ **全部后续错位** | ✅ **仍然正确** |

**且这不会导致编译错误**：

| 项 | 后果 |
| --- | --- |
| 类型 | `argCount` 是 `size_t`，函数指针转 `size_t` 通常仍可编译（需显式 cast，但生成器可以加） |
| 编译器警告 | 聚合初始化的顺序不匹配在部分编译器下有 `-Wmissing-field-initializers` 之类提示，但**不保证** |
| 运行时 | 生成的代码把一个巨大的整数当 argCount 用，一个整数当函数指针调用 → **未定义行为** |

> **这是「同一份生成器里两种风格并存」的典型** ——
> `GenerateModuleH.js:187` 的作者知道正确写法，
> 但 `serializeModule.js:142` 与 `GenerateModuleJniCpp.js:79` 没有沿用。
>
> **与 49 文档 OO-12（`MAX_HEADER_BYTES` 在 4 个文件各复制一份）同源**：
> **同一逻辑被复制到多个文件，改进只落在其中一个。**

### 2.5 RR-1 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **语言** | C++ / JSI（Android 与 iOS 的 JSI 路径共用） |
| **受影响生成器** | `GenerateModuleObjCpp`、`GenerateModuleJniCpp` |
| **不受影响** | `GenerateModuleH`（C++ spec 路径，用指定初始化器） |

## 3. 【核心发现 RR-2】`javaPackageName` 在 JS 生成器侧未接线

### 3.1 组件侧的硬编码与显式 TODO

```javascript
// packages/react-native-codegen/src/generators/components/GeneratePropsJavaInterface.js:243-244
    // TODO: This doesn't support custom package name yet.
    const normalizedPackageName = 'com.facebook.react.viewmanagers';
```

**注释直说「还不支持自定义包名」，代码硬编码为 `com.facebook.react.viewmanagers`。**

**同一文件 `:51` 处实际使用该常量**：生成的 Java 文件首行为
`package ${packageName};` —— 即**直接插入该硬编码常量**。

### 3.2 配置键在全仓库的读取点

| 位置 | 读取方式 | 侧 |
| --- | --- | --- |
| `packages/react-native/scripts/generate-specs-cli.js:36` | `alias: 'javaPackageName'` | **CLI 参数** |
| `packages/react-native/scripts/generate-specs-cli.js:62` | `argv.javaPackageName` | **CLI 参数** |
| `packages/gradle-plugin/.../GenerateCodegenArtifactsTaskTest.kt:91`、`:129`、`:146` | `--javaPackageName` | **仅测试** |

> **初稿称「Kotlin/Gradle 侧只出现在测试文件」—— 这是错的，已修正。**
>
> **实测 5 个文件**，其中 **3 个是生产代码**：
>
> | 文件 | 性质 |
> | --- | --- |
> | `packages/gradle-plugin/react-native-gradle-plugin/src/main/kotlin/com/facebook/react/tasks/GenerateCodegenArtifactsTask.kt` | **生产** |
> | `packages/gradle-plugin/react-native-gradle-plugin/src/main/kotlin/com/facebook/react/ReactPlugin.kt` | **生产** |
> | `packages/gradle-plugin/shared/src/main/kotlin/com/facebook/react/model/ModelCodegenConfigAndroid.kt` | **生产**（模型定义） |
> | `packages/gradle-plugin/react-native-gradle-plugin/src/test/kotlin/com/facebook/react/tasks/GenerateCodegenArtifactsTaskTest.kt` | 测试 |
> | `packages/gradle-plugin/shared/src/test/kotlin/com/facebook/react/utils/JsonUtilsTest.kt` | 测试 |
>
> **即 Gradle 侧完整实现了「读配置 → 传 `--javaPackageName` 参数」这条链，
> 但 JS 生成器不消费它** —— **断点在「CLI 参数 → 生成器」这一段。**
>
> **这让 RR-2 的定位更精确**：不是「没人实现」，而是
> **「两侧都实现了，中间那一跳没人接」。**

### 3.3 与之并存的硬编码

| 目标 | 值 | 位置 |
| --- | --- | --- |
| 组件 Java 接口包名 | **`com.facebook.react.viewmanagers`** | `GeneratePropsJavaInterface.js:244` |
| TurboModule JNI 的 Java 包 | **`com.facebook.fbreact.specs`** | 见 §3.4 |

### 3.4 后果

| 项 | 后果 |
| --- | --- |
| **第三方库自定义包名** | **无法生效** —— 生成的 Java 类会落在 RN 的固定包名下 |
| **包名冲突** | 多个第三方库的生成类落在**同一个包**里 |
| **是否致命** | **不致命**（能编译能运行），但**第三方库无法隔离命名空间** |
| **Gradle 侧** | **已完整实现**（`GenerateCodegenArtifactsTask.kt`、`ReactPlugin.kt`、`ModelCodegenConfigAndroid.kt` 三个生产文件） |

> **这条不是「隐藏缺陷」，而是「已声明的技术债」** ——
> `// TODO: This doesn't support custom package name yet.` **明确写在代码里**。
>
> **按 46 文档建立的三类划分，它属于「历史承诺」**：
> 文档/配置声明了能力（`javaPackageName`），
> 实现明确不做（硬编码 + TODO）。
>
> **对比 44 文档的 `devLoadingViewManager`**：
> 那是「配置项存在但在新架构路径下不生效」；
> **这里是「配置项存在但生成器根本不用」** —— 层级更靠前（生成期而非运行期）。

## 4. 【核心发现 RR-3】同名 spec 的静默覆盖

### 4.1 合并只有三行

```javascript
// packages/react-native-codegen/src/cli/combine/combine-js-to-schema.js:42-48
        const schema = parser.parseFile(filename);

        if (schema && schema.modules) {
          merged.modules = {...merged.modules, ...schema.modules};
        }
      }
      return merged;
    },
```

**`{...merged.modules, ...schema.modules}` —— 对象展开，后来的覆盖先来的。**

**三个后果中的前两个是确定的**：

| # | 后果 | 是否静默 |
| --- | --- | --- |
| ① | **两个 spec 声明同名 module → 后解析的那个覆盖前一个** | ✅ **完全静默，无任何日志** |
| ② | **后解析的 module 少一个方法 → 该方法从生成产物中消失** | ✅ **静默** |
| ③ | 若两者都在 `codeGenComponents` 中声明同名 component → 应有校验 | 见 §4.2 |

### 4.2 校验只在 component 层

| 校验对象 | 位置 | 状态 |
| --- | --- | --- |
| **component 名重复** | `packages/react-native-codegen/src/SchemaValidator.js` | ✅ **有校验** |
| **module 名重复** | — | ❌ **无**（走 §4.1 的静默覆盖） |
| iOS `codegenConfig` 注解重复 | `utils.js` 的 `parseiOSAnnotations` | ✅ 有校验 |

> **即：重复检测存在，但只覆盖 component 与 iOS 注解两条路径，
> TurboModule 的 module 名不在其中。**
>
> **结合 49 文档 OO-3 的经验**：
> 这里的门禁是**半覆盖**的 —— 不是没有检查，而是检查范围与出问题的地方不重合。

### 4.3 RR-3 的适用范围声明

| 维度 | 条件 |
| --- | --- |
| **触发条件** | 两个 `.js` spec 文件声明了**同名 module** |
| **发生概率** | 低 —— 需两个库用同一 module 名（常见于 fork 或模板复制） |
| **后果严重性** | **高** —— 生成产物少方法，且**运行时才发现** |
| **是否有日志** | **无** |
