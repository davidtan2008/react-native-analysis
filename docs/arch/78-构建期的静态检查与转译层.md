## 2. 【核心 LNT-1】同一份规则集在两种配置格式下作用于不同的文件集合

### 2.1 eslintrc 格式：四个 override 全用 `*.js`

```js
// packages/eslint-config-react-native/index.js:33-53
  overrides: [
    {
      ...sharedConfig.overrides.flow,
      files: ['*.js'],
      parser: '@babel/eslint-parser',
      plugins: ['ft-flow'],
    },
    {
      files: ['*.jsx'],
      parser: '@babel/eslint-parser',
    },
    {
      ...sharedConfig.overrides.reactNative,
      files: ['*.js', '*.jsx', '*.ts', '*.tsx'],
    },
    {
      ...sharedConfig.overrides.typescript,
      files: ['*.ts', '*.tsx'],
      parser: '@typescript-eslint/parser',
      plugins: ['@typescript-eslint/eslint-plugin'],
    },
```

### 2.2 flat 格式：同样的 override 全用 `**/*.js`

```js
// packages/eslint-config-react-native/flat.js:58-99
  // JavaScript files with Babel parser and Flow
  {
    ...sharedConfig.overrides.flow,
    files: ['**/*.js'],
    languageOptions: {
      parser: babelParser,
    },
    plugins: {
      'ft-flow': ftFlowPlugin,
    },
  },

  // JSX files with Babel parser
  {
    files: ['**/*.jsx'],
    languageOptions: {
      parser: babelParser,
    },
  },

  // All JS/TS files - React Native specific rules
  {
    ...sharedConfig.overrides.reactNative,
    files: ['**/*.js', '**/*.jsx', '**/*.ts', '**/*.tsx'],
  },
```

### 2.3 覆盖范围的差距

**「可验证的事实」**：`index.js` 的**前四个** override（`flow` / `jsx` / `reactNative` / `typescript`，分别在 `:36`、`:41`、`:46`、`:50`）用 `*.js` / `*.jsx` / `*.ts` / `*.tsx`（**四处，无一个 `**/`**）；`flat.js` 的对应 override 全用 `**/*.js` 形式。

**（第五个 override 是 jest 的，`:56` 的 `files` 里用了 `**/__{mocks,tests}__/**` —— 也就是说**同一个文件里两种 glob 宽度并存**，只有前四个是窄的。）**

**「可验证的推论」**：在 eslintrc 的 glob 语义下 `*` **不跨越 `/`**，而 `**` 跨越任意层级目录 → 同一份 `shared.js` 的 `overrides` 在两种格式下**覆盖的文件集合相差一个数量级**。

### 2.4 被放大的一处：仓库根自己的配置也混用两种

```js
// .eslintrc.js:23-24
    {
      files: ['*.js', '*.js.flow', '*.jsx'],
      parser: 'flow-eslint',
```

```js
// .eslintrc.js:66
      files: ['flow-typed/**/*.js', 'packages/react-native/flow/**/*'],
```

```js
// .eslintrc.js:113
      files: ['**/__tests__/**/*-test.js'],
```

**同一个文件里，`*.js`（只到顶层）与 `**/__tests__/**`（任意层级）并存** → 读者无法从写法上判断某个 override 到底管多宽。

### 2.5 影响最大的一条规则

`shared.js` 里 RN 自有的规则只有一条：

```js
// packages/eslint-config-react-native/shared.js:34-38
    reactNative: {
      rules: {
        '@react-native/no-deep-imports': 1,
      },
    },
```

**它挂在 `overrides.reactNative` 上** → 而 `overrides.reactNative` 恰好是 `index.js:44-49` 那个 `files: ['*.js', '*.jsx', '*.ts', '*.tsx']` 的 override → **在 eslintrc 格式下，这条规则的作用范围与其它三个 override 一样窄**。

**「无法验证」**：ESLint 对「被 extend 的 shareable config 里的相对 `files` 模式以谁为基准」的解析细节 —— 本轮未安装依赖，**本文不断言该规则在 RN 仓库内实际覆盖了多少文件**。

**判定：结构脆弱（两种配置格式共用一份 `shared.js`，却需要两套不同宽度的 glob；差异没有任何注释说明）。**

## 3. 【核心 LNT-2】`shared.js` 有一处配置文本损坏

### 3.1 损坏的那一行

```js
// packages/eslint-config-react-native/shared.js:173
    'no-warning-comments': 0, // disallow usage of configurable warning terms in comments": 1,                        // e.g. TODO or FIXME (off by default)
```

**`: 1,` 这一段被吞进了行尾注释里**，注释文本中还多出一个孤立的 `"`。

**语法上完全合法**（就是一条注释），所以 ESLint 不会报错 —— **但它意味着某个配置项从未生效**。

### 3.2 从残留文本可以推断原本的样子

两段注释分属**两条不同的规则**：

| 片段 | 归属 |
| --- | --- |
| `// disallow usage of configurable warning terms in comments` | ESLint 内置 `no-warning-comments` 的标准描述 |
| `// e.g. TODO or FIXME (off by default)` | 同一规则的另一处标准描述（该规则的 `terms` 选项默认是 `todo` / `fixme`） |

**两段描述同时出现，说明原文件里曾有两条相邻的规则项** —— 一条被合并时丢了换行。

### 3.3 后果

`no-warning-comments` 实际生效的级别是 **`0`（关闭）**；被吞掉的那条（推测级别为 `1`）**从未配置**。

**判定：缺陷（配置文本损坏，一条规则静默失效）。** 与 49 文档 OO-2（format 包装器缺工具链时 `console.warn` + `return`）同属「**配置层静默降级**」形态，但这里更隐蔽：**语法合法、无任何报错**。

## 5. LNT-4 `globals` 的 legacy 布尔形式是刻意的（正面）

### 5.1 `shared.js` 的写法与注释

```js
// packages/eslint-config-react-native/shared.js:61-63
  // Map from global var to bool specifying if it can be redefined
  globals: {
    __DEV__: true,
```

### 5.2 `flat.js` 显式转换

```js
// packages/eslint-config-react-native/flat.js:24-31
// Convert globals from legacy format (true/false) to flat config format ('readonly'/'writable')
const convertGlobals = globals => {
  const converted = {};
  for (const [key, value] of Object.entries(globals)) {
    converted[key] = value ? 'writable' : 'readonly';
  }
  return converted;
};
```

**注释与实现完全对得上**：布尔 `true` → 可写、`false` → 只读。

**判定：正面** —— 这是**刻意的双格式兼容**，不是遗留问题。`__DEV__: true` 意味着 `__DEV__` 在两种格式下都可写，语义一致。

## 7. 【核心 LNT-6】ESLint 规则与 Babel 插件的 deep-import 判定不一致

### 7.1 两处判定逻辑

**ESLint 侧**（豁免了 4 个二级入口 + 内部目录）：

```js
// packages/eslint-plugin-react-native/no-deep-imports.js:197-216
    function isSecondaryEntryPoint(source) {
      if (source.type !== 'Literal' || typeof source.value !== 'string') {
        return false;
      }

      return (
        source.value === 'react-native/asset-registry' ||
        source.value === 'react-native/react-private-interface' ||
        source.value === 'react-native/setup-env' ||
        source.value === 'react-native/unstable-internals-do-not-use'
      );
    }

    function isFbInternalImport(source) {
      if (source.type !== 'Literal' || typeof source.value !== 'string') {
        return false;
      }

      return source.value.startsWith('react-native/src/fb_internal/');
    }
```

**Babel 侧**（一个都不豁免）：

```js
// packages/react-native-babel-preset/src/plugin-warn-on-deep-imports.js:36-39
function isDeepReactNativeImport(source) {
  const parts = source.split('/');
  return parts.length > 1 && parts[0] === 'react-native';
}
```

### 7.2 后果

| 导入路径 | ESLint | Babel（dev） |
| --- | --- | --- |
| `react-native/asset-registry` | **豁免** ✓ | **警告** ✗ |
| `react-native/setup-env` | **豁免** ✓ | **警告** ✗ |
| `react-native/src/fb_internal/...` | **豁免** ✓ | **警告** ✗ |

**同一个导入，静态检查放行、构建期却打出警告** —— 而 `react-native` 包的 `exports` 明确放行了其中四个：

```json
// packages/react-native/package.json
    "./asset-registry": { "types": null, "default": "./src/asset-registry.js" },
    "./react-private-interface": { "types": null, "default": "./src/react-private-interface.js" },
    "./setup-env": "./src/setup-env.js",
    "./unstable-internals-do-not-use": { ... },
```

**判定：缺陷（双实现漂移）** —— 与 73 文档 MMM-3 记录的「同一份消息的三份实现」同型；这里同一个判定被写了两遍，**且两遍不同**。

### 7.3 更广的一层：exports 放行的路径远多于两份判定

`react-native` 的 `exports` 还放行了 `"./Libraries/*"`、`"./scripts/*"` 等 —— 而 **ESLint 的 `isDeepReactNativeImport` 会把 `react-native/Libraries/...` 判为 deep import**（`parts.length > 1 && parts[0] === 'react-native'`）。

**→ 一个被包 `exports` 明确允许的导入，会被 ESLint 报为 deep import**，修复靠 `publicAPIMapping` 里是否有对应条目（否则只报错、不给 fix）。

**判定：ESLint 的豁免清单与包的 `exports` 契约是两套独立维护的清单**（实测：ESLint 豁免 4 条，`exports` 放行 10 余条）。

## 9. LNT-8 `DynamicColorIOS` 的多个错误报在同一位置

```js
// packages/eslint-plugin-react-native/platform-colors.js:80-94
          const properties = args[0].properties;
          properties.forEach(property => {
            if (!(
              property.type === 'Property' &&
```

## 10. LNT-9 一处 messageId 文案的语病

```js
// packages/eslint-plugin-react-native/platform-colors.js:18-27
    messages: {
      platformColorArgsLength:
        'PlatformColor() must have at least one argument that is a literal.',
      platformColorArgTypes:
        'PlatformColor() every argument must be a literal.',

      dynamicColorIOSValue:
        'DynamicColorIOS() value must be either a literal or a PlatformColor() call.',
```

## 12. LNT-11 `prepack` / `postpack` 的精确字符串替换会静默失败


**判定：缺陷（替换无成功校验、失败无声）。** 正确做法是替换后**断言结果确实变了**，否则报错退出。

### 12.3 附带的正面：两份脚本对称

`prepack` 置真、`postpack` 置回假 → **成对出现**，不会单向漂移。
