## 2. 线程模型

RN 至少涉及以下线程，跨线程调用统一通过 `CallInvoker` / `RuntimeExecutor`：

| 线程 | 职责 | 关键载体 |
| --- | --- | --- |
| **JS 线程** | 唯一的 JS 执行线程；事件循环；React 渲染 | `jsi::Runtime`、`MessageQueueThread`、`RuntimeScheduler` |
| **主线程 / UI 线程** | iOS MainThread / Android UI Thread；挂载原生视图、跑动画、跑 layout/diff 事务 | `UIManager`、`MountingCoordinator::pullTransaction`；Android 侧 `MountItemDispatcher` 标注 `@UiThread @ThreadConfined(UI)`（`MountItemDispatcher.kt:121-123`） |
| **后台加载线程** | **两端都有，机制不同**：Android 用专用单线程创建实例、加载 bundle、启停 surface（`bgExecutor`，`ReactHostImpl.kt:102`）；iOS 把大 bundle 读取 dispatch 到全局并发队列（`RCTJavaScriptLoader.mm:246-247`） | 见左 |
| **Native Modules 线程**（旧架构） | 执行原生模块的异步方法 | `NativeModulesQueueThread` |
| **GC 线程** | Hermes GC；受 `allocInOldGenBeforeTTI` 等参数影响 | `HermesInstance.cpp:53-66` |

JS → 原生的同步调用必须走 `CallInvoker`（`ReactCommon/callinvoker/ReactCommon/CallInvoker.h`、`react/runtime/CallInvokerImpl.cpp`）。`ReactInstance.h:46-56` 注释说明：`enableBufferedCallInvoker` 打开时异步调用会与 `callFunctionOnModule` 一起排队，保证不会在主 bundle 求值完成前执行。

> **关于「Shadow 队列」—— 平台差异明显，不要一概而论**：
>
> | 平台 | 状态 | 证据 |
> | --- | --- | --- |
> | **Android** | **不存在** | 全仓库搜索 `ShadowQueueThread` 为 0 命中；Fabric 挂载统一在 UI 线程：`MountingManager.MountItemExecutor`（`MountingManager.kt:53`）→ `FabricUIManager` 的实现（`FabricUIManager.java:232-240`）→ `MountItemDispatcher.dispatchMountItems()`，后者标注 `@UiThread @ThreadConfined(UI)`（`MountItemDispatcher.kt:121-123`）；`SurfaceMountingManager` 同样密集标注 `@UiThread` / `@ThreadConfined(ThreadConfined.UI)`（`:101, 111, 118, 202-203, 208-209, 296`） |
> | **iOS** | **仍然存在** | `RCTUIManagerUtils.m:14-33` 定义串行队列 `com.facebook.react.ShadowQueue`（QoS `USER_INTERACTIVE`），由 `RCTGetUIManagerQueue()` 创建、`RCTIsUIManagerQueue()` / `RCTExecuteOnUIManagerQueue()` 使用。**注意命名有历史遗留**：队列名仍叫 `ShadowQueue`，但语义是旧架构 UIManager 队列 |
> | **C++ 挂载/调度层** | **无自建线程** | `renderer/mounting/`、`renderer/scheduler/` 中 `std::thread` / `pthread_create` / `TaskThread` 均 0 命中 |
>
> 关键区别：iOS 的 ShadowQueue 属于**旧架构（Paper / bridge）的 UIManager 队列**，与 Fabric 挂载无关。Fabric 在 iOS 上同样在主线程挂载（`RCTMountingManager.mm:234-250` 的 `initiateTransaction:` 入口带 `RCTAssertMainQueue()`）。

## 5. 事件循环

`ReactCommon/react/renderer/runtimescheduler/__docs__/README.md` 是官方说明，要点：

一个 tick 四步（`:110-116`）：

1. **Select a task** —— `RuntimeScheduler` 按优先级 + 过期时间选任务
2. **Execute the task**
3. **Execute all microtasks**
4. **Update the rendering** —— Event Timing 分发 → ResizeObserver → IntersectionObserver → 排空 `pendingRenderingUpdates_`

核心语义是**任务内 UI 更新的原子性**：一个 task 里触发的所有 UI 变更（React state 更新、view command）会一次性 flush，UI 永远不会看到「半个 task」的结果。

对应源码：
- `RuntimeScheduler_Modern.cpp:277-344` `runEventLoop` / `runEventLoopTick`
- `:411` `executeTask`（带 `id` / `priority` / `didUserCallbackTimeout` 参数的 TraceSection）
- `:449` `performMicrotaskCheckpoint`
- `:456-479` microtask 排空有硬上限 `kRetriesBound = 255`，超了 `throw std::runtime_error("Hits microtasks retries bound.")`

优先级与超时（`SchedulerPriorityUtils.h:43-60`）：

```cpp
ImmediatePriority     → 0ms
UserBlockingPriority  → 250ms
NormalPriority        → 5s
LowPriority           → 10s
IdlePriority          → 5min
```

**注意**：这些超时是「用户回调饥饿保护」，**不是**首帧渲染超时保护（见 `05` 白屏章节）。
