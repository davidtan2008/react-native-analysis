## 2. 【核心发现 OO-1】ESLint 在 CI 里无法失败

### 2.1 包装脚本全文（16 行）

```bash
# .github/workflow-scripts/exec_swallow_error.sh:7-16
# execute command
"$@"

# check status
STATUS=$?
if [ $STATUS == 0 ]; then
  echo "Command " "$@" " completed successfully"
else
  echo "Command " "$@" " exited with error status $STATUS"
fi
```

**逐行分析退出码**：

| 行 | 命令 | 该行退出码 |
| --- | --- | --- |
| 8 | `"$@"` | 被命令决定，但**未立即退出** |
| 11 | `STATUS=$?` | **0**（赋值总是成功） |
| 12–16 | `if` 分支，末行是 `echo` | **`echo` 恒为 0** |

**脚本自身的退出码 = 最后一个命令的退出码 = `echo` 的 0。**

> **即：无论 `"$@"` 是成功还是失败，本脚本都返回 0。**
> 脚本名 `exec_swallow_error` **诚实地自陈了这一点** ——
> 「swallow error」即「吞掉错误」。

### 2.2 谁在用它

```yaml
# .github/workflows/test-all.yml:565-567
      - name: ESLint
        shell: bash
        run: ./.github/workflow-scripts/exec_swallow_error.sh yarn lint --format junit -o ./reports/junit/eslint/results.xml
```

**全仓库唯一调用点**（`grep -rn "exec_swallow_error" .github/` 实测）。

### 2.3 `lint` job 的 5 个步骤

| # | 步骤 | 命令 | 能否失败 |
| --- | --- | --- | --- |
| ① | Checkout | `actions/checkout@v6` | ✅ |
| ② | Setup Node.js | `./.github/actions/setup-node` | ✅ |
| ③ | Install dependencies | `./.github/actions/yarn-install` | ✅ |
| ④ | Run shellcheck | `./.github/workflow-scripts/analyze_scripts.sh` | ✅ |
| ⑤ | markdownlint | `yarn run lint-markdown` | ✅ |
| ⑥ | **ESLint** | **`exec_swallow_error.sh yarn lint …`** | ❌ **恒 0** |
| ⑦ | Flow | `yarn flow-check` | ✅ |
| ⑧ | TypeScript | `yarn test-typescript-legacy` | ✅ |

**8 个步骤里只有 ESLint 这一处被吞掉错误**，其余 7 处都能正常失败。

### 2.4 生成的 JUnit XML 有无消费者（决定性反证）

| 搜索 | 结果 |
| --- | --- |
| `grep -rn "junit/eslint\|reports/junit" .github/` | 3 处命中 |
| `.github/workflows/test-all.yml:567` | **写入方**（ESLint 步骤本身） |
| `.github/actions/test-js/action.yml:26` | `path: ./reports/junit` —— **仅 upload-artifact** |
| `.github/actions/test-ios-rntester/action.yml:153` | `path: ./reports/junit` —— **仅 upload-artifact** |

**`lint` job 的 8 个步骤里没有任何 `upload-artifact`** ——
即 **ESLint 的 XML 报告被写入后直接丢弃，不上传、不解析**。

> **完整结论（三步反证，全部实测）**：
>
> | # | 检查 | 结果 |
> | --- | --- | --- |
> | 1 | `exec_swallow_error.sh` 的退出码 | **恒 0**（末行是 `echo`） |
> | 2 | `lint` job 是否有后续步骤消费 XML | **无**（8 步骤已逐条列出） |
> | 3 | 是否有其他 workflow 消费该 XML | **无**（3 处命中全是写入或上传） |
>
> **因此：ESLint 报出任意数量的 error，`lint` job 依然绿色，
> `test_js` / `build_js_types` 因 `needs: [check_code_changes, lint]` 也不会被阻塞。**
>
> **这是本仓库最严重的一条工具链问题** ——
> 它不产生任何告警，只是**让一整个静态检查类别失去意义**。

### 2.5 范围界定（必须精确）

| 维度 | 结论 |
| --- | --- |
| **是否 CI 的唯一 JS 静态检查** | **是** —— `yarn lint` 在 CI 中只此一处被调用 |
| **本地 `yarn lint` 是否有效** | **有效** —— 直接跑不经过包装脚本，退出码正常 |
| **谁会受影响** | **仅 CI**；本地开发者按 AGENTS.md 跑 `yarn lint` 仍会看到失败 |
| **是否 fork 会受影响** | **否** —— `lint` job 有 `if: github.repository == 'react/react-native'` |
| **Flow / TS 是否受影响** | **否** —— `yarn flow-check`、`yarn test-typescript-legacy` 均未包装 |

## 3. 【核心发现 OO-2】四种语言的 format-check 在缺工具链时静默通过

### 3.1 串联结构

```json
// package.json:17-23
    "format-check": "yarn format-check-javascript && yarn format-check-cpp && yarn format-check-kotlin && yarn format-check-java && yarn format-check-python && yarn format-check-swift",
    "format-check-cpp": "node ./scripts/clang-format.js --check",
    "format-check-java": "node ./scripts/format-java.js --check",
    "format-check-javascript": "prettier --check \"./**/*.{cjs,cts,flow,js,jsx,md,mjs,mts,ts,tsx,yaml,yml}\"",
    "format-check-kotlin": "node ./scripts/format-kotlin.js --check",
    "format-check-python": "node ./scripts/format-python.js --check",
    "format-check-swift": "node ./scripts/format-swift.js --check",
```

**`&&` 串联 6 种语言** —— 只有前面全部成功才会继续。

### 3.2 四个包装器的跳过分支

| 脚本 | 跳过行 | 行为 |
| --- | --- | --- |
| `scripts/format-python.js` | `:79-84`、`:86-92`、`:116-120`、`:137-141`、`:166-169`、`:181-187` | **6 处** `console.warn("Skipping …")` + `return` |
| `scripts/format-kotlin.js` | `:47-51` | `warnMissingJava('Kotlin'); return;` |
| `scripts/format-java.js` | `:65-69` | `warnMissingJava('Java'); return;` |
| `scripts/format-swift.js` | `:107-110` | `if (swiftFormat == null) { return; }` |

**四者共同点：`return` 之后 `main()` 正常结束 → `process.exitCode` 保持初始值 0。**

**共享的告警函数**：

| 文件 | 行号 | 作用 |
| --- | --- | --- |
| `scripts/format-utils.js` | `:73-80` | `warnMissingJava` —— 被 Kotlin/Java 两个脚本共用 |

**Python 有 6 处跳过**，是最细的一个（对应 6 类 Python 工具/依赖缺失）。

### 3.3 后果矩阵

| 开发者本机环境 | `format-check` 结果 |
| --- | --- |
| 全部工具齐全 | ✅ 真正检查 6 种语言 |
| **缺 Python** | ⚠️ **Python 全跳过，其余 5 种正常检查，退出 0** |
| **缺 JDK 17+** | ⚠️ **Kotlin + Java 双双跳过，退出 0** |
| **缺 Swift 工具链** | ⚠️ **Swift 跳过，退出 0** |

> **AGENTS.md 已经预告了这个行为**（「Each language wrapper checks its own
> requirements and prints installation guidance when something is missing;
> `yarn format` then skips that language and continues formatting the others」）
> —— **文档是准确的，但文档没有说明「因此 CI 上的 format 门禁在本机缺工具链时形同虚设」。**
>
> **注意这不是纯本地问题**：若 CI runner 镜像变更导致某个工具链缺失，
> **该语言的格式检查会静默失效，而 CI 依然绿色**。
>
> **这是与 OO-1 相反的方向**：OO-1 是**恒定失效**，OO-2 是**条件失效**。

## 4. 【核心发现 OO-3】C++ API 快照的三条「无基线即通过」

### 4.1 三处 `return True`

```python
# scripts/cxx-api/parser/snapshot_diff.py:34-46
def _check_snapshots_impl(generated_dir: str, committed_dir: str, out) -> bool:
    if not os.path.isdir(committed_dir):
        print(f"No committed snapshots directory found at: {committed_dir}", file=out)
        print("Skipping comparison (no baseline to compare against)", file=out)
        return True

    committed_files = sorted(f for f in os.listdir(committed_dir) if f.endswith(".api"))
    generated_files = sorted(f for f in os.listdir(generated_dir) if f.endswith(".api"))

    if not committed_files:
        print("No committed snapshot files found", file=out)
        print("Skipping comparison (no baseline to compare against)", file=out)
        return True
```

**两处 `return True`** —— 即**校验函数报告「通过」**。

### 4.2 第三处：新增视图不算失败

```python
# scripts/cxx-api/parser/snapshot_diff.py:63-66
        if filename not in committed_set:
            print(f"OK: {filename} generated (no committed baseline)", file=out)
            continue
```

**`continue` 跳过该文件** —— **新生成的快照永远不是失败**。

**打印文案是 `OK:` 前缀**，进一步强化了「这是正常情况」的错觉。

### 4.3 汇总：三种「通过」与唯一一种「失败」

| 情形 | 行为 | 打印 |
| --- | --- | --- |
| 基线目录不存在 | **`return True`** | `Skipping comparison (no baseline to compare against)` |
| 基线目录存在但无 `.api` | **`return True`** | 同上（先打印 `No committed snapshot files found`） |
| **新增了快照视图** | **`continue`（跳过）** | `OK: … (no committed baseline)` |
| 基线有但未生成 | `all_passed = False` | `FAIL: … exists in committed snapshots but was not generated` |
| 两者都有且内容不同 | 差异报错 | — |

> **唯一的失败方向是「删了 API」**（基线有、生成没有）。
>
> **即 C++ API 快照门禁是单向的**：
> **新增公开 API 不会让 CI 失败，删除公开 API 才会。**
>
> **这与 AGENTS.md 的记载方向相反**：
> AGENTS.md 写「CI validates the committed snapshots」——
> **准确的说法是「CI validates deletions from the committed snapshots」。**

### 4.4 相邻的第二条静默路径：Doxygen 文件缺失被跳过

| 位置 | 行为 |
| --- | --- |
| `scripts/cxx-api/parser/main.py:414-416` | `print(f"Detail file not found at {detail_file}"); continue` |
| `scripts/cxx-api/parser/main.py:445-446` | `print(f"Unknown compound kind: {kind}")` |
| `scripts/cxx-api/parser/main.py:105-107` | `print(f"Unknown section kind: …")` |

**三处都是「打印 + 继续」** —— **产出的是残缺快照**。

> **这类残缺快照的后果与 OO-3 相反**：
> 缺文件会导致生成结果比基线**少内容**，
> 而「基线有、生成没有」**恰好是唯一会失败的方向** ——
> **因此这条路径会被下游抓到（以误报形式）**。
>
> **即：部分缺失 = 误报失败；全部新增 = 静默通过。**

### 4.5 快照体量（决定误报成本）

| 目录 | 文件数 | 行数 |
| --- | --- | --- |
| `scripts/cxx-api/` | 334 | **139 326** |
| 其中 `scripts/cxx-api/api-snapshots/` | 9 个 `.api` | 约 **123 000** |
| `scripts/cxx-api` 扣除快照后 | — | 约 **16 000** |

**`scripts/` 合计 461 文件 / 153 904 行，扣除快照后为 455 文件 / 31 578 行。**

> **即 `scripts/` 的 95% 体积是 9 个提交的 `.api` 快照文件。**
> **这解释了为什么 `cxx-api` 需要 Python 工具链而非 Node 脚本** ——
> 它是一个独立的 Doxygen + Python 流水线。

### 4.6 文档与实现的第二处偏差

| 项 | `scripts/cxx-api/README.md:76` | 实际 |
| --- | --- | --- |
| `private_directories` 配置键 | **有文档说明 + 警告** | **`config.yml` 无此键、`config.py:28-41` 未读取、`scripts/` 全文无引用** |

**快照数量也不一致**：

| 项 | 值 |
| --- | --- |
| README 列出的快照 | **6** |
| 实际提交 | **9** |
| 未列出的 | **全部 3 个 `Newarch` 变体** |

> **即 Newarch 相关的三个快照未进文档** ——
> 而 Newarch 正是当前的主架构方向，**文档缺失最要紧的部分恰好是最新的部分**。

## 6. Hermes：两个逐字相同的脚本

```sh
$ diff scripts/releases/use-hermes-nightly.js scripts/releases/use-hermes-prebuilt.js
$ echo $?
0
```

**`diff` 退出 0 = 逐字相同**（各 32 行）。

| 项 | 值 |
| --- | --- |
| 两个文件名 | `use-hermes-nightly.js` / `use-hermes-prebuilt.js` |
| 行数 | 各 **32** |
| `diff` 退出码 | **0**（无差异） |

## 7. 版本号的定义、传播与哨兵

### 7.1 `'1000.0.0'` 哨兵（9+ 文件）

| 项 | 值 |
| --- | --- |
| 哨兵值 | **`'1000.0.0'`** |
| 出现文件数 | **9 及以上**（跨文件复制） |
| 作用 | 占位版本，发布时被真实版本替换 |

**版本传播链**：

```
scripts/releases/set-version.js
  └─ monorepoUtils.updatePackageJson        ← 所有 workspace
       └─ set-rn-artifacts-version.js:87-119   ← 用模板写 4 个文件
            └─ gradle.properties:1           ← VERSION_NAME
```

| 环节 | 位置 |
| --- | --- |
| 版本设置入口 | `scripts/releases/set-version.js` |
| 全 workspace 改写 | `monorepoUtils.updatePackageJson` |
| 原生产物版本 | `set-rn-artifacts-version.js:87-119` |
| Android 侧读取 | `gradle.properties:1` 的 `VERSION_NAME` |

### 7.2 一条自我否认的注释

| 位置 | 内容 |
| --- | --- |
| `scripts/releases/set-rn-artifacts-version.js:56-57` | **`"This does not update package.json"`** |
| `set-rn-artifacts-version.js:127-145` | **却会改一个已提交的 Jest 快照** |

> **注释与行为直接矛盾** —— 注释说的是「不改 package.json」，
> 这本身是对的；**但同一文件改了仓库里的测试快照**，注释未提。
>
> **即「发布只写版本号」的自我约束，被一个快照写入破了一次。**

### 7.3 跨文件复制粘贴的两处

| 常量 / 逻辑 | 复制位置 |
| --- | --- |
| **`MAX_HEADER_BYTES = 4096`** | **4 个 format 脚本各一份** |
| **`isGenerated()` 探针** | **4 个 format 脚本各一份** |

> **这两处是 OO-2 的根因** ——
> **4 个文件**因为共享逻辑被复制，也就**共享了「缺工具链就 return」的缺陷**。
> **若改为共用模块，4 处缺陷可一次性修掉。**
>
> **分布实测**（`grep -c`）：
>
> | 文件 | `MAX_HEADER_BYTES` | `isGenerated` |
> | --- | --- | --- |
> | `scripts/format-kotlin.js` | 2 | 2 |
> | `scripts/format-java.js` | 2 | 2 |
> | `scripts/format-swift.js` | 2 | 2 |
> | `scripts/clang-format.js` | 2 | 2 |
> | `scripts/format-python.js` | **0** | **0** |
>
> **即 Python 包装器不含这段逻辑** —— 它 6 处 `Skipping` 分支是另一套写法。

| 位置 | 值 |
| --- | --- |
| `scripts/build/babel/node.config.js:13` | `TARGET_NODE_VERSION = '18'` |
| `packages/react-native/package.json:24` | `engines.node`: **`^22.13.0 \|\| ^24.3.0 \|\| >= 26.0.0`** |

> **一个说 Node 18，一个说 Node ≥22.13。**
>
> `TARGET_NODE_VERSION = '18'` 的用途是决定 Babel 的编译目标语法，
> **与「运行时需要哪个 Node」不是同一件事** ——
> 但**同一个常量名 `TARGET_NODE_VERSION` 极易被误读**，
> 且 **`engines` 声明才是实际约束**。
>
> **这是「同名不同义」的典型**：需要读代码才能区分，不能靠名字判断。
