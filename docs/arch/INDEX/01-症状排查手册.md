- `RT-1` `registerErrorListener` 无移除接口

**18 · Android JNI 胶水层：异常穿透的两个方向**

- `JNI-1` `extraData` 序列化在 `noexcept` 回调内，失败即 abort 进程
- `JNI-2` 未知参数/返回类型用 `LOG(FATAL)` 而非抛异常

- `JNI-7` 默认 ExceptionsManager 在 fatal 时必然抛异常

**20 · iOS CoreModules：崩溃上报与 RCTFatal 终止机制**

**64 · 渲染器基础设施：三处锁语义错配、一个 JS 可控的栈溢出向量、一个未文档化的信任边界**

- `DDD-1` 【核心】`ComponentDescriptorRegistry` 三处锁语义错配：① `registerComponentDescriptor` 完全不持锁地写两个被 `shared_lock` 保护读的 `unordered_map`；② `setFallbackComponentDescriptor` 同样无锁（且 `getFallbackComponentDescriptor` 是无锁的 `const` 读）；③ `at()` 的 interop 分支在共享锁下调 `registerComponentDescriptor`
- `DDD-1b` 【核心】`ComponentDescriptorProviderRegistry` 两处同类错配：`setComponentDescriptorProviderRequest` 与 `createComponentDescriptorRegistry` 均在 `shared_lock` 下写成员

- `DDD-3` 【核心】`MapBuffer` 的头部 `count` 不与 `bytes_.size()` 交叉校验，`getKeyBucket` 的二分查找与动态数据区的偏移均无边界保护（`clampToBufferBounds` 只 clamp 长度不 clamp 偏移）

- `DDD-5` 【核心】`Element::reference(ConcreteUnsharedShadowNode &)` 的 lambda 按引用捕获，而另一重载按 `std::move` 捕获 —— 后者安全、前者有未文档化的生命周期要求

- `DDD-11` `MapBuffer::DataType` 枚举与 Kotlin 侧 `MapBuffer.kt` 的 `DataType` 必须严格同序（JVM 侧按 ordinal 索引）
- `DDD-12` 7 处工程实践样本（见 §7）：umbrella 头的 `push_macro`、非对齐 `memcpy` 说明、Kotlin 字节序陷阱注释、5 处带编号的 TODO/FIXME、clamp 的双层防护注释、`measureLayout` 用 optional 的理由、Web 语义对齐注释

**65 · 错误处理的 C++ 底层：assert 宏的平台不对称、同模块两套数字解析策略、RedBox URL 还原的三个往返损坏**

- `EEE-1` 【核心】`react_native_expect` 与非 Android 版 `react_native_assert` 是裸 `if` 宏（无 `do{}while(0)`），而 Android 版 `react_native_assert` 是三元表达式 → 平台不对称；实测形态 B（`if` 后不写分号 + 有 `else`）静默改变语义（`else` 分支被跳过），仅 `-Wdangling-else` 警告（默认不开）
- `EEE-1b` 平台不对称：`REACT_NATIVE_DEBUG` + `NDEBUG` 的组合下，Android 的 assert 仍 `abort`，非 Android 的只打日志不中止（`assert(cond)` 在 `NDEBUG` 下是空操作）
- `EEE-2` 【核心】`RedBoxErrorParser` 的 `std::stoi` 越界抛 `std::out_of_range`，`parseErrorMessage` 无 try/catch；输入（错误消息）由 JS 完全可控；实测 `2147483648` 与 20 位数字均抛异常；同模块的 `StackTraceParser::toInt` 用 `std::from_chars` 安全返回 `nullopt` → 两套策略并存
- `EEE-3` 【核心】`JscSafeUrl` 的 `toJscSafeUrl`/`toNormalUrl` 有三个往返损坏（实测）：① query 中的 `?` 被编码成 `%3F` 但还原不解码 → 不可逆；② path 含 `//&` 时 `find` 误取第一个 → 路径被截断；③ path 以 `//&` 开头时抛 `std::invalid_argument`（一个正常 URL）
- `EEE-4` 【核心】`ParsedError::isRetryable` 恒为 `true`（7 处构造 0 处设置），而 iOS `startAutoRetryIfApplicable` 有 `if (!_errorData.isRetryable) return;` 分支
- `EEE-5` RedBox 消息的截断只作用于 `_lastErrorMessage`，真正做正则匹配的 `message` 未截断
- `EEE-6` `react_native_expect.h` 的裸 `if` 宏没有 Android 特化（与 `react_native_assert` 不同）
- `EEE-7` `flags.h` 定义的 `REACT_NATIVE_PRODUCTION` 在 `react_native_assert.h` / `react_native_expect.h` 中从未被使用（两处只判 `!REACT_NATIVE_DEBUG`）

**69 · legacy 桥的 C++ 侧：四处理性的「工作被静默丢弃」、一个无上限的调用缓冲，以及两套互不知情的组件名归一化**

- `III-1` 【核心】桥销毁/失效路径上有 4 处「工作被静默丢弃」，全部是 `if (...) { ... }` 无 `else` 的早退，无任何日志或通知：① `runOnExecutorQueue` 入队前 `*m_destroyed`；② 执行时 `*isDestroyed`；③ `JSCallInvoker::scheduleAsync` 的 `weak_ptr` 过期；④ `getRuntimeExecutor` 的 `weak_ptr` 过期
- `III-2` 【核心】`JSCallInvoker::m_workBuffer` 是无上限的 `std::list<CallFunc>` —— 桥建立前的调用无限积压，无计数器、无告警
- `III-3` 【核心】`ModuleRegistry::normalizeName` 与 `componentNameByReactViewName` 是两套互不知情的组件名归一化：一边剥 `RCT`+`RK`、一边剥 `RCT`+10 条映射表 → 同一个名字在两条路径上归一化成不同结果（`RCTText` → `Text` vs `Paragraph`）
- `III-4` `getConfig` 组装的是「变长数组 + 位置协议」（长度 2/3/4/5，每种位置含义不同），`methodId` 是方法在 `getMethods()` 数组里的下标 → 顺序变化即 methodId 错位
- `III-5` 头注释的「not implemented」列表描述了 6 个本类里不存在的接口（`onBatchComplete` / `getModule` / `getAllModules` / `notifyCatalystInstanceInitialized` / `notifyCatalystInstanceDestroy`），且引用了 `our.intern.facebook.com` 的内部任务链接
- `III-6` 四处逐字重复的 `moduleId` 边界检查（4 行 × 4 处）
- `III-7` `invokeSync` 直接抛 `std::runtime_error("Synchronous native -> JS calls are currently not supported.")`
