## 2. 【核心 PLY-1】polyfills 有两条消费路径，其中一条绕过了 `console`

### 2.1 生产路径：Metro 注入

`packages/metro-config/src/index.flow.js:66`：

```js
// packages/metro-config/src/index.flow.js:66
      getPolyfills: () => require('@react-native/js-polyfills')(),
```

`packages/polyfills/index.js:13-16` 返回的是**两个文件的绝对路径**，不是模块：

```js
// packages/polyfills/index.js:13-16
module.exports = () /*: Array<string> */ => [
  require.resolve('./console.js'),
  require.resolve('./error-guard.js'),
];
```

Metro 会把这两个文件的内容按序**内联到 bundle 的 `__prelude__`**，所以它们在用户代码之前执行，且 `require.resolve` 的路径由打包器处理 —— 这个设计使得 polyfill 不能 `import` 任何东西（内联后 `require` 语义不同）。`error-guard.js` 因此只用了裸全局（`global.RN$handleException`、`global.ErrorUtils = ...`），没有一行 `import`。

### 2.2 测试路径：直接 import 子路径

`packages/jest-preset/jest/setup.js:16`：

```js
// packages/jest-preset/jest/setup.js:16
import '@react-native/js-polyfills/error-guard';
```

### 2.3 后果

| 环境 | `console.*` 来源 | `ErrorUtils` 来源 |
| --- | --- | --- |
| React Native 应用（Metro） | `packages/polyfills/console.js` | `packages/polyfills/error-guard.js` |
| Jest（`@react-native/jest-preset`） | **Node 的原生 `console`** | `packages/polyfills/error-guard.js` |

也就是说：**`consoleTablePolyfill`、`consoleGroupPolyfill`、`Warning:` 降级、以及 `console.error` → `RN$handleException` 那条链，在任何 Jest 测试里都不会执行**。`__tests__/consoleTable-itest.js` 之所以能测到它，是因为它是 Fantom 集成测试（文件名 `*-itest.js`，在真实 RN 运行时里跑），不是 Jest 单测。

**判定：设计如此，但两条路径的差集没有任何文档或断言标注。** 任何「在 Jest 里验证 console 行为」的尝试都会得到与线上不同的对象。

## 3. 【核心 PLY-2】`applyWithGuardIfNeeded` 在「不在 guard 内」时丢掉返回值

`packages/polyfills/error-guard.js:78-93`：

```js
// packages/polyfills/error-guard.js:78-93
  applyWithGuardIfNeeded<TArgs extends ReadonlyArray<unknown>, TOut>(
    fun: Fn<TArgs, TOut>,
    context?: ?unknown,
    args?: ?TArgs,
  ): ?TOut {
    if (ErrorUtils.inGuard()) {
      /* $FlowFixMe[incompatible-type] : TODO T48204745 (1) apply(context,
       * null) is fine. (2) array -> rest array should work */
      /* $FlowFixMe[incompatible-type] : TODO T48204745 (1) apply(context,
       * null) is fine. (2) array -> rest array should work */
      return fun.apply(context, args);
    } else {
      ErrorUtils.applyWithGuard(fun, context, args);
    }
    return null;
  },
```

两条路径：

| 调用时的 `_inGuard` | 执行 | 返回值 |
| --- | --- | --- |
| > 0（已在 guard 内） | `return fun.apply(context, args)` | `fun` 的真实返回值 |
| 0（不在 guard 内） | `ErrorUtils.applyWithGuard(...)`，**没有 `return`** | 恒为 `null`（`:92`） |

**同一函数的返回类型是 `?TOut`，但实际只有一半的路径可能返回 `TOut`。** 调用方若依赖返回值，会在「最外层调用」时静默拿到 `null`、在「嵌套调用」时拿到真值 —— 这种不对称比「总是返回 `null`」更难发现。

**判定：缺陷（分支不对称）。** 修法是把 `else` 分支改成 `return ErrorUtils.applyWithGuard(fun, context, args);`，并删掉 `:92` 的 `return null`（或保留为 `undefined` 兜底）。

## 4. 【核心 PLY-3】默认的 `_globalHandler` 就是 `throw`，所以 guard 会重新抛出

`packages/polyfills/error-guard.js:22-27`：

```js
// packages/polyfills/error-guard.js:22-27
let _globalHandler: ErrorHandler =
  global.RN$useAlwaysAvailableJSErrorHandling === true
    ? global.RN$handleException
    : (e: unknown, isFatal: boolean) => {
        throw e;
      };
```

`applyWithGuard` 的 catch 分支（`:64-76`）：

```js
// packages/polyfills/error-guard.js:64-76
    try {
      _inGuard++;
      /* $FlowFixMe[incompatible-type] : TODO T48204745 (1) apply(context,
       * null) is fine. (2) array -> rest array should work */
      /* $FlowFixMe[incompatible-type] : TODO T48204745 (1) apply(context,
       * null) is fine. (2) array -> rest array should work */
      return fun.apply(context, args);
    } catch (e) {
      ErrorUtils.reportError(e);
    } finally {
      _inGuard--;
    }
    return null;
```

把两者接起来：

```text
fun 抛异常
  → catch (e)
    → ErrorUtils.reportError(e)
      → _globalHandler(e, false)
        → 默认实现 throw e        ← 重新抛出
```

于是：

- `RN$useAlwaysAvailableJSErrorHandling === true` 时，`_globalHandler` 是 `RN$handleException`，只要它不抛，`applyWithGuard` 就真的「吞掉」异常并返回 `null`；
- **其余情况**（含所有未设置该 flag 的宿主），`applyWithGuard` 会**把原异常重新抛出**。注意 `throw` 发生在 `catch` 块内，`finally { _inGuard-- }` 仍会执行，所以计数不会泄漏，但异常逃出了 guard。

文件头的注释（`:17-21`）把这个默认行为说成「before ExceptionsManager is configured」的兜底；而 `ErrorUtils.setGlobalHandler`（`:38-40`）正是让宿主在配置后替换它。

**判定：行为事实，且与「guard 等于安全网」的直觉相反。** 这条结论的意义在于：任何「用 `applyWithGuard` 包住回调以免崩」的写法，在 `RN$useAlwaysAvailableJSErrorHandling` 为假时**不成立**。

## 5. 【核心 PLY-4】`formatValue` 有 200 次调用上限，且计数器是全树共享

`packages/polyfills/console.js:68-72`：

```js
// packages/polyfills/console.js:68-72
  function formatValue(ctx, value, recurseTimes) {
    ctx.formatValueCalls++;
    if (ctx.formatValueCalls > 200) {
      return `[TOO BIG formatValueCalls ${ctx.formatValueCalls} exceeded limit of 200]`;
    }
```

四个细节：

1. **计数器在 `ctx` 上**（`:46-50` 的 `ctx` 由每次 `inspect()` 新建），所以是「单次 `console.log` 调用」的总预算，不是全局的。
2. **只增不减** —— 没有配对的 `--`，所以整棵对象树共享 200 次配额。
3. **判定的是「访问节点数」而不是深度**：宽度优先地遍历一个 300 个属性的扁平对象，比深度 10 的嵌套更容易触发；而 `getNativeLogFunction` 固定用 `depth: 10`（`:400`）。
4. **超额后返回的是一段字符串**，它会像正常值一样被拼进输出（而不是抛错或截断整棵树）。所以用户看到的可能是一个「里面某几个叶子变成 `[TOO BIG ...]`」的对象。

Node 的 `util.inspect` 没有这个上限（原文件 `:22-43` 的版权头来自 Joyent/Node）。这是 RN 为防病理对象自加的护栏。

**判定：有意的护栏，但输出形态容易被误读。** 这段文本说「exceeded limit of 200」，读起来像一条独立日志，实际是被格式化的**某个属性值**。

## 6. 【核心 PLY-5】`console` 的组装顺序决定「宿主优先」与「无条件覆盖」

`packages/polyfills/console.js:589-608`：

```js
// packages/polyfills/console.js:589-608
  global.console = {
    time: stub,
    timeEnd: stub,
    timeStamp: stub,
    count: stub,
    countReset: stub,
    createTask: consoleCreateTaskStub,
    ...(originalConsole ?? {}),
    error: getNativeLogFunction(LOG_LEVELS.error),
    info: getNativeLogFunction(LOG_LEVELS.info),
    log: getNativeLogFunction(LOG_LEVELS.info),
    warn: getNativeLogFunction(LOG_LEVELS.warn),
    trace: getNativeLogFunction(LOG_LEVELS.trace),
    debug: getNativeLogFunction(LOG_LEVELS.trace),
    table: consoleTablePolyfill,
    group: consoleGroupPolyfill,
    groupEnd: consoleGroupEndPolyfill,
    groupCollapsed: consoleGroupCollapsedPolyfill,
    assert: consoleAssertPolyfill,
  };
```

`...(originalConsole ?? {})` 位于两组之间，因此：

| 位置 | 成员 | 语义 |
| --- | --- | --- |
| spread **之前** | `time` / `timeEnd` / `timeStamp` / `count` / `countReset` / `createTask` | **宿主优先**：宿主提供了就用宿主的，没有才落到 stub |
| spread **之后** | `error` / `info` / `log` / `warn` / `trace` / `debug` / `table` / `group*` / `assert` | **无条件覆盖**：即使宿主有实现也被换掉 |

两个后果：

1. `console.time()` / `console.timeEnd()` 在 RN 里**默认什么也不做** —— 只有宿主（Hermes 自带 console 或 DevTools 注入）提供了真实实现才有计时。这与 [75 文档](./75-DevTools外壳的入口分叉与启动契约.md) 里 DevTools 外壳的分叉是同一类问题：**行为取决于宿主，而不取决于 RN**。
2. `createTask` 的 stub 是同步执行回调（`:575-577`：`return {run: cb => cb()}`），它只在宿主没有 `createTask` 时生效。「异步任务跟踪」在那种情况下不成立。

**判定：顺序是对的、但极易读错。** 同一个对象字面量里相邻 7 行是「可能被覆盖」，紧接着 11 行是「一定覆盖」，中间只靠一行 spread 分隔 —— 这是本文件最需要注释却**没有**注释的地方。

## 7. PLY-6 三个分组字形：`groupCollapsed` 与 `groupEnd` 用了同一个

`packages/polyfills/console.js:540-542` 定义三个 box-drawing 字符：

```js
// packages/polyfills/console.js:540-542
const GROUP_PAD = '\u2502'; // Box light vertical
const GROUP_OPEN = '\u2510'; // Box light down+left
const GROUP_CLOSE = '\u2518'; // Box light up+left
```

`packages/polyfills/console.js:551-564` 的三种用法：

| 函数 | 行 | 前缀字符 | 之后 |
| --- | --- | --- | --- |
| `consoleGroupPolyfill` | `:552` | `GROUP_OPEN`（`┐`） | `groupStack.push(GROUP_PAD)` |
| `consoleGroupCollapsedPolyfill` | `:557` | **`GROUP_CLOSE`（`┘`）** | `groupStack.push(GROUP_PAD)` |
| `consoleGroupEndPolyfill` | `:563` | **`GROUP_CLOSE`（`┘`）** | `groupStack.pop()`（先弹） |

所以 `console.groupCollapsed('x')` 与 `console.groupEnd()` 打出来的**首字符相同**（`┘`），区别只在于前者带 label、后者不带。

再加上一个结构性事实：`groupStack` 只影响**后续**消息（`groupFormat` 在 `:546-549` 把 `groupStack.join('')` 前置到消息里），而每条 RN 日志都是独立的一行字符串 —— 所以「分组」在原生日志里表现为逐行重复的前缀，不是一个可折叠的结构。这也解释了为什么 `groupCollapsed` 与 `group` 对原生输出毫无区别（原生不会折叠），只剩字形差异。

**判定：轻微缺陷（字形语义错配）。** `groupCollapsed` 用「闭合」的字形来「打开」一个分组，视觉上与 `groupEnd` 撞在一起。

## 8. PLY-7 `console.table` 的列宽按 UTF-16 码元计算

`packages/polyfills/console.js:501-509`：

```js
// packages/polyfills/console.js:501-509
  columns.forEach(function (k, i) {
    columnWidths[i] = k.length;
    for (var j = 0; j < rows.length; j++) {
      var cellStr = formatCellValue(rows[j], k);
      stringRows[j] = stringRows[j] || [];
      stringRows[j][i] = cellStr;
      columnWidths[i] = Math.max(columnWidths[i], cellStr.length);
    }
  });
```

`String.prototype.length` 数的是 UTF-16 码元，不是终端显示宽度：

| 字符 | `length` | 终端列宽 |
| --- | --- | --- |
| `'a'` | 1 | 1 |
| `'…'`（U+2026） | 1 | 1 |
| `'中'` | 1 | **2** |
| `'😀'` | **2** | **2** |

所以含全角字符的表格会错位（竖线不齐）。

现有测试没有覆盖这个偏差：`packages/polyfills/__tests__/consoleTable-itest.js` 的期望字符串里唯一的非 ASCII 是 `ƒ`（U+0192）与 `{…}` 的 `…`（U+2026），两者都是**单宽**字符（该文件共 4 行含非 ASCII，全部是这两类）。所以 275 行测试锁定的是一张**纯 ASCII/单宽表**的精确输出。

**判定：缺陷（显示宽度口径错误）+ 测试盲区。** 顺带一个值得记下的正面事实：`console.table` 的实现只有 132 行（`:437-538`），测试却有 275 行、12 个用例、逐个断言完整表格字符串 —— 这是 `packages/polyfills/` 里覆盖最扎实的一块。

## 11. 【核心 NAP-1】`getRuntimeProperties?.()` 只保护了调用，没保护结果

`packages/new-app-screen/src/NewAppScreen.js:131-142`：

```jsx
// packages/new-app-screen/src/NewAppScreen.js:131-142
function getHermesLabel(): React.Node {
  if (global.HermesInternal == null) {
    return null;
  }

  return (
    <ThemedText color="secondary" style={styles.label}>
      JS Engine: Hermes (
      {global.HermesInternal.getRuntimeProperties?.()['OSS Release Version']})
    </ThemedText>
  );
}
```

求值顺序：

```text
global.HermesInternal == null ?
  否 → global.HermesInternal.getRuntimeProperties
       存在 ? 调用 → 返回对象
       不存在 ? ?.() 短路 → undefined
     → undefined['OSS Release Version']     ← TypeError
```

`getRuntimeProperties?.(...)` 的可选链只作用在**方法引用**上；它短路返回 `undefined` 之后，后面的 `[...]` 是**普通成员访问**，不再受 `?.` 保护。所以：

| `HermesInternal` | `getRuntimeProperties` | 结果 |
| --- | --- | --- |
| `null` / `undefined` | — | 返回 `null`，正常 |
| 对象 | 函数 | 打印版本号 |
| **对象** | **不存在** | **抛 `TypeError: Cannot read properties of undefined (reading 'OSS Release Version')`** |

`packages/react-native/flow/HermesInternalType.js` 把所有成员都声明为**可选**（文件头 `:26-27` 的注释：「All members are optional because they may not exist when OTA'd to older VMs.」）—— 也就是说「对象存在、方法不存在」正是该类型**明确允许**的状态。这段代码对合法状态会崩。

而欢迎屏是新项目 `npx react-native init` 后第一眼看到的东西，崩在这里的代价是全屏红。

**判定：真实缺陷（可选链位置错误）。** 正确写法是 `global.HermesInternal.getRuntimeProperties?.()?.['OSS Release Version']`。


`packages/react-native-test-library/common/TestLibraryCommon.mm:19-22`（见 §19 的引用）同样只调 `resolve`。

两个方法都不会失败 —— 没有条件分支、没有可能抛的调用。保留 `reject` 块是 RN Promise 方法的惯例（签名对称），但这里它在**两个模块里都**是纯未使用参数，编译器对未使用的 Objective-C 参数不报警，所以没有任何机制会提示「这个 reject 永远不会被调用」。

顺带一个值得注意的架构事实：`TestLibraryApple.mm:10-14` 的注释解释了为什么用尖括号 import 兄弟模块：

```objc
// packages/react-native-test-library/apple/TestLibraryApple.mm:10-14
// Synth library products are emitted as .library(type: .dynamic, ...), so SPM
// wraps each autolinked dep as a Foo.framework under PackageFrameworks/. That
// gives angle-bracket imports the standard <Module/Header.h> resolution path,
// matching how most React Native libraries already organize their headers.
#import <TestLibraryCommon/TestLibraryCommon.h>
```

也就是说 `#import <TestLibraryCommon/...>` 之所以能解析，是因为 SPM 把每个依赖包成 `Foo.framework` —— 这是**夹具存在的目的**（验证 SPM 直接依赖 + 传递依赖的解析），不是随意选择。

**判定：无害，但「永不失败的 reject」是夹具的一个未记录特征。**
