## 2. 【核心 HHH-1】同一个「无 prerelease」在四种语言里有三种表示

### 2.1 四份模板的逐字对照

| 语言 | 文件 | 无 prerelease 时的表示 | 出处 |
| --- | --- | --- | --- |
| **ObjC** | `RCTVersion.m` | **`[NSNull null]`**（字典**值**） | `RCTVersion.m-template.js` |
| **C++** | `ReactNativeVersion.h` | **`""`**（空 `std::string_view`） | `ReactNativeVersion.h-template.js` |
| **JS** | `ReactNativeVersion.js` | **`null`**（字面量） | `ReactNativeVersion.js-template.js` |
| **Kotlin** | `ReactNativeVersion.kt` | **`null`**（`Map` 的**值**） | `ReactNativeVersion.kt-template.js` |

**逐字引用**：

```javascript
// scripts/releases/templates/RCTVersion.m-template.js
                  RCTVersionPrerelease: ${
                    version.prerelease != null
                      ? `@"${version.prerelease}"`
                      : '[NSNull null]'
                  },
```

```javascript
// scripts/releases/templates/ReactNativeVersion.h-template.js
  std::string_view Prerelease = ${
    version.prerelease != null ? `"${version.prerelease}"` : '""'
  };
```

```javascript
// scripts/releases/templates/ReactNativeVersion.js-template.js
  static prerelease: string | null = ${version.prerelease != null ? `'${version.prerelease}'` : 'null'};
```

```javascript
// scripts/releases/templates/ReactNativeVersion.kt-template.js
    "prerelease" to ${
      version.prerelease != null ? `"${version.prerelease}"` : 'null'
    }
```

### 2.2 跨语言读取时的具体陷阱

| 场景 | 后果 |
| --- | --- |
| JS 侧 `if (ReactNativeVersion.prerelease == null)` → 迁到 C++ 侧读 `ReactNativeVersion.Prerelease` | **C++ 侧是 `""` 而非 null** → 判空逻辑**恒不成立** → 被误判为「有 prerelease」 |
| ObjC 侧 `RCTGetReactNativeVersion()[@"prerelease"]` | **值是 `[NSNull null]`** → 必须 `== NSNull.null` 或 `== nil` 双重判断；**`if (dict[@"prerelease"])` 在 NSNull 下是 true** |
| Kotlin 侧 `VERSION["prerelease"]` | `Map<String, Any?>` → **值是 `null`** → `VERSION["prerelease"]?.toString()` 需判空 |

**即：同一个语义在四个平台需要四种判空写法**，而**没有任何一处文档说明这一点**。

### 2.3 另一处不对称：C++ 侧**只有 3 个宏、4 个字段**

```cpp
// packages/react-native/ReactCommon/react/utils/ReactNativeVersion.h:16-28
#define REACT_NATIVE_VERSION_MAJOR 1000
#define REACT_NATIVE_VERSION_MINOR 0
#define REACT_NATIVE_VERSION_PATCH 0

namespace facebook::react {

struct ReactNativeVersionType {
  int32_t Major = 1000;
  int32_t Minor = 0;
  int32_t Patch = 0;
  std::string_view Prerelease = "";
};
```

| 项 | 宏 | struct 字段 |
| --- | --- | --- |
| Major | ✅ `REACT_NATIVE_VERSION_MAJOR` | ✅ `Major` |
| Minor | ✅ `REACT_NATIVE_VERSION_MINOR` | ✅ `Minor` |
| Patch | ✅ `REACT_NATIVE_VERSION_PATCH` | ✅ `Patch` |
| **Prerelease** | ❌ **无宏** | ✅ `Prerelease` |

**即：C/C++ 消费者拿不到 prerelease 的编译期常量**（只能读 `ReactNativeVersion.Prerelease`）。

**与 52 文档 RR-3（位置聚合初始化依赖字段顺序）的对照**：
**这里是「宏集合与字段集合不对称」** —— 同样属于「两处表示同一份数据、但覆盖范围不同」。

### 2.4 弃用转发头：写法正确 ✓

```cpp
// packages/react-native/ReactCommon/cxxreact/ReactNativeVersion.h:10-20
#warning "Deprecated: use <React/Utils.h> instead."

#pragma push_macro("RN_UMBRELLA_CONTEXT")
#undef RN_UMBRELLA_CONTEXT
#define RN_UMBRELLA_CONTEXT 1

#include <react/utils/ReactNativeVersion.h>

#undef RN_UMBRELLA_CONTEXT
#pragma pop_macro("RN_UMBRELLA_CONTEXT")
```

| 特征 | 评价 |
| --- | --- |
| `#warning` 明确告知弃用 | ✓ |
| 用 `push_macro`/`pop_macro` 而非裸 `#define`/`#undef` | ✓ **正是 62 文档 BBB-5 描述的模式** |
| 转发到一个 `UmbrellaGuard`（public 档）的头 | ✓ 通过 `RN_UMBRELLA_CONTEXT` 合法放行 |
| **`#warning` 在 release 构建也会触发** | ⚠️ 见下 |

> **⚠️ 一个副作用**：`#warning` 是**无条件**的 ——
> **任何仍 `#include <react/cxxreact/ReactNativeVersion.h>` 的代码，在 release 构建里也会每次编译都打一条警告**。
> **若该头仍被广泛 include，release 构建日志会被刷屏**。
> **本轮未检索该头的 include 点数量**（不在本轮读的文件范围内）。

## 3. 【核心 HHH-2】`package.json` 的版本写入路径**完全绕过** `parseVersion`

### 3.1 两条路径的分工

```javascript
// scripts/releases/set-version.js:80-88
  const newPackageVersions = Object.fromEntries(
    Object.keys(packagesToVersion).map(packageName => [
      packageName,
      packageName === 'react-native' && skipReactNativeVersion
        ? '1000.0.0'
        : version,
    ]),
  );
```

**注意：这里用的是原始的 `version` 参数（一个字符串），不是 `parseVersion` 的结果。**

```javascript
// scripts/releases/set-version.js:105-108
  // Update generated files in packages/react-native/
  if (!skipReactNativeVersion) {
    await updateReactNativeArtifacts(version);
  }
```

**只有 native 文件路径才会走 `parseVersion`（在 `set-rn-artifacts-version.js:80`）**。

### 3.2 写入 package.json 时逐字复制

```javascript
// packages/react-native/scripts/shared/monorepoUtils.js:143-147
  const packageName = packageJson.name;

  if (packageName in newPackageVersions) {
    packageJson.version = newPackageVersions[packageName];
  }
```

**逐字赋值，无任何 semver 校验。**

### 3.3 `parseVersion` 接受并**保留** `v` 前缀

```javascript
// scripts/releases/utils/version-utils.js:13
const VERSION_REGEX = /^v?((\d+)\.(\d+)\.(\d+)(?:-(.+))?)$/;
```

**实测**（用逐字复制的正则与解构逻辑）：

| 输入 | `version.version` | `major` | `prerelease` |
| --- | --- | --- | --- |
| `0.76.0` | `"0.76.0"` | `0` | `undefined` |
| **`v0.76.0`** | **`"v0.76.0"`** ← **保留 `v`** | `0` | `undefined` |
| `v0.76.0-rc.1` | `"v0.76.0-rc.1"` ← 保留 | `0` | `"rc.1"` |
| `0.76.0-rc.1` | `"0.76.0-rc.1"` | `0` | `"rc.1"` |
| `1000.0.0` | `"1000.0.0"` | `1000` | `undefined` |
| `0.77.0-nightly-20250101-abc1234` | 原样 | `0` | `"nightly-20250101-abc1234"` |
| `1.2.3` | `"1.2.3"` | `1` | `undefined`（`validateRelease` 会拒绝） |
| `0.76.0-` | **抛异常** ✓ | — | — |

### 3.4 结论与后果

| 项 | 判定 |
| --- | --- |
| **`parseVersion` 接受 `v` 前缀** | ✅ 实测确认，且 `version.version` **保留**该前缀 |
| **`v` 前缀会进 package.json** | ✅ —— 因为 package.json 路径**根本不过 `parseVersion`** |
| **当前仓库是否会触发** | **不会** —— 实测仓库里的 `set-version.js` 调用点**都没有 `v` 前缀** |
| **风险类型** | **结构脆弱** —— CLI 参数无格式校验，`v` 前缀一路直达 `package.json` 的 `version` 字段 |
| **修复成本** | 极低：`setVersion` 里加一次 `parseVersion(version).version` 归一化 |

> **公允说明**：本轮**未验证** npm 对 `"v0.76.0"` 这种 `version` 字段的具体处理
> （npm 的 `semver.valid(x, true)` 严格模式会拒绝 `v` 前缀，但**本轮未实测 npm 的行为**）。
> **本文只断言「package.json 路径没有任何版本格式校验」这一可验证的事实。**

### 3.5 顺带：`isNightly` 依赖版本串里含字面量 `'nightly'`

```javascript
// scripts/releases/utils/version-utils.js:146-153
function isNightly(version /*: Version */) /*: boolean */ {
  // Check if older nightly version
  if (version.major === '0' && version.minor === '0' && version.patch === '0') {
    return true;
  }

  return version.version.includes('nightly');
}
```

| 分支 | 条件 | 说明 |
| --- | --- | --- |
| ① | `0.0.0` | **旧式 nightly**（`version.version.includes('nightly')` 为 false，靠这个特例兜住） |
| ② | 版本串**含字面量 `nightly`** | 靠**字符串包含**判定，而非结构化字段 |

**即 nightly 版本号必须把 `nightly` 这个词写进 prerelease 部分** —— 例如
`0.77.0-nightly-20250101-abc1234`（实测被正确解析）。

**注释里的四个例子与实现一致**：

```
 * - stable: 0.68.1
 * - prerelease: 0.Y.Z-rc.K
 * - e2e-test: X.Y.Z-20221116-2018
 * - nightly: X.Y.Z-20221116-0bc4547fc
 * - dryrun: 1000.0.0
```

> **注意 `e2e-test: X.Y.Z-20221116-2018` 这个格式** ——
> `isStablePrerelease` 的第三个分支 `version.prerelease?.match(/^(\d{8})-(\d{4})$/)` **正好匹配它**。
> **即 e2e 版本被当作「stable prerelease」处理** ✓ 分类正确。

### 3.6 buildType 校验体系（**这一层是完整的**）

| buildType | 校验函数 | 接受的形式 |
| --- | --- | --- |
| `release` | `validateRelease` | `isStableRelease`（`0.Y.Z`）或 `isStablePrerelease`（`0.Y.Z-rc.*` / `0.Y.Z-YYYYMMDD-NNNN`） |
| `dry-run` | `validateDryRun` | 上述 + `isMain`（`1000.0.0`）+ `isNightly` |
| `nightly` | `validateNightly` | `isNightly` |

**`validateBuildType` 用 `Set` 白名单**（`['release', 'dry-run', 'nightly']`），
**非法 buildType 抛错** ✓。

**即：native 文件路径的版本校验是三层（正则 → buildType 白名单 → 版本形态）**，
**而 package.json 路径是零层** —— **两条路径的严格程度相差三个数量级**。

## 4. 【核心 HHH-3】实测：生成文件与模板的同步状态

### 4.1 实测方法

**直接 `require` 四个模板，用 `version = {1000.0.0, major:'1000', minor:'0', patch:'0', prerelease:null}` 渲染，与仓库里的文件逐字节比对**（模板是纯 JS，无外部依赖）。

### 4.2 实测结果

| 生成文件 | 结果 |
| --- | --- |
| `packages/react-native/React/Base/RCTVersion.m` | ✅ **逐字节一致** |
| `packages/react-native/ReactCommon/react/utils/ReactNativeVersion.h` | ✅ **逐字节一致** |
| `packages/react-native/Libraries/Core/ReactNativeVersion.js` | ✅ **逐字节一致** |
| `packages/react-native/ReactAndroid/src/main/java/com/facebook/react/modules/systeminfo/ReactNativeVersion.kt` | ⚠️ **内容一致但格式不同** |

### 4.3 Kotlin 的差异**纯粹是格式化**

**逐行差异（实测）**：

| 行 | 模板 | 实际文件 |
| --- | --- | --- |
| 4-5 | 版权头**两行** | 版权头**一行**（长行） |
| 9-10 | `package com.facebook.react.modules.systeminfo` 前有空行 | 无空行 |
| 14-19 | `mapOf(` 后**每项一行** | **全部压成一行**：`mapOf("major" to 1000, "minor" to 0, "patch" to 0, "prerelease" to null)` |

**即：仓库里的 Kotlin 文件是「模板输出 + 格式化器（prettier / kotlin 格式器）」的结果**，
**而模板输出本身是未格式化的**。

**版本值两边完全一致**（`1000 / 0 / 0 / null`）✓

### 4.4 由此得到一个**反直觉但重要**的结论

> **「生成产物快照门禁」在这里不能用逐字节比对** ——
> **因为仓库里提交的是「生成 + 格式化」的产物，而生成器输出的是未格式化的文本。**
>
> **任何逐字节校验都会立刻失败**（且失败原因是格式化，与内容无关）。
>
> **正确的门禁形式必须是「生成 → 跑格式化 → 比对」**。
>
> **这解释了为什么这道门禁「不存在」** ——
> **不是「不知道要校验」，而是「校验方法还没设计出来」**。
>
> **与 67 文档 feature flags 的关键差异**：

| | 67 文档 feature flags | 本文 版本文件 |
| --- | --- | --- |
| 生成文件是否被格式化 | **否**（生成的 C++/Java/JS 头文件不经格式化器） | **是**（Kotlin 走格式化器） |
| 逐字节比对是否可行 | ✅ **可行**（`--verify-unchanged` 就是这么做的） | ❌ **不可行**（必须先格式化） |
| 门禁为何缺失 | **工具已实现，CI 未调用** | **工具不存在，CI 也无从调用** |
| **修复成本** | **加一个 workflow** | **需先设计「生成+格式化+比对」的流程** |

### 4.5 CI 现状：**跑生成器但不比对**

```yaml
# .github/actions/build-android/action.yml:33
      run: node ./scripts/releases/set-rn-artifacts-version.js --build-type ${{ inputs.release-type }}
```

```yaml
# .github/workflows/prebuild-ios-core.yml:60
            node ./scripts/releases/set-rn-artifacts-version.js --build-type "${{ inputs.version-type }}"
```

**实测：这两个调用之后没有任何 `git diff --exit-code` 步骤** —— 直接进入下一步。

### 4.6 失效方式与 67 文档**相反**

| | 67 文档 feature flags | 本文 版本文件 |
| --- | --- | --- |
| CI 是否跑生成器 | ❌ **不跑** | ✅ **跑**（构建前） |
| 手改生成文件的后果 | **CI 不抓**（生成文件原样参与构建） | **CI 静默修正**（生成器覆盖工作区文件后继续构建） |
| **构建产物的版本号** | 可能是错的 | ✅ **是对的**（用生成的值） |
| **仓库里提交的版本号** | 可能是错的 | **可能是错的**（但构建不受影响） |

> **即：版本文件的漂移在 CI 里是「静默修正」的** ——
> **构建出来的产物永远正确，但提交进仓库的源码可能是错的**。
>
> **这比 67 文档的形态更难被发现**：
> 67 文档是「CI 什么都不做」，本文是「CI 做了正确的事，但没检查你提交的东西对不对」。
>
> **对从源码构建的下游用户的影响**：
> 他们拿到的源码里版本号是错的，**但如果他们走 CI 构建，产物是对的**；
> **如果他们在本地构建且不跑生成器，产物就是错的**。
> **RN 的官方构建流程（CI）会跑生成器 → 官方用户不受影响；自行构建的用户受影响。**

| 另一个版本号（如某个 fixture 的 `"1.2.3`） | **被一并改写成新版本** → **测试快照被静默污染** |
| 形如 `"0.76.0-rc.1`（带 `rc.`） | 会被匹配（正则含该分支）→ 同上 |
| 形如 `"0.76.0-beta.1`（其他 prerelease） | **不匹配**（正则只认 `-rc.N`）→ **旧版本号残留** |

**即：正则只覆盖 `-rc.N` 形态的 prerelease**，而 `parseVersion` 允许**任意** prerelease 字符串。

| 项 | 判定 |
| --- | --- |
| **当前是否造成功能问题** | **否** |
| **风险类型** | **结构脆弱** —— 用正则改写测试快照，模式覆盖不全且无边界 |
| **更好的做法** | 用结构化替换（只改已知的 4 处），或让 snapshot 模板化 |

### 5.4 顺带：`gradle.properties` 的版本写入是**结构化**的 ✓

```javascript
// scripts/releases/set-rn-artifacts-version.js:155-161
async function updateGradleFile(version /*: string */) /*: Promise<void> */ {
  const contents = await fs.readFile(GRADLE_FILE_PATH, 'utf-8');

  return fs.writeFile(
    GRADLE_FILE_PATH,
    contents.replace(/^VERSION_NAME=.*/, `VERSION_NAME=${version}`),
  );
}
```

**用 `^VERSION_NAME=.*` 精确匹配单行** ✓ —— **与 snapshot 的正则改写形成鲜明对照**。

**实测当前值**：`packages/react-native/ReactAndroid/gradle.properties:1` → `VERSION_NAME=1000.0.0`。
