# 03 · 核心技术原理

> **基线**：react-native @ `9b131e42`（submodule `react-native/`，本文路径基准 = 该 submodule 根）

## 1. JS 引擎抽象：JSI

### 1.1 为什么需要 JSI

传统 RN 用 **Bridge**（JSON 序列化 + 异步消息队列）通信，代价是：

- 每次跨线程调用都要 JSON 序列化/反序列化
- 无法传递函数、Promise、原生对象
- 无法同步调用
- 引入额外的内存拷贝与延迟

**JSI（JavaScript Interface）** 是 C++ 接口，直接嵌入 JS 引擎（Hermes / JSC）的对象模型，允许 C++ 直接读写 JS 对象。接口定义在 `ReactCommon/jsi/jsi/jsi.h`。

核心类型：
- `jsi::Runtime` —— 引擎实例的抽象
- `jsi::Value` / `jsi::Object` / `jsi::Array` / `jsi::Function` / `jsi::String`
- `jsi::PropNameID` —— 属性名（做了 interning 优化）
- `jsi::JSError` —— JS 异常在 C++ 的表示

### 1.2 Runtime 的可插拔性

`ReactCommon/jsitooling/react/runtime/JSRuntimeFactory.h` 定义工厂接口，各端提供实现：

| 平台 | 文件 | 内容 |
| --- | --- | --- |
| Android | `ReactAndroid/src/main/java/com/facebook/react/runtime/hermes/HermesInstance.kt:15-23`、`ReactAndroid/src/main/jni/react/runtime/jni/JReactInstance.cpp:16-29` | 构造 Hermes / JSC |
| iOS | `React/Runtime/RCTHermesInstanceFactory.mm:17` | 构造 Hermes |

`ReactCommon/react/runtime/hermes/HermesInstance.cpp:53-66` 有 TTI 感知的 GC 调优：

```cpp
if (allocInOldGenBeforeTTI) {
  // For the next two arguments: avoid GC before TTI
  // ...
  gcConfig.withAllocInYoung(false).withRevertToYGAtTTI(true);
}
```

**但 `allocInOldGenBeforeTTI` 在两端都被硬编码为 `false`**（`RCTHermesInstanceFactory.mm:17` 的 `/* allocInOldGenBeforeTTI */ false`，`ReactCxxPlatform/react/runtime/ReactHost.cpp:201` 同）—— 这条优化路径在 OSS 中**完全不生效**。

### 1.3 JSI 绑定的注入时机

`ReactInstance::initializeRuntime`（`ReactInstance.cpp:442-609`）在 runtime 上注入一批全局：

```cpp
runtimeScheduler_->scheduleWork([...](jsi::Runtime& runtime) {
  TraceSection s("ReactInstance::initializeRuntime");

  bindNativePerformanceNow(runtime);                                  // performance.now()
  RuntimeSchedulerBinding::createAndInstallIfNeeded(runtime, runtimeScheduler_);
  runtime_->unstable_initializeOnJsThread();
  defineReactInstanceFlags(runtime, options);

  defineReadOnlyGlobal(runtime, "RN$useAlwaysAvailableJSErrorHandling", ...);
  defineReadOnlyGlobal(runtime, "RN$isRuntimeReady", ...);
  defineReadOnlyGlobal(runtime, "RN$hasHandledFatalException", ...);
  defineReadOnlyGlobal(runtime, "RN$notifyOfFatalException", ...);
  defineReadOnlyGlobal(runtime, "RN$inExceptionHandler", ...);
  defineReadOnlyGlobal(runtime, "RN$handleException", ...);
  defineReadOnlyGlobal(runtime, "RN$registerExceptionListener", ...);
```

## 2. 事件循环

> **交互式流程图**：[事件循环：一个 tick 内的任务与 UI 原子更新](./diagrams/03-event-loop.html)

官方文档：`ReactCommon/react/renderer/runtimescheduler/__docs__/README.md`

### 2.1 模型

对齐 HTML 规范，一个 tick 四步：

```
┌─────────────────────────────────────────────────┐
│ 1. Select a task      （RuntimeScheduler 选任务）  │
├─────────────────────────────────────────────────┤
│ 2. Execute the task   （执行 JS 函数 / C++ 回调）   │
├─────────────────────────────────────────────────┤
│ 3. Execute microtasks （drainMicrotasks）         │
├─────────────────────────────────────────────────┤
│ 4. Update the rendering                          │
│    ├─ Event Timing 分发                          │
│    ├─ ResizeObserver 广播                         │
│    ├─ IntersectionObserver 更新                   │
│    └─ 排空 pendingRenderingUpdates_（提交 + 命令）   │
└─────────────────────────────────────────────────┘
```

### 2.2 核心语义：任务内 UI 更新的原子性

文档 `:45-61` 明确：

> One of the most important semantics of the event loop is the **atomicity of UI updates in tasks**.

举例（文档 `:64-100`）：事件 handler 里 `setState` → React 排 microtask → microtask 里处理 state + commit + `useLayoutEffect` 里再 `setWidth`（同步处理，同一 microtask）→ **用户从头到尾看不到中间状态**。

实现位置：`RuntimeScheduler_Modern.cpp`

| 步骤 | 位置 |
| --- | --- |
| `runEventLoop` / `runEventLoopTick` | `:277-344` |
| `selectTask` | `:295-314`（含 `// Skip executed tasks` 的空 callback 清理） |
| `executeTask` | `:411` |
| `performMicrotaskCheckpoint` | `:449` |
| microtask 排空 | `:456-479`（`kRetriesBound = 255`） |
| `updateRendering` | `:357-405` |
| `scheduleRenderingUpdate` | `:204-211`（**无超时**） |

### 2.3 任务优先级

`RuntimeScheduler.h` + `SchedulerPriorityUtils.h:43-60`：

| 优先级 | 回调饥饿超时 |
| --- | --- |
| `ImmediatePriority` | 0ms |
| `UserBlockingPriority` | 250ms |
| `NormalPriority` | 5s |
| `LowPriority` | 10s |
| `IdlePriority` | 5min |

选任务规则（文档 `:135-141`）：
1. 有过期任务 → 按过期顺序选
2. 否则按优先级，同优先级按调度顺序

### 2.4 错误对事件循环的影响

`RuntimeScheduler_Modern::handleTaskError`（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:498-504`）：

```cpp
void RuntimeScheduler_Modern::handleTaskError(jsi::Runtime& runtime, jsi::JSError& error) {
  clearQueues();
  onTaskError_(runtime, error);
}
```

`clearQueues()`（`RuntimeScheduler_Modern.cpp:506-515`）：

```cpp
void RuntimeScheduler_Modern::clearQueues() {
  { std::unique_lock lock(schedulingMutex_); taskQueue_ = {}; isEventLoopScheduled_ = false; }
  pendingRenderingUpdates_ = {};
  surfaceIdsWithPendingRenderingUpdates_.clear();

```

**一个 task 抛错会清空整个事件循环的所有待处理工作。** 这是有意为之（避免在损坏的运行时上继续），但对 App 来说是「一个异常毁掉整批交互」。

### 2.5 `requestIdleCallback`

`ReactCommon/react/nativemodule/idlecallbacks/NativeIdleCallbacks.cpp`：

- `:130-134` 旧调度器不支持时抛 `jsi::JSError("requestIdleCallback is not supported in legacy runtime scheduler")`

### 3.5 RSNRU：Runtime Shadow Node Reference Update

`ReactCommon/react/renderer/core/__docs__/RSNRU.md` 记录了一个重要的内存优化：**JS 侧持有的 ShadowNode 引用，在 commit 后会被降级**。

```cpp
// .cpp:32-40
// packages/react-native/ReactCommon/react/renderer/uimanager/consistency/LazyShadowTreeRevisionConsistencyManager.cpp:32-40
// We don't need to store the revision if we haven't locked.
```

### 4.2 同步调用能力

TurboModule 相对旧 Bridge 的核心优势是**支持同步方法**。这依赖于 `CallInvoker` 能在需要时阻塞 JS 线程等待原生返回。

`ReactInstance.h:46-56` 的注释解释了 buffered invoker 的动机：

```cpp
/**
 * The CallInvoker platforms should hand to TurboModules and other native
 * callers. Behind `enableBufferedCallInvoker` this shares the instance's
 * BufferedRuntimeExecutor, so async calls are ordered against
 * `callFunctionOnModule` and do not run before the main bundle has finished
 * evaluating; otherwise it is the unbuffered RuntimeScheduler-backed invoker.
 * See CallInvokerImpl.
 */
```

`BufferedRuntimeExecutor`（`react/runtime/BufferedRuntimeExecutor.h`）的作用是**把所有回调推迟到 bundle 完全执行之后**。iOS 的 surface 启动也用了它（`RCTHost.mm:437-438`）：

```objc
// Use the BufferedRuntimeExecutor to start the surface after the main JS bundle was fully executed.
[_instance callFunctionOnBufferedRuntimeExecutor:[weakSurface](facebook::jsi::Runtime &_) { [weakSurface start]; }];
```

flush 时机在 `ReactInstance.cpp:312-315`：

```cpp
if (auto strongBufferedRuntimeExecuter = weakBufferedRuntimeExecuter.lock()) {
  strongBufferedRuntimeExecuter->flush();
}
```

**在 `loadScript` 内部、`afterLoad` 之前。** 这保证了「JS 侧注册的组件、注册的模块都准备就绪后，原生才知道该往哪个 surface 上挂载」。

## 6. 定时器

### 6.1 C++ `TimerManager`（新架构）

`ReactCommon/react/runtime/TimerManager.h:85-92`：

```cpp
void TimerManager::callTimer(TimerHandle timerHandle) {
  runtimeExecutor_([this, timerHandle](jsi::Runtime& runtime) {
    auto it = timers_.find(timerHandle);
    if (it != timers_.end()) {
      auto& timerCallback = it->second;
      bool repeats = timerCallback.repeat;
      { TraceSection s("TimerManager::callTimer", ...); timerCallback.invoke(runtime); }
      if (!repeats) {
        // Invoking a timer has the potential to delete it. Do not re-use the
        // existing iterator to erase it from the map.

      }
    }
  });
}
```

`deleteTimer`（`packages/react-native/ReactCommon/react/runtime/TimerManager.cpp:135-169`）严格遵循 Web 规范忽略负数 id：

**`requestAnimationFrame` 就是 `setTimeout(0)`**（`packages/react-native/ReactCommon/react/runtime/TimerManager.cpp:360-367`）：
