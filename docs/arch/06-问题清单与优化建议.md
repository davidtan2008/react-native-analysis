## 一、P0 阻塞级

### P0-1 启动耗时指标 `RCTPLTTI` 永远算不出有效值

**位置**：`React/Base/Surface/SurfaceHostingView/RCTSurfaceHostingProxyRootView.mm:122`

```objc
if (RCTSurfaceStageIsRunning(stage)) {
  [_bridge.performanceLogger markStopForTag:RCTPLTTI];
```

**问题**：全仓库搜索 `RCTPLTTI` 只有 3 处命中 —— `RCTPLTag.h:25`（枚举声明）、`RCTPerformanceLoggerLabels.m:46`（label）、以及上面这处 `markStopForTag`。**没有任何 `markStartForTag:RCTPLTTI`。**

`RCTPerformanceLogger.mm:66-86` 的 `markStopForTag:`：

```objc
const NSTimeInterval currentTime = CACurrentMediaTime() * 1000;
if (_data[tag][0] != 0 && _data[tag][1] == 0) {
  _data[tag][1] = currentTime;
} else {
  RCTLogInfo(@"Unbalanced calls start/end for tag %li", (unsigned long)tag);
}
```

因为 `_data[RCTPLTTI][0] == 0`，走进 `else` 分支，只打一条 Info 日志，`_data[RCTPLTTI][1]` 保持 0。随后 `durationForTag:`（`:125-128`）返回 `0 - 0 == 0`。

**后果**：iOS 上最关键的「Time To Interactive」指标**恒为 0**，任何基于它的启动耗时看板都是错的。

**修复方向**：在 `RCTInstance` 开始加载 bundle 处（`RCTInstance.mm:122` 附近，与 `RCTPLReactInstanceInit` 同一位置）补 `markStartForTag:RCTPLTTI`；或重新定义 TTI 起点为「`didFinishLaunching`」。

### P0-2 `SoLoader.init` 完全没有耗时测量

**位置**：`ReactAndroid/src/main/java/com/facebook/react/ReactInstanceManager.java:383-392`

```java
static void initializeSoLoaderIfNecessary(Context applicationContext) {
  // ...
  SoLoader.init(applicationContext, /* native exopackage */ false);
}
```

被 `:239`（构造函数）和 `ReactInstanceManagerBuilder.kt:375` 调用。

**问题**：**没有任何 `ReactMarker` 包裹**。而 `ReactNativeJniCommonSoLoader.kt:22-24`、`ReactNativeJNISoLoader.kt:24-26`、`FabricSoLoader.kt:23-27` 都各自打了 `LOAD_REACT_NATIVE_SO_FILE_START/END` marker。

**修复方向**：在 `initializeSoLoaderIfNecessary` 前后加 `ReactMarkerConstants` marker（可复用 `LOAD_REACT_NATIVE_SO_FILE_START/END`，或新增专用常量）。

### P0-3 Android 的 JS `memoryWarning` 事件是空实现

**位置**：`Libraries/AppState/AppState.js:45-58, 139-142` 声明并分发 `memoryWarning`；iOS 实现在 `React/CoreModules/RCTAppState.mm:77-113`。

```objc
- (NSArray<NSString *> *)supportedEvents { return @[ @"appStateDidChange", @"memoryWarning" ]; }

- (void)handleMemoryWarning { [self sendEventWithName:@"memoryWarning" body:nil]; }
```

**问题**：**在 `ReactAndroid/` 目录下搜索 `memoryWarning`：0 命中。**

`AppStateModule.kt`（`ReactAndroid/.../modules/appstate/`）完全没有发送这个事件。但 `MemoryPressureRouter.kt:52-56` 明明已经把压力事件分发到了所有 `MemoryPressureListener`。

**后果**：
- `AppState.addEventListener('memoryWarning', handler)` 在 Android 上**静默无效**。这是 RN 公开 API（`ReactNativeApi.d.ts` 中有声明），跨平台行为不一致。
- App 无法在收到内存警告时清理自己的业务缓存（图片、WebView、大 JSON）。
- RNTester 的示例 `packages/rn-tester/js/examples/AppState/AppStateExample.js:31,37,70` 还在统计这个事件数，在 Android 上会永远显示 0。

**修复方向**：在 `AppStateModule` 中注册为 `MemoryPressureListener`，在 `handleMemoryPressure` 时发送 `memoryWarning` 事件；或直接复用 `MemoryPressureRouter` 的分发链。

### P0-4 `JsErrorHandler` 的 fatal 去重会丢数据

**位置**：`ReactCommon/jserrorhandler/JsErrorHandler.cpp:395-404`

```cpp
if (isFatal || !isWarn) {
  if (isFatal) {
    if (_hasHandledFatalError) { return; }   // 后续所有 fatal 都被丢弃
    _hasHandledFatalError = true;
  }
  _onJsError(runtime, processedError);
}
```

**问题**：`_hasHandledFatalError` 一旦置真，进程生命周期内**所有后续 fatal 错误都不会被上报**。

设计意图是避免「一次崩溃触发级联错误」导致的重复上报。但实际场景中：
- 应用崩溃 → 被 APM 捕获 → 尝试上报 → 过程中再抛错 → 丢失
- 热修复 / 错误恢复后继续运行 → 第二个真实崩溃被丢弃
- 长时间运行的应用里，第一个致命错误可能是无关紧要的 OOM 副作用，第二个才是真正的 bug

**附带问题**：`RCTExceptionsManager.mm:74-77` 的 `static NSUInteger reloadRetries = 0;` 也是**进程级静态计数器，永不重置**：

```objc
static NSUInteger reloadRetries = 0;
if (!RCT_DEBUG && reloadRetries < _maxReloadAttempts) {
  reloadRetries++;
  RCTTriggerReloadCommandListeners(@"JS Crash Reload");
}
```

**后果**：iOS 上前 N 次崩溃会被「自动 reload 掩盖」，第 N+1 次才崩。这导致**灰度期崩溃率被系统性低估**。

**修复方向**：
- 改为「时间窗内去重」而非「进程内一次性去重」，例如同 fingerprint 5 秒内只报一次。
- `reloadRetries` 应在成功 reload 且运行 N 秒后重置。

### P0-5 iOS 与 Android 的崩溃终局不一致，导致崩溃率口径失真

| 场景 | iOS Release | Android Release |
| --- | --- | --- |
| JS fatal 错误 | reload 耗尽 → `RCTFatal` → `@throw NSException` → **进程崩溃** | `RedBox` + `ReactHost.destroy()` → **不崩溃** |
| bundle 加载失败 | `RCTInstance.mm:482` **无条件 `RCTFatal`** → 崩溃 | `DevSupportManagerBase.kt:819-827` 只显示红框 → 不崩溃 |
| DevSupport 关闭 | `RCTFatal` | `DefaultJSExceptionHandler` **rethrow** → 崩溃 |
| Host 异常 | 手动 `[_instance invalidate]` | `ReactHostImpl.kt:792` **自动 `destroy(method, e)`** |

**问题**：同一份业务代码，Android 上「JS 崩溃」被降级成「容器销毁 + 红框」，iOS 上是真崩溃。任何跨端的崩溃率大盘都会失真。

**修复方向**：这是架构级决策，建议在文档中明确「哪些错误算 crash、哪些算 ANR/异常退出」，并推动两端统一。至少应该让 APM 侧能通过 `extraData` 区分。

## 二、P1 严重

### P1-1 `ReactMarker::logTaggedMarkerImpl` 是全局单槽位

**位置**：`ReactCommon/cxxreact/ReactMarker.h:48-75`

```cpp
struct RN_EXPORT AtomicLogTaggedMarker {
  AtomicLogTaggedMarker &operator=(LogTaggedMarker marker) {
    std::unique_lock lock(mutex_); impl_ = std::move(marker); return *this;
  }
  ...
  LogTaggedMarker impl_;
  mutable std::shared_mutex mutex_;
};
```

赋值点：
- iOS：`RCTPerformanceLoggerUtils.mm:70`
- Android：`JReactMarker.cpp:23`（`std::call_once` 内）

**问题**：`std::shared_mutex` 只保证**线程安全**，不保证**多订阅者**。第二个赋值者会**静默覆盖**第一个。

**影响**：
1. App 无法在不破坏 RN 内部统计的前提下监听启动 marker。
2. 多 RN 实例场景（Android 上多 ReactHost）后创建的实例会抢走槽位。
3. `ReactInstance.cpp:275` 和 `JSIExecutor.cpp:154` 还把这个槽位当作「有没有人在监听」的判据：
   ```cpp
   bool hasLogger(ReactMarker::logTaggedMarkerImpl);
   if (hasLogger) { /* 打三个 marker */ }
   ```
   槽位被 App 抢走后，RN 内部的计时开关逻辑仍然工作，但 RCTPerformanceLogger 不再收到数据（反之亦然），两端数据会错位。

**修复方向**：改为 `std::vector` 多播 + 明确的「优先级/独占」语义。

### P1-4 `LeakChecker` 的最后一个 surface 永远不会被检查

**位置**：`ReactCommon/react/renderer/leakchecker/LeakChecker.cpp:25-41`

```cpp
void LeakChecker::stopSurface(SurfaceId surfaceId) {
  if (previouslyStoppedSurface_ > 0) {
    runtimeExecutor_([previouslyStoppedSurface = previouslyStoppedSurface_, this](jsi::Runtime& runtime) {
      runtime.instrumentation().collectGarbage("LeakChecker");
      // For now check the previous surface because React uses double
      // buffering which keeps the surface that was just stopped in
      // memory. This is a documented problem in the last point of
      // https://github.com/facebook/react/issues/16087
      checkSurfaceForLeaks(previouslyStoppedSurface);
    });
  }
  previouslyStoppedSurface_ = surfaceId;
}
```

**问题**：`previouslyStoppedSurface_` 初值为 0（`LeakChecker.h:36`）。流程是「检查上一个，然后把当前记为上一个」。因此：
- surface A stop → 检查 `0 > 0` 不成立 → 记录 A
- surface B stop → 检查 A → 记录 B
- **B 永远不会被检查**

**影响**：单页面应用的唯一 surface（最常见的 App 结构）**完全得不到泄漏检测**。这是唯一在跑的泄漏检测器，其核心场景失效。

**修复方向**：在 `~LeakChecker()` 中对 `previouslyStoppedSurface_` 做最后一次检查（此时 runtime 可能已不可用，需要用 `RuntimeExecutor` 的延迟语义或改用 `ShadowTree` 析构钩子）。更好的方案是等 facebook/react#16087 的双缓冲问题解决后直接检查当前 surface。

### P1-6 `ListMetricsAggregator._cellMetrics` 无界增长

**位置**：`packages/virtualized-lists/Lists/ListMetricsAggregator.js`

```js
// packages/virtualized-lists/Lists/ListMetricsAggregator.js:61,117,132-137
:61   _cellMetrics: Map<string, CellMetrics> = new Map();

:117  this._cellMetrics.set(cellKey, next);          // 写入

:132  notifyCellUnmounted(cellKey: string): void {
:133    const curr = this._cellMetrics.get(cellKey);
:134    if (curr) { curr.isMounted = false; }          // 只标记，不删除
:135  }
```

唯一的清理在方向变化时（`:314-329`）：

```js
_invalidateIfOrientationChanged(orientation: ListOrientation): void {
  if (orientation.rtl !== this._orientation.rtl) { this._cellMetrics.clear(); }
  if (orientation.horizontal !== this._orientation.horizontal) {
    this._cellMetrics.clear();
    this._averageCellLength = 0;
    ...
  }
  this._orientation = orientation;

```

**问题**：`CellMetrics` 内含 `frame: Rect`（在 `:227` 被用于计算 layout）。**这个 Map 会为每一个曾被 layout 过的 `cellKey` 永久保留一个对象及其中的 Rect 数据。**

聊天 / 社交 / 消息流场景中 `keyExtractor` 通常返回每条消息的唯一 id，用户持续上滑浏览 10 万条消息 → 10 万个 `CellMetrics` 常驻。**这是 RN JS 侧最明确的无界内存增长点。**

对比：同文件中 `_cellRefs` 是被正确删除的（`packages/virtualized-lists/Lists/VirtualizedList.js:1357-1360`）：

```js
_onCellUnmount = (cellKey: string) => {
  delete this._cellRefs[cellKey];
  this._listMetrics.notifyCellUnmounted(cellKey);
};
```

**源码里甚至有一段防御性注释（`:106-116`）承认了相关的风险**：

```js
// NOTE: _measuredCellsCount is incremented before this line whenever a new
// cell is added, so it should never be 0 here. This guard is defense in
// depth against a future bug where _measuredCellsCount is reset (e.g. during
// orientation changes) without also clearing _cellMetrics — which would leave
// `curr` with a stale value and count === 0, causing a divide-by-zero.
```

**修复方向**：`notifyCellUnmounted` 中判断该 cell 是否在「测量贡献窗口」内，若已远超当前最高测量索引（`highestMeasuredCellIndex`）且 `isMounted === false`，则从 Map 删除。或改为 LRU 缓存并设定容量上限。

### P1-7 LogBox 的两个容器无界增长（Dev 环境）

**问题 1**：`Libraries/LogBox/Data/LogBoxData.js:69` + `:139-194`

```js
// packages/react-native/Libraries/LogBox/Data/LogBoxData.js:69,139-154
let logs: LogBoxLogs = new Set();
...
function appendNewLog(newLog: LogBoxLog) {
  if (isMessageIgnored(newLog.message.content)) { return; }

  // If the next log has the same category as the previous one
  // then roll it up into the last log in the list by incrementing
  // the count (similar to how Chrome does it).
  const lastLog = Array.from(logs).pop();
  if (lastLog && lastLog.category === newLog.category) {
    lastLog.incrementCount();
    handleUpdate();
    return;
  }
  ...
  logs.add(newLog);
}
```

只有**相邻同 category** 才会合并计数。交替出现的不同 category（或不同 message 文本导致 category 变化）会**永久累积**。`clear()` / `clearWarnings()` / `clearErrors()` / `dismiss()` 都需要外部主动调用。

**问题 2**：`Libraries/LogBox/Data/LogBoxSymbolication.js:18`

```js
const cache: Map<Stack, Promise<SymbolicatedStackTrace>> = new Map();
```

key 是 Stack **数组对象本身**（引用相等）。而 `LogBoxData.js:241` 每次都 `parseErrorStack(...)` 产生新数组：

```js
const stack = parseErrorStack(log.stack ?? errorForStackTrace?.stack);
```

**这个缓存的命中率接近 0，且永不淘汰。** `deleteStack` 仅在 `retrySymbolicate`（`LogBoxLog.js:87-89`）中被调用。

**后果**：在有大量 console.error 的开发会话中（比如接了某个高频打点库），`logs` Set 和 `cache` Map 都会持续增长，导致开发版本自身越来越卡。

**修复方向**：
- `logs` 加上限（如 100），超出后丢弃最旧的非 fatal 项。
- `cache` 改用 stack 的**内容哈希**作为 key（这样能命中），并加 LRU 上限。

### P1-8 `RCTHost._attachedSurfaces` 永不清理

**位置**：`ReactCommon/react/runtime/platform/ios/ReactCommon/RCTHost.mm`

```objc
// packages/react-native/ReactCommon/react/runtime/platform/ios/ReactCommon/RCTHost.mm:276,587-601
:276  std::vector<__weak RCTFabricSurface *> _attachedSurfaces;

:587  - (void)_attachSurface:(RCTFabricSurface *)surface { _attachedSurfaces.push_back(surface); }
```

**问题**：只有 `push_back`，**没有任何 `erase` / `remove`**。整个文件中 `_attachedSurfaces` 只出现 3 次（声明、push、遍历）。

**后果**：

**修复方向**：改用 `NSHashTable<__weak RCTFabricSurface *>`（自动弱引用 + 自动清理），或在 `_reloadWithShouldRestartSurfaces:`（`:628-652`）和 `dealloc`（`:476-484`）中统一清空。

```js

:40   const timerIDs: Array<number> = [];
:49   const freeIdxs: Array<number> = [];
```

```js
:189  const index = timerIDs.indexOf(timerID);   // 线性扫描
```

**问题**：
1. `GUID` 单调递增，永不重置。`TimerHandle` 是 `int`（C++ `TimerManager.h:92` 的 `timerIndex_{1}` 同样如此）。
2. `timerIDs` 是**并行数组**，`_getFreeIndex`（`:40-46`）用 free-list 回收槽位，所以数组长度 = 同时存活定时器数量的历史峰值。
3. `_freeCallback`（`:183-202`）中的 `timerIDs.indexOf(timerID)` 是 **O(n) 线性扫描**。

**后果**：一次创建 10 万个 `setTimeout` 的突发（比如解析大 JSON 后批量调度）之后，数组长度永久停在 10 万，此后**每次 `clearTimeout` 都是 10 万次比较**。

**注意**：`JSTimers.js:9` 已标 `@deprecated`，Bridgeless 模式走 `TimerManager`（C++，`unordered_map`，O(1)）。所以这个问题主要影响旧架构。

**修复方向**：`Map<number, number>` 替代并行数组（`timerID → index`），把查找降到 O(1)。
