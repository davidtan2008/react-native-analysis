# 11 · 运行时与错误桥：ReactInstance 与 JsErrorHandler

> **模块**：A3（`ReactCommon/react/runtime` + `ReactCommon/jsi` + `reactperflogger`）+ `ReactCommon/jserrorhandler`
> **基线**：react-native @ `9b131e42`（submodule `react-native/`，本文路径基准 = 该 submodule 根）
> **前置**：[04 文档](./04-崩溃日志捕获收集处理上传.md) 讲了崩溃的捕获与分发。本文补上**其中最关键的一环**：
> C++ 侧的 `JsErrorHandler` 如何把一个 `jsi::JSError` 结构化成可上报的 `ProcessedError`，
> 以及**RN 在这条链路上明确不做什么**。

---

## 1. 上报端是注入的，不是 RN 实现的

`ReactInstance` 的构造函数（`react/runtime/ReactInstance.cpp:68-78`）：

```cpp
ReactInstance::ReactInstance(
    std::unique_ptr<JSRuntime> runtime,
    std::shared_ptr<MessageQueueThread> jsMessageQueueThread,
    std::shared_ptr<TimerManager> timerManager,
    JsErrorHandler::OnJsError onJsError,
    jsinspector_modern::HostTarget* parentInspectorTarget)
    : runtime_(std::move(runtime)),
      jsMessageQueueThread_(std::move(jsMessageQueueThread)),
      timerManager_(std::move(timerManager)),
      jsErrorHandler_(std::make_shared<JsErrorHandler>(std::move(onJsError))),
      parentInspectorTarget_(parentInspectorTarget) {
```

`onJsError` 是**外部注入的回调**。全仓库只有这一处 `JsErrorHandler` 的构造点，
`OnJsError` 本身在 RN 内部**没有任何实现**（`packages/react-native/ReactCommon/jserrorhandler/JsErrorHandler.h:40`）：

```cpp
  using OnJsError = std::function<void(jsi::Runtime &runtime, const ProcessedError &error)>;
```

**这印证并细化了 04 文档的结论**：RN 负责「捕获 → 结构化 → 回调分发」，
**上传、存储、重试、限流全部由宿主 App 决定**。框架层没有网络代码，也没有崩溃落盘。

`JsErrorHandler.h:57-62` 对回调的两条约束写得非常清楚：

```cpp
  /**
   * This callback:
   * 1. Shouldn't retain the ReactInstance. So that we don't get retain cycles.
   * 2. Should be implemented by something that can outlive the react instance
   *    (both before init and after teardown). So that errors during init and
   *    teardown get reported properly.
   **/
  OnJsError _onJsError;
```

> **第 2 条是设计承诺也是陷阱**：框架**期望**初始化前与销毁后的错误也能被上报。
> 但由于 `onJsError` 由宿主注入，框架无法保证宿主真的做到了 ——
> 这是「框架保证」与「宿主责任」的边界。

## 2. 错误从哪里被捕获

### 2.1 运行时执行器的兜底捕获

`ReactInstance.cpp:100-108`：

```cpp
            try {
              callback(jsiRuntime);
            } catch (jsi::JSError& originalError) {
              jsErrorHandler->handleError(jsiRuntime, originalError, true);
            } catch (std::exception& ex) {
              jsi::JSError error(
                  jsiRuntime, std::string("Non-JS exception: ") + ex.what());
              jsErrorHandler->handleError(jsiRuntime, error, true);
            }
```

**两个 `catch` 都在 `RuntimeExecutor` 的最内层**，覆盖所有投递给 JS 线程的任务。

| 捕获类型 | 包装方式 | `isFatal` |
| --- | --- | --- |
| `jsi::JSError` | 原始错误 | `true` |
| `std::exception` | 包成 `"Non-JS exception: " + what()` | `true` |

**这里无条件传 `isFatal = true`** —— 意味着任何逃逸到执行器边界的异常都被视为致命错误。
非致命的 JS 异常（如 `console.error` 路径、React 错误边界捕获的 render 错误）
由更上层的 `RN$handleException` 以 `isFatal=false` 传入，不会走到这里。

注意 `RuntimeExecutor` 用 `weak_ptr` 捕获 runtime / timerManager / jsThread
（`ReactInstance.cpp:80-83`），**实例销毁后任务直接丢弃**，不执行也不报错：

```cpp
        if (weakRuntime.expired()) {
          return;
        }
```

### 2.2 JS 主动调用的 8 个全局

`ReactInstance::initializeRuntime`（`ReactInstance.cpp:~415-650`）通过
`defineReadOnlyGlobal` 注入一组 `RN$*` 全局。这是 JS 侧与 C++ 错误处理通信的全部接口：

| 全局 | 行号 | 作用 |
| --- | --- | --- |
| `RN$Bridgeless` | `:421` | 是否为 Bridgeless 模式（常量 `true`） |
| `RN$DiagnosticFlags` | `:430` | 诊断开关串（受 `isProfiling` 控制） |
| `RN$useAlwaysAvailableJSErrorHandling` | `:463` | Feature Flag 镜像 |
| `RN$isRuntimeReady` | `:469` | 查询 `jsErrorHandler->isRuntimeReady()` |
| `RN$hasHandledFatalException` | `:484` | 是否已处理过致命错误（用于去重） |
| `RN$notifyOfFatalException` | `:499` | 主动标记「已处理致命错误」 |
| `RN$inExceptionHandler` | `:515` | 当前是否正在错误处理器内（防重入） |
| `RN$handleException` | `:531` | **主入口**：JS 把错误交给 C++ |
| `RN$registerExceptionListener` | `:572` | 注册错误监听器 |
| `RN$registerCallableModule` | `:613` | 注册可被原生调用的 JS 模块 |

**全部用 `defineReadOnlyGlobal`** —— JS 侧无法覆写这些全局，App 也就无法意外劫持错误通道。

### 2.3 `RN$handleException` 的早退分支

`ReactInstance.cpp:539-553`：

```cpp
              if (count < 2) {
                throw jsi::JSError(
                    runtime,
                    "handleException requires 3 arguments: error, isFatal, logToConsole (optional)");
              }

              auto isFatal = isTruthy(runtime, args[1]);

              if (!ReactNativeFeatureFlags::
                      useAlwaysAvailableJSErrorHandling()) {
                if (jsErrorHandler->isRuntimeReady()) {
                  return jsi::Value(false);
                }
              }
```

**注意这个双重否定**：`useAlwaysAvailableJSErrorHandling` 关闭 **且** 运行时已就绪
→ 直接 `return false`，**C++ 侧什么都不做**。

其含义是：Feature Flag 关闭时，**错误处理完全交给 JS 管线**
（`ExceptionsManager.js` 一路走 `LogBox` / `console.error`），C++ 侧主动让路。
`return false` 是给 JS 的信号：「C++ 没处理，你自己处理」。

源码在 `:528` 上方有一条 TODO：

```cpp
    // TODO(T196834299): We should really use a C++ turbomodule for this
```

**已知技术债**：`RN$handleException` 应该是 TurboModule 而非全局 HostFunction。

## 3. `JsErrorHandler::handleError`：两条管线

`jserrorhandler/JsErrorHandler.cpp:229-254`：

```cpp
void JsErrorHandler::handleError(
    jsi::Runtime& runtime,
    jsi::JSError& error,
    bool isFatal,
    bool logToConsole) {
  // TODO: Current error parsing works and is stable. Can investigate using
  // REGEX_HERMES to get additional Hermes data, though it requires JS setup

  if (!ReactNativeFeatureFlags::useAlwaysAvailableJSErrorHandling() &&
      _isRuntimeReady) {
    try {
      handleJSError(runtime, error, isFatal);
      return;
    } catch (jsi::JSError& ex) {
      logErrorWhileReporting(
          "handleError(): Error raised while reporting using js pipeline. Using c++ pipeline instead.",
          ex,
          error);

      // Re-try reporting using the c++ pipeline
      _hasHandledFatalError = false;
    }
  }

  handleErrorWithCppPipeline(runtime, error, isFatal, logToConsole);
}
```

**决策表**（`_isRuntimeReady` 是 `_` 成员，`:64` 声明）：

| `useAlwaysAvailableJSErrorHandling` | `_isRuntimeReady` | 走哪条 |
| --- | --- | --- |
| `false` | `true` | 先试 **JS 管线**；抛异常则回退 C++ 管线 |
| `false` | `false` | **C++ 管线**（JS 侧还没准备好） |
| `true` | 任意 | **C++ 管线**（Always Available = 永远走 C++） |

### 3.1 致命错误的去重

`:396-401`：

```cpp
    if (isFatal) {
      if (_hasHandledFatalError) {
        return;
      }
      _hasHandledFatalError = true;
    }
```

**第一个致命错误上报后，后续致命错误全部静默丢弃。**

回退时特意把它清零（`:249`）：

```cpp
      // Re-try reporting using the c++ pipeline
      _hasHandledFatalError = false;
```

因为 JS 管线「处理了」但实际抛异常了，不清零会导致 C++ 管线也跳过 —— **错误彻底丢失**。

这是一处**正确且微妙**的处理：去重标志必须与「谁真正处理了」保持一致。

`notifyOfFatalError()`（`:424-426`）是给 JS 的手动置位接口：

```cpp
void JsErrorHandler::notifyOfFatalError() {
  _hasHandledFatalError = true;
}
```

**若 App 的 JS 代码误调用 `RN$notifyOfFatalException()`，后续所有致命错误都会被吞掉。**
框架不校验调用者身份。

### 3.2 运行时未就绪时的消息前缀

`:328-330`：

```cpp
  ProcessedError processedError = {
      .message =
          _isRuntimeReady ? message : ("[runtime not ready]: " + message),
```

**唯一的降级信息就是给消息加一个前缀。** 没有单独的 `isRuntimeReady` 字段、
没有「错误发生在启动早期」的结构化标记。

上报方要区分「启动期错误」只能靠字符串匹配 `[runtime not ready]: ` 前缀。
这在 04 文档讨论的日志分类里是一个**易被忽略但对归因很关键**的维度 ——
启动期崩溃与运行期崩溃的根因分布差异很大。

## 4. C++ 管线的结构化过程

`handleErrorWithCppPipeline`（`JsErrorHandler.cpp:256-405`）分五步。

### 4.1 重入保护

`:261-262`：

```cpp
  *_inErrorHandler = true;
  SetFalseOnDestruct temp{_inErrorHandler};
```

`_inErrorHandler` 是 `std::shared_ptr<bool>`（`:64`），`SetFalseOnDestruct` 保证
**即使中途抛异常也会复位**。这正是 `RN$inExceptionHandler`（`ReactInstance.cpp:515`）查询的值。

> **为什么要 shared_ptr 而不是普通 bool？** 因为 `inErrorHandler()` 可能在
> 错误处理器尚未返回时被另一个线程查询。用 `shared_ptr` 拷贝一份所有权，
> 避免数据竞争。`JsErrorHandler.h:64` 的类型选择本身就是并发设计。

### 4.2 字段提取

`:264-278`：

```cpp
  auto message = error.getMessage();
  auto errorObj = wrapInErrorIfNecessary(runtime, error.value());
  auto componentStackValue = errorObj.getProperty(runtime, "componentStack");
  if (!isLooselyNull(componentStackValue)) {
    message += "\n" + stringifyToCpp(runtime, componentStackValue);
  }

  auto nameValue = errorObj.getProperty(runtime, "name");
  auto name = (isLooselyNull(nameValue) || isEqualTo(runtime, nameValue, ""))
      ? std::nullopt
      : std::optional(stringifyToCpp(runtime, nameValue));

  if (name && !message.starts_with(*name + ": ")) {
    message = *name + ": " + message;
  }
```

**`componentStack` 被拼进 message**（而不是单独字段），且 `name` 有去重前缀逻辑
（避免 `"Error: Error: xxx"`）。原始 message 单独存在 `originalMessage`（`:315-317`）。

### 4.3 extraData 组装

`:280-313` 收集 6 类附加数据：

| 属性 | 来源 | 用途 |
| --- | --- | --- |
| `RN$ErrorExtraDataKey` | 错误对象上的自定义键 | 上报方自定义扩展位 |
| `jsEngine` | `errorObj.jsEngine` | 引擎标识（Hermes / JSC） |
| `rawStack` | `error.getStack()` | 未解析的原始栈 |
| `__DEV__` | `global().__DEV__` | 区分开发/生产 |
| `bundleMetadata` | `getBundleMetadata(runtime, error)` | 定位 bundle 版本 |
| `cause.*` | `errorObj.cause` | 仅转发 3 个栈字段 |

`cause` 的转发有明确取舍（`:301-302`）：

```cpp
    // TODO: Consider just forwarding all properties. For now, just forward the
    // stack properties to maintain symmetry with js pipeline
```

**只转发 `stackSymbols` / `stackReturnAddresses` / `stackElements`**，不转发 `cause` 的其他属性。
注释说明是为了「与 JS 管线保持对称」—— 两条管线的输出结构必须一致，
否则按管线分类的统计会失真。

### 4.4 栈解析

`:323-324`：

```cpp
  auto isHermes = runtime.global().hasProperty(runtime, "HermesInternal");
  auto stackFrames = StackTraceParser::parse(isHermes, error.getStack());
```

**通过 `global.HermesInternal` 是否存在来探测引擎**，而不是问 JSI 层。
栈被解析为 `ProcessedError::StackFrame` 结构（`JsErrorHandler.h:21-27`）：

```cpp
    struct StackFrame {
      std::optional<std::string> file;
      std::string methodName;
      std::optional<int> lineNumber;
      std::optional<int> column;
```

除 `methodName` 外**全部是 `optional`** —— Hermes 栈、source map 后的栈、
内联栈都可能缺字段。

### 4.5 分发与 `preventDefault`

`:361-390`：

```cpp
  // packages/react-native/ReactCommon/jserrorhandler/JsErrorHandler.cpp:361-390
  std::shared_ptr<bool> shouldPreventDefault = std::make_shared<bool>(false);
  auto preventDefault = jsi::Function::createFromHostFunction(
      runtime,
      jsi::PropNameID::forAscii(runtime, "preventDefault"),
      0,
      [shouldPreventDefault](...) {
        *shouldPreventDefault = true;
        return jsi::Value::undefined();
      });

  data.setProperty(runtime, "preventDefault", preventDefault);

  for (auto& errorListener : _errorListeners) {
    try {
      errorListener(runtime, jsi::Value(runtime, data));
    } catch (jsi::JSError& ex) {
      logErrorWhileReporting(
          "handleErrorWithCppPipeline(): Error raised inside an error listener. Executing next listener.",
          ex,
          error);
    }
  }

  if (*shouldPreventDefault) {
    return;
  }
```

**`preventDefault` 让监听器可以吞掉默认上报。** 三个关键点：

1. **每个监听器独立 try/catch** —— 一个监听器抛异常不影响其余（`:378-385`）
2. **监听器是同步调用的**（`:379`），在错误处理器栈内
3. **`shouldPreventDefault` 用 `shared_ptr` 共享** —— 因为它是 JS 侧可调用的闭包，
   C++ 侧要在调用后读回结果

`registerErrorListener`（`:407-410`）只 push，**没有移除接口**：

```cpp
void JsErrorHandler::registerErrorListener(
    const std::function<void(jsi::Runtime&, jsi::Value)>& errorListener) {
  _errorListeners.push_back(errorListener);
}
```

而 `RN$registerExceptionListener`（`ReactInstance.cpp:572-608`）内部用
**弱指针**捕获 JS 函数：

```cpp
              jsErrorHandler->registerErrorListener(
                  [weakErrorListener = std::weak_ptr<jsi::Function>(
                       errorListener)](jsi::Runtime& runtime, jsi::Value data) {
                    if (auto strongErrorListener = weakErrorListener.lock()) {
                      strongErrorListener->call(runtime, data);
                    }
                  });
```

**两层防护**：
- C++ 侧的 `std::function` 列表只增不减（小幅泄漏：每个已 GC 的监听器留一个空壳）
- 但 `weak_ptr` 保证 **JS 函数被 GC 后不会被调用**，也不会崩溃

> **这与 09 文档 §3 的 RSNRU 是同一个设计模式**：
> `std::shared_ptr` 存壳 + `std::weak_ptr` 指向真实对象。
> RN 里凡是「JS 与 C++ 交叉引用」的地方都在用这个模式。

### 4.6 最终分流

`:392-404`：

```cpp
  // packages/react-native/ReactCommon/jserrorhandler/JsErrorHandler.cpp:392-404
  auto errorType = errorObj.getProperty(runtime, "type");
  auto isWarn = isEqualTo(runtime, errorType, "warn");

  if (isFatal || !isWarn) {
    if (isFatal) {
      if (_hasHandledFatalError) {
        return;
      }
      _hasHandledFatalError = true;
    }

    _onJsError(runtime, processedError);
  }
```

**`type === "warn"` 的错误（且非致命）不会走到 `_onJsError`** —— 只通知监听器。

| 条件 | 是否调用 `_onJsError` |
| --- | --- |
| `isFatal == true` | ✅（去重后仅第一次） |
| `isFatal == false` 且 `type != "warn"` | ✅ |
| `isFatal == false` 且 `type == "warn"` | ❌ 仅监听器可见 |
| 任何监听器调用了 `preventDefault()` | ❌ 直接 return |

**这是上报方能收到的全部错误**，其余都止步于监听器。

## 5. `_isRuntimeReady` 的设置时机

`setRuntimeReady()`（`jserrorhandler/JsErrorHandler.cpp:416-418`）：

```cpp
void JsErrorHandler::setRuntimeReady() {
  _isRuntimeReady = true;
}
```

**唯一调用点**在 `ReactInstance.cpp:296-303` —— 恰好在 JS bundle 求值**之后**：

```cpp
        /**
         * TODO(T183610671): We need a safe/reliable way to enable the js
         * pipeline from javascript. Remove this after we figure that out, or
         * after we just remove the js pipeline.
         */
        if (!jsErrorHandler->hasHandledFatalError()) {
          jsErrorHandler->setRuntimeReady();
        }
```

### 5.1 「ready」的真实含义

`_isRuntimeReady` 由四个条件共同决定：

| 条件 | 依据 |
| --- | --- |
| JS bundle 已 `evaluateJavaScript` 完成 | `ReactInstance.cpp:293` 之后 |
| **且** 此前没有处理过致命错误 | `ReactInstance.cpp:301` 的 `!hasHandledFatalError()` |
| **且** 同一时刻调用 `setRuntimeReady` | 唯一写点 `JsErrorHandler.cpp:417` |

**「runtime ready」= 「bundle 跑完且没崩」**，而不是「JS 侧通知可以用了」。

这带来一个重要后果：**如果 bundle 执行期间发生了致命错误，`_isRuntimeReady` 永远是 `false`。**
此后所有错误都会被打上 `[runtime not ready]: ` 前缀（§3.2），
并全部走 C++ 管线而非 JS 管线。

对上报方而言这其实是有利的归因信号：**带此前缀的错误 = 启动期错误**。

### 5.2 两条 TODO 说明这是一段未收敛的设计

`ReactInstance.cpp:296-300` 的 TODO（T183610671）直说：

> We need a safe/reliable way to enable the js pipeline from javascript.
> Remove this after we figure that out, or after we just remove the js pipeline.

**"or after we just remove the js pipeline"** —— 维护者自己都不确定 JS 管线会不会长期存在。
配合 `ReactInstance.cpp:528` 的另一条 TODO（T196834299，`RN$handleException` 应改为 TurboModule），
说明这套「双管线 + 全局函数」的错误处理是**过渡形态**。

## 6. 本模块的设计要点

| 设计 | 收益 | 代价 / 风险 |
| --- | --- | --- |
| 上报端由宿主注入 | 框架零网络依赖，可完全离线运行 | 框架无法保证「启动期错误也被上报」 |
| 双管线 + C++ 兜底 | 任一管线故障都不丢错误 | 输出结构必须人工保持对称 |
| 致命错误去重 | 防止一个错误触发上百次上报 | `notifyOfFatalError` 可被 JS 误用吞掉后续全部 |
| 监听器弱引用 | JS 函数被 GC 后不崩溃、不泄漏 | C++ 侧 `std::function` 列表仍只增不减 |
| 监听器独立 try/catch | 单个坏监听器不阻断其他 | 监听器内的错误只记日志不上报 |
| `preventDefault` | App 可接管上报策略 | 可静默吞掉所有错误 |
| `_inErrorHandler` 用 `shared_ptr<bool>` | 跨线程可读、无数据竞争 | 语义上仍是裸 bool 的原子性假设 |
| 栈帧字段大量 `optional` | 兼容不同引擎/source map | 上报方必须处理缺失 |
| 「运行期未就绪」仅靠消息前缀 | 实现简单 | 无法结构化筛选，只能字符串匹配 |

## 7. 已发现的问题

| 编号 | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| RT-1 | `registerErrorListener` 无移除接口 | `jserrorhandler/JsErrorHandler.cpp:407-410` | 每次热重载/重新初始化都新增一个监听器，`_errorListeners` 单调增长 |
| RT-2 | `notifyOfFatalError()` 可被任意 JS 调用 | `jserrorhandler/JsErrorHandler.cpp:424-426`、`ReactInstance.cpp:499` | 误调用会让后续所有致命错误被静默丢弃 |
| RT-3 | 「runtime not ready」仅是消息前缀 | `jserrorhandler/JsErrorHandler.cpp:328-330` | 启动期/运行期错误无法结构化区分，影响归因统计 |
| RT-4 | `handleException` 早退依赖 Feature Flag | `ReactInstance.cpp:549-553` | Flag 关闭且运行时已就绪时，C++ 侧完全不参与错误处理 |
| RT-5 | `RN$handleException` 应为 TurboModule 而非全局 | `ReactInstance.cpp:528`（TODO T196834299） | 已知技术债；全局 HostFunction 无法按模块治理 |
| RT-6 | `RuntimeExecutor` 把所有逃逸异常标记为 fatal | `ReactInstance.cpp:102-108` | 非致命的原生异常也会进入致命错误通道，可能触发「首个致命错误」去重而丢失后续 |
| RT-7 | `cause` 只转发 3 个字段 | `jserrorhandler/JsErrorHandler.cpp:301-312` | 上报方拿不到 `cause` 的自定义属性 |
| RT-8 | bundle 执行期崩溃后 `_isRuntimeReady` 永远为 `false` | `ReactInstance.cpp:301-303` | 后续错误被永久标记为「runtime not ready」，误判为启动期 |

RT-2 与 04 文档讨论的「RN 不做崩溃上传」是同一个结构性事实的两面：
**框架把最终决定权交给宿主，代价是宿主可以静默丢弃所有错误而框架无从知晓。**
