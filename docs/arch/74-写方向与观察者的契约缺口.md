## 2. 【核心 NNN-1】写方向：`header_.count` 会回绕

### 2.1 计数字段的类型

```cpp
// packages/react-native/ReactCommon/react/renderer/mapbuffer/MapBuffer.h:79-81
  struct Header {
    uint16_t count; // amount of items in the map
  };
```

**`count` 是 `uint16_t` → 最大 65535。**

### 2.2 写入时无上限检查

```cpp
// packages/react-native/ReactCommon/react/renderer/mapbuffer/MapBufferBuilder.cpp:50-52
  buckets_.emplace_back(key, static_cast<uint16_t>(type), data);

  header_.count++;
```

**`header_.count++` 没有任何上限检查。**

### 2.3 与 64 文档 DDD-3 构成**同一问题的两端**

| | 64 文档 DDD-3（读方向） | 本文 NNN-1（写方向） |
| --- | --- | --- |
| **问题** | `count_` 与 `bytes_.size()` **不交叉校验** | `count` **会回绕** |
| **触发** | 收到一个 `count` 与实际长度不符的 buffer | **写入超过 65535 个条目** |
| **后果** | 二分查找 `hi = count_ - 1` 越界读 | **写出的 buffer 的 `count` 与实际 bucket 数不符** → **读方向的 `hi = count_ - 1` 用错上界** → **越界读** |
| **合并后果** | **写侧回绕 → 读侧越界** | 同 |

**即：一个「写超过 65535 个条目」的 MapBuffer，会让**读**它的代码越界读。**

### 2.4 触发条件的现实性

| 项 | 评估 |
| --- | --- |
| `MapBuffer::Key` 也是 `uint16_t` | **key 空间只有 65536 个** |
| 一个 MapBuffer 装 65535 个条目 | 需要 65535 个**不同的** key（因为 key 空间只有 65536）—— **理论可达** |
| 现实中的 MapBuffer | 通常装几十个属性 —— **实际不可达** |
| **是否有防御** | ❌ 无 |

**判定：结构脆弱（理论可达、实际不可达、无防御）。**

### 2.5 写方向的**另一个**硬限制：超限时 `abort()`

```cpp
// packages/react-native/ReactCommon/react/renderer/mapbuffer/MapBufferBuilder.cpp:40-44
  if (valueSize > MAX_BUCKET_VALUE_SIZE) {
    LOG(ERROR) << "Error: size of value must be <= MAX_VALUE_SIZE. ValueSize: "
               << valueSize;
    abort();
  }
```

**`MAX_BUCKET_VALUE_SIZE = sizeof(uint64_t)`**（`:16`）= 8 字节。

| 特征 | 评价 |
| --- | --- |
| **有检查** ✓ | 与读方向的无检查形成对照 |
| **但失败方式是 `abort()`** | **进程立即终止** —— 不是抛异常、不是返回错误码 |
| **与 65 文档 EEE-2 对照** | 那里 `std::stoi` 抛未捕获异常；**这里是直接 abort** —— **都不会被调用方处理** |
| **`LOG(ERROR)` 的措辞与常量名不符** | 消息里写 `MAX_VALUE_SIZE`，常量名却是 `MAX_BUCKET_VALUE_SIZE` |

**即：写方向的「值太大」会导致进程死掉，且错误消息里的常量名是错的。**

## 3. 【核心 NNN-2】写方向不检查重复 key

### 3.1 明确的 TODO

```cpp
// packages/react-native/ReactCommon/react/renderer/mapbuffer/MapBufferBuilder.cpp:217
  // TODO(T83483191): add pass to check for duplicates
```

**即：重复 key 不被检测 —— TODO 明确承认。**

### 3.2 重复 key 对读方向的后果

**写方向**：`storeKeyValue` 无条件 `buckets_.emplace_back(key, ...)` → **同一个 key 可以出现多次**。

**读方向**（64 文档 DDD-3 的二分查找）：

```cpp
// packages/react-native/ReactCommon/react/renderer/mapbuffer/MapBuffer.cpp:78-89
    Key midVal = readUnaligned<Key>(bytes_.data(), bucketOffset(mid));

    if (midVal < key) {
      lo = mid + 1;
    } else if (midVal > key) {
      hi = mid - 1;
    } else {
      return mid;      // ← 找到第一个匹配就返回
    }
```

| 情况 | 后果 |
| --- | --- |
| 重复 key 且**值相同** | 无害 |
| **重复 key 且值不同** | **二分查找返回其中一个（不保证是最后写入的）** → **静默取到错误的值** |

**即：`putInt(key, 1)` 后 `putInt(key, 2)` → `getInt(key)` 的结果**取决于二分查找的路径**，**不保证是 2**。

**这是「同一 key 多次写入」这一 API 用法的正确性缺口** —— 且**没有任何警告**。

### 3.3 与 64 文档 DDD-3 的对照：两个方向的「信任假设」各有一个缺口

| | 缺口 | 后果 |
| --- | --- | --- |
| **读方向**（64 文档） | `count_` 不与实际长度交叉校验 | 越界读 |
| **写方向**（本文） | 重复 key 不检测 | **静默取到错误的值**（不是崩溃，更难发现） |

**即：MapBuffer 的「信任模型」在两端各漏了一块。**

## 4. 【核心 NNN-3】`PerformanceObserver` 的三个成员无锁保护

### 4.1 成员的线程安全现状

| 成员 | 声明 | 保护 |
| --- | --- | --- |
| `registry_`（引用） | `PerformanceObserverRegistry &registry_;` | ✅ registry 内部有 `observersMutex_`（66 文档） |
| `callback_` | `PerformanceObserverCallback callback_;` | ✅ 只在构造时赋值 |
| **`observedTypes_`** | `PerformanceObserverEntryTypeFilter observedTypes_;` | ❌ **无锁** |
| **`durationThreshold_`** | `HighResDuration durationThreshold_ = DEFAULT_DURATION_THRESHOLD;` | ❌ **无锁** |
| `buffer_` | `std::vector<PerformanceEntry> buffer_;` | ✅ `bufferMutex_` |
| **`requiresDroppedEntries_`** | `bool requiresDroppedEntries_ = false;` | ❌ **无锁** |
| `didScheduleFlushBuffer_` | `bool didScheduleFlushBuffer_ = false;` | ✅ `bufferMutex_` |

**即：7 个成员里 4 个有保护、3 个没有。**

### 4.2 无锁成员的具体竞态

**`observedTypes_`（`std::unordered_set`）**：

```cpp
      [](const auto& entryData) { return entryData.entryType; }, entry);

  if (observedTypes_.contains(entryType)) {
```

**读**在 `bufferMutex_` **之外**（锁在 `:29` 才取），
**写**在 `observe()` 里（`:50`、`:66`）也**无锁**。

| 触发 | 后果 |
| --- | --- |
| JS 线程调 `observe()` 同时渲染线程推 entry | **`std::unordered_set` 的并发读写 → UB**（可能崩溃、可能读到半构造的桶） |
| **实际严重性** | `observe()` 通常只在 observer 创建后调用一次，但 `observe` 是 public 的、可重复调用 |

**`requiresDroppedEntries_`（`bool`）**：`takeRecords` 写（`:37`）、`observe` 写（`:68`）、`getDroppedEntriesCount` 读+写（`:74`、`:86`）—— **全部无锁**。

**`durationThreshold_`（标量）**：`handleEntry` 读（`:22`）、`observe` 写（`:52`）—— 无锁。**标量撕裂风险低，但仍是 UB。**

### 4.3 正确的一处：`scheduleFlushBuffer` 的锁外回调

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.cpp:94-107
void PerformanceObserver::scheduleFlushBuffer() {
  bool shouldSchedule = false;
  {
    std::lock_guard lock(bufferMutex_);
    if (!didScheduleFlushBuffer_) {
      didScheduleFlushBuffer_ = true;
      shouldSchedule = true;
    }
  }

  if (shouldSchedule) {
    callback_();
  }
}
```

**✓ 正确** —— 标志位在锁内改、**回调在锁外调**（避免回调重入 `takeRecords` 造成死锁）。
**这与 69 文档 III-1 的「解锁 → 回调 → 重锁」是同一模式** ✓。

### 4.4 与 69 文档 III-1 的对照

| | 69 文档 III-1 | 本文 NNN-3 |
| --- | --- | --- |
| **形态** | 写路径**没有**独占锁 | **锁存在但没覆盖全部成员** |
| **危险** | 共享锁下写 `unordered_map` | **无锁下读/写 `unordered_set`** |
| **可观测性** | 静默 | 静默 |

**即：69 文档是「该加锁没加」，本文是「加了锁但漏了三个成员」** —— **后者更难发现，因为「这个类有锁」会给人虚假的安全感。**

## 5. 【核心 NNN-4】两个 `observe` 重载语义不一致，且与注释矛盾

### 5.1 两个重载的逐字对照

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.cpp:47-53
void PerformanceObserver::observe(
    PerformanceEntryType type,
    PerformanceObserverObserveSingleOptions options) {
  observedTypes_.insert(type);

  durationThreshold_ = options.durationThreshold;
```

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.cpp:63-68
void PerformanceObserver::observe(
    std::unordered_set<PerformanceEntryType> types) {
  observedTypes_ = std::move(types);
  requiresDroppedEntries_ = false;
  registry_.addObserver(shared_from_this());
}
```

| | 单类型重载 | 多类型重载 |
| --- | --- | --- |
| **`observedTypes_`** | **`insert(type)`（累加）** | **`= std::move(types)`（整体替换）** |
| **`durationThreshold_`** | **`= options.durationThreshold`（覆盖）** | 不改（保留原值） |
| **`requiresDroppedEntries_`** | 不改 | **置 false** |
| `registry_.addObserver` | ✓ | ✓ |

### 5.2 注释说的是「重置」

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.h:94-99
  /**
   * Configures the observer to watch for specified entry type.
   *
   * This operation resets and overrides previous configurations. So consecutive
   * calls to this methods remove any previous watch configuration (as per
   * spec).
   */
  void observe(PerformanceEntryType type, PerformanceObserverObserveSingleOptions options = {});
```

**注释明说：「resets and overrides previous configurations … consecutive calls … remove any previous watch configuration (as per spec)」**

**但单类型重载的实现是 `insert`（累加），不是重置。**

### 5.3 实际行为后果

| 调用序列 | 注释声称 | 实际 |
| --- | --- | --- |
| `observe(A, {threshold: 100})` | 观察 A | 观察 A，阈值 100 ✓ |
| `observe(B, {threshold: 200})` | **只观察 B**，阈值 200 | **观察 A 和 B**，阈值 **200** |

**即：第二次调用后，**A 类事件也开始用 200 的阈值过滤** —— 而按 spec，A 类的阈值应该是 100。**

**即：`durationThreshold_` 是「整个 observer 一个值」，而 spec 的语义是「每个 entry type 一个值」。**

**这是 Web Performance Timeline spec 与实现的偏差**，且**注释自称符合 spec**。

### 5.4 判定

| 项 | 判定 |
| --- | --- |
| **注释与实现矛盾** | ✅ **确定**（注释说 reset，实现是 insert） |
| **与 spec 不符** | ✅ **确定**（spec 允许多类型各自阈值） |
| **实际影响** | **多类型观察时阈值被意外共享** —— 事件被过早过滤（`duration < durationThreshold_` 时 skip，`:22-26`） |
| **是否可触发** | ✅ JS 侧可连续调 `observe()` |

### 6.3 完整的四层传导链

```
hash<AttributedString>            （逐位）
  └─ hash_combine(fragment)  →  hash<Fragment>    （逐位）
       └─ hash_combine(textAttributes)  →  hash<TextAttributes>   （逐位）✗
```

**且传导方向是「逐位侧在上、容差侧在下」** —— **越往上层越明显**（因为每一层都把下层的冲突继承下来）。

### 6.4 后果与 63 文档 §3.5 完全一致

| 项 | 结果 |
| --- | --- |
| 「容差内相等但位模式不同」的两个 `TextAttributes` | **`==` 为真、`hash` 不同** |
| 放进 `unordered_map`/`unordered_set` | **落在不同桶 → 永远查不到彼此** |
| **在 `AttributedString` 层的表现** | **两个内容「相等」的富文本对象，在哈希容器里是两个不同的 key** |

### 6.5 一个正面对照：`isContentEqual` 的字段集

```cpp
// packages/react-native/ReactCommon/react/renderer/attributedstring/AttributedString.cpp:45-48

      std::tie(rhs.string, rhs.textAttributes);
```

**它只比 2 个字段（忽略 layout），且不被任何 hash 使用** → **不构成契约问题** ✓。

**即：三个比较函数（`operator==` / `isContentEqual` / `hash`）的字段集是**分层清晰**的** ——
`operator==` 与 `hash` 严格配对 ✓，`isContentEqual` 是另一个语义（忽略 layout）**。

## 7. 附带发现：observer 的 buffer 与 reporter 的无界缓冲**双份存储**

### 7.1 两条存储路径

| 路径 | 容器 | 生命周期 |
| --- | --- | --- |
| **reporter 侧** | `markBuffer_` / `measureBuffer_`（`PerformanceEntryKeyedBuffer`） | **无上限、无淘汰**（66 文档 FFF-1） |
| **observer 侧** | `PerformanceObserver::buffer_`（`std::vector`） | `takeRecords()` 时 `swap` 清空 ✓ |

### 7.2 同一批 entry 被存了两份

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.cpp:28-31
    {
      std::lock_guard lock(bufferMutex_);
      buffer_.push_back(entry);
    }
```

**observer 把 reporter 已经存下的 entry 又存了一份**（`shared_ptr` 共享，但 `PerformanceEntry` 是**按值**的 `variant`）。

**即：每个被观察到的 entry，内存里存在两份 `PerformanceEntry`**（一份在 reporter 的 keyed 缓冲、一份在 observer 的 vector）。

**缓解**：`takeRecords()` 会清空 observer 侧 ✓ —— **但 reporter 侧那份永远不清**（66 文档 FFF-1）。

### 7.3 `getDroppedEntriesCount` 的「call time 快照」语义与 66 文档 FFF-2 闭环

```cpp
// packages/react-native/ReactCommon/react/performance/timeline/PerformanceObserver.cpp:71-89
uint32_t PerformanceObserver::getDroppedEntriesCount() noexcept {
  uint32_t droppedEntriesCount = 0;

  if (requiresDroppedEntries_) {
    auto reporter = PerformanceEntryReporter::getInstance();

    for (auto& entryType : observedTypes_) {
      droppedEntriesCount += reporter->getDroppedEntriesCount(entryType);
    }

    requiresDroppedEntries_ = false;
  }

  return droppedEntriesCount;
}
```

| 事实 | 说明 |
| --- | --- |
| **它是「call time 快照」** | 头注释明说 `counted at call time`（`PerformanceObserver.h:117-118`） |
| **它读的是 reporter 的计数** | `reporter->getDroppedEntriesCount(entryType)` |
| **而 reporter 对 MARK/MEASURE 恒返回 0** | 66 文档 FFF-2 |
| **→ observer 对这两类也恒返回 0** | **闭环** |

**即：66 文档的「监控盲区」在 observer 这一层同样存在** —— JS 侧无论从哪个入口问，都得不到 MARK/MEASURE 的丢弃信息。
