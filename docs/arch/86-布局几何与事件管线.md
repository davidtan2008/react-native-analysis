## 2. 布局几何：坐标系、裁剪与命中

### 2.1 LayoutMetrics 有 10 个字段，但哈希和 debug 各漏一部分

`LayoutMetrics` 的字段（`packages/react-native/ReactCommon/react/renderer/core/LayoutMetrics.h:26-42`）一共 10 个：`frame`、`contentInsets`、
`borderWidth`、`displayType`、`positionType`、`layoutDirection`、
`wasLeftAndRightSwapped`、`pointScaleFactor`、`fontSizeMultiplier`、`overflowInset`。

三个「派生几何量」都由 `frame` 减出来，**没有任何 clamp**：

- `getContentFrame()`（`packages/react-native/ReactCommon/react/renderer/core/LayoutMetrics.h:55-64`）= `frame` 减去 `contentInsets` 四边；
- `getOverflowInsetFrame()`（`:67-78`）= `frame` 按 `overflowInset` 向负方向扩边；
- `getPaddingFrame()`（`:83-91`）= `frame` 减去 `borderWidth` 四边。

`contentInsets > frame` 时前两个函数会返回**负尺寸的 Rect**，调用方拿到后不判断就会得到
反向包含关系。`operator==` 是 `= default`（`:92`），比较全部 10 个字段；
`std::hash`（`:117-131`）只合并了 8 个——**漏掉 `positionType` 与
`wasLeftAndRightSwapped`**；`LayoutMetrics.cpp` 的 debug 输出（`:21-61`）只打印 7 项，
**漏掉 `positionType`、`wasLeftAndRightSwapped`、`fontSizeMultiplier`**。

`EmptyLayoutMetrics`（`:100-102`）只有 `frame.size = {-1, -1}`、origin 仍是 `{0,0}`；
它不是「全零」，而是一个宽高为负、可与其他 metrics 判等的「无效值」。注意它没有把
`displayType` 设成 `None`，也没有把 overflowInset 清空。

**GEO-1**：`LayoutMetrics` 有 10 个字段；`std::hash` 漏 2 个（`positionType`、
`wasLeftAndRightSwapped`），`LayoutMetrics.cpp` 的 debug 输出漏 3 个（另加
`fontSizeMultiplier`）；`EmptyLayoutMetrics` 只是 `frame.size={-1,-1}` 的无效值，
三个派生 frame 都是不 clamp 的减法、可能返回负尺寸。

### 2.2 LayoutConstraints：默认上界是 +inf，`min > max` 时 min 赢

```cpp
// packages/react-native/ReactCommon/react/renderer/core/LayoutConstraints.h:23-33
struct LayoutConstraints {
  Size minimumSize{.width = 0, .height = 0};
  Size maximumSize{.width = std::numeric_limits<Float>::infinity(), .height = std::numeric_limits<Float>::infinity()};
  LayoutDirection layoutDirection{LayoutDirection::Undefined};
  Size clamp(const Size &size) const;
};
```

`clamp` 的实现（`LayoutConstraints.cpp:14-23`）是一个逐轴的
`max(min, min(max, size))`。这个组合在 `min > max` 时**没有任何断言或日志**：
`std::min(max, size) ≤ max < min`，于是 `std::max(min, …)` 恒返回 `min`——
即「约束区间非法时，最小尺寸胜出」。`layoutDirection` 不参与 `clamp`，它只被布局引擎
（Yoga）在别的层使用。`operator==`（`packages/react-native/ReactCommon/react/renderer/core/LayoutConstraints.h:35-39`）与 `std::hash`
（`:43-51`）都覆盖全部 3 个字段，**没有** `LayoutMetrics` 那种漏字段问题。

**GEO-2**：`LayoutConstraints` 默认是 `[0,0] → [+inf,+inf]`、方向 `Undefined`；
`clamp` 是逐轴 `max(min, min(max, size))`，`min > max` 时**静默返回 min**；
`layoutDirection` 不参与 clamp；相等与哈希覆盖全部 3 字段。

### 2.3 LayoutContext：`affectedNodes` 是裸指针，比较按地址

`LayoutContext`（`packages/react-native/ReactCommon/react/renderer/core/LayoutContext.h:22-69`）一共 6 个字段：`pointScaleFactor`（默认 1.0）、
`affectedNodes`、`swapLeftAndRightInRTL`（默认 false）、`fontSizeMultiplier`（默认 1.0）、
`viewportOffset`、`viewportSize`。

`affectedNodes` 的类型是 `std::vector<const LayoutableShadowNode *> *`（`:38`），
注释明确写「**Nothing in this collection is owning (on purpose)，调用方自行管理内存**」。
也就是说：布局实现只往调用方给的 vector 里 push 指针，不延长任何节点生命周期；
vector 必须比整个 layout pass 活得久。

`operator==`（`:71-87`）把 `affectedNodes` 的**指针地址**也纳入比较——两个只有
「往哪个表里写」不同的 context 会被判为不相等。如果 context 被用作缓存键，这一条会让
相等判断随栈上 vector 地址变化。

**GEO-3**：`LayoutContext` 6 个字段；`affectedNodes` 是
`std::vector<const LayoutableShadowNode*>*` 裸指针容器（不拥有、不延长生命周期，
必须比 layout pass 活得久）；`operator==` 把该指针地址计入比较，语义是「相同列表」
而不是「相同数值环境」。

### 2.4 同一个 family 的两条快路径：返回节点自己的 frame

`computeLayoutMetricsFromRoot`（`LayoutableShadowNode.cpp:36-53`）和
`computeRelativeLayoutMetrics(family, ancestor)`（`:58-79`）开头都有一个
「descendant 与 reference 是同一个 family」的短路：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/LayoutableShadowNode.cpp:58-79 (节选)
if (&descendantNodeFamily == &ancestorNode.getFamily()) {
  auto layoutMetrics = ancestorNode.getLayoutMetrics();
  if (layoutMetrics.displayType == DisplayType::None) {
    return EmptyLayoutMetrics;
  }
  if (policy.includeTransform) {
    layoutMetrics.frame = layoutMetrics.frame * ancestorNode.getTransform();
  }
  layoutMetrics.frame.origin = {.x = 0, .y = 0};
  return layoutMetrics;
}
```

两条路径只有一处差别：`fromRoot` 版本**不清零 origin**（`:41-52`）——root 的 metrics
就是绝对坐标，清零反而丢信息；`Relative` 版本把 origin 清成 `{0,0}`（`:74`），因为
「相对自己」的 origin 必然是零。共同点是：都以 `displayType == None →
EmptyLayoutMetrics` 短路，且 `includeTransform` 为真时用 `frame * transform` 变换整个
Rect（origin 与 size 一起参与）。

注意 `computeLayoutMetricsFromRoot` 的语义是「以 root 视角算 descendant」，但当两者同
family 时它返回的其实是 **rootNode 自己的 metrics**——调用方传的 descendant 会被忽略。

**GEO-4**：`computeLayoutMetricsFromRoot` 与 `computeRelativeLayoutMetrics` 都有
「同 family → 直接返回该节点自己的 layoutMetrics」的快路径；`displayType == None`
→ `EmptyLayoutMetrics`；`includeTransform` 时 frame 乘自身 transform；Relative 版本
额外把 origin 清零，fromRoot 版本保留原 origin。

### 2.5 全链相对布局：逐层累加 origin、按中心变换、逐层裁剪

真正的相对布局在 `computeRelativeLayoutMetrics(ancestors, policy)`
（`LayoutableShadowNode.cpp:82-199`）。输入是 `getAncestors` 产出的
`AncestorList`（parent + childIndex 的序列），算法分三步：

**Step 1（`:91-119`）**：从 `ancestors.back()` 找到 descender，构造从 descender 到
ancestor 的链（含两端）；沿链向上遇到 `RootNodeKind` 就停，所以跨 root 的测量不会
把 root 之外的节点算进去。

**Step 2（`:123-136`）**：descender 必须能 `dynamic_cast` 成 `LayoutableShadowNode`，
否则返回 `EmptyLayoutMetrics`；初始 metrics 取该节点的 `getLayoutMetrics()`，
origin 清零。

**Step 3（`:138-193`）**：对链上每个节点 `currentShadowNode`：

1. dynamic_cast 失败 → Empty；
2. `displayType == None` → Empty（**祖先**为 None 也会让整个测量变成 Empty）；
3. 最后一层（`i == size-1`，即 ancestor 本身）的 origin 被清零（`:157`）；
4. `shouldApplyTransformation = (policy.includeTransform && !isRootNode) ||
   (policy.includeViewportOffset && isRootNode)`（`:163-165`）——**root 节点默认不应用
   transform**，除非打开 `includeViewportOffset`；
5. `resultFrame.origin += currentFrame.origin`，然后可选用
   `transform.applyWithCenter(resultFrame, currentFrame.getCenter())` 以该节点中心为
   原点做 scale/rotate（`:171-178`）；
6. `i != 0 && includeTransform` 时再加 `getContentOriginOffset(true)`（`:180-186`）。
   这一项单独存在是因为 ScrollView 的 `scrollAwayPaddingTop` 不能算进 transform；
7. 若 `policy.enableOverflowClipping` 且（不是最后一层 或 `clipSpecifiedAncestor`），
   用 `insetBy(currentFrame * transform, overflowInset)` 与 result 求交
   （`:188-196`）；**只有宽和高同时为 0** 才返回 Empty，单边为 0 会继续。

返回值是**被裁剪过**的 `layoutMetrics`：size 可能因 intersect 变小，origin 是全链累加值。

**GEO-5**：全链相对布局从 descender 沿 ancestors 向上、遇 `RootNodeKind` 停止；
逐层累加 `frame.origin`，可选按节点中心 `applyWithCenter`，`i!=0 && includeTransform`
时追加 `contentOriginOffset(true)`；root 默认不应用 transform（除非
`includeViewportOffset`）；`enableOverflowClipping` 时逐层与 overflow 区域求交，
**仅当宽高同时为 0** 才判 Empty；返回值的 size 可能已被裁剪。

### 2.6 measure 的默认实现与「只在克隆上布局」

`measureContent` 与 `measure` 在基类里都有默认实现：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/LayoutableShadowNode.cpp:252-265
Size LayoutableShadowNode::measure(
    const LayoutContext& layoutContext,
    const LayoutConstraints& layoutConstraints) const {
  auto clonedShadowNode = clone({});
  auto& layoutableShadowNode =
      static_cast<LayoutableShadowNode&>(*clonedShadowNode);

  auto localLayoutContext = layoutContext;
  localLayoutContext.affectedNodes = nullptr;

  layoutableShadowNode.layoutTree(localLayoutContext, layoutConstraints);

  return layoutableShadowNode.getLayoutMetrics().frame.size;
}
```

四个要点：

- `measureContent`（`:246-251`）默认 `return {}`——零尺寸；具体布局引擎必须覆盖它；
- `measure` 先 `clone({})`，**在克隆体上跑完整 layoutTree**，只返回 `frame.size`；
  原节点的 `layoutMetrics_` 不会被改，副作用（dirty 标记、Yoga 节点状态）也留在克隆体上；
- 它把 `localLayoutContext.affectedNodes` **强制置 nullptr**（`:260`）——调用方即使传了
  收集列表也收不到任何 affected 节点，measure 路径永远不上报脏节点；
- `baseline` 默认 0（`:267-271`）；`setLayoutMetrics`（`:205-213`）先 `ensureUnsealed()`
  再在 metrics 相等时早退——相等判断用的是 `operator==`（全部 10 字段）。

**GEO-6**：`measureContent` 默认返回零尺寸、`baseline` 默认 0；`measure` 在
`clone({})` 上跑 layoutTree 并只返回 `frame.size`，原节点不被改变；它强制把
`affectedNodes` 置 nullptr，所以 measure 路径永远不会上报 affected 节点。

### 2.7 findNodeAtPoint：z 序反向 + inversion 翻转

`findNodeAtPoint(node, point)`（`LayoutableShadowNode.cpp:273-346`）是触摸命中的唯一
递归入口。判定顺序：

1. `dynamic_cast` 成 `LayoutableShadowNode` 失败 → `nullptr`（`:276-280`）；
2. `canBeTouchTarget()` 与 `canChildrenBeTouchTarget()` **都为 false** → `nullptr`
   （`:282-286`）——两者都关掉的节点整棵子树都不参与命中；
3. 用 `frame * transform` 得到 `transformedFrame` 做包含测试（`:288-291`）；
4. 命中且 **不能**命中子节点（`!canChildrenBeTouchTarget()`）→ 直接返回该节点
   （`:293-294`）；未命中时用 `insetBy(frame, overflowInset)` 扩出 overflow 区域，
   若 point 连 overflow 区域都不在 → `nullptr`（`:295-302`）。也就是说**子节点溢出父节点
   时仍可被命中**，这是 overflow 参与触摸的关键；
5. 若 transform 是垂直/水平 inversion，把 point 绕 `transformedFrame` 的**中心**翻转
   （`:306-325`），使后续子节点坐标与视觉方向一致；
6. `newPoint = point - transformedFrame.origin - getContentOriginOffset(false)`
   （`:327-328`）——content offset 传 **false**，即不把 transform 部分算进去；
7. 取 `getChildren()` 的**副本**，按 `getOrderIndex()` 升序做 `stable_sort`
   （`:331-337`），然后从 `rbegin()` 反向遍历（`:338-343`）——最后绘制（z 最高）的
   孩子最先被测试，第一个命中的直接返回；
8. 所有孩子都没命中时，`canBeTouchTarget() ? node : nullptr`（`:345`）。

**GEO-7**：`findNodeAtPoint` 先 dynamic_cast、再要求至少一个 touch-target 开关为真；
点在 frame 外时允许在 `insetBy(frame, overflowInset)` 内继续递归；inversion 时绕
`transformedFrame` 中心翻转 point；子节点按 `orderIndex` 升序稳定排序后**从 rbegin 反向**
（z 最大优先）递归；`newPoint` 减去 `transformedFrame.origin` 与
`getContentOriginOffset(false)`；未命中任何孩子时返回
`canBeTouchTarget() ? node : nullptr`。

### 2.8 graphicsConversions：Point 不校验未知键，CornerInsets 掉了 return

`graphicsConversions.h` 里四个几何 `fromRawValue` 的容错策略并不一致：

| 目标类型 | 标量分支 | map 分支的未知 key | 数组分支 |
| --- | --- | --- | --- |
| `Point`（`:88-115`） | 无 | **静默忽略**（`:93-100` 只有 x/y 两个 if，没有 else） | `size >= 2` 取前两个；不足 → 清零 + LOG；expect 仅 Debug |
| `Size`（`:117-147`） | 无 | `LOG(ERROR)` + `react_native_expect(false)`（`:127-128`） | `size >= 2`；不足 → 清零 + LOG |
| `EdgeInsets`（`:149-189`） | 数字 → 四边同值（`:151-156`） | LOG + expect（`:169-170`） | `size >= 4`；不足 → 清零 + LOG |
| `CornerInsets`（`:203-246`） | 数字 → 四角同值（`:205-208`） | LOG + expect（`:223-224`） | **见下：赋值后没有 return** |

`CornerInsets` 的向量分支（`:230-239`）在 `array.size() >= 4` 时把四个角写进
`result`，但分支结束后**没有 `return`**，控制流直接落到函数末尾的「错误兜底」
（`:241-244`）：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/graphicsConversions.h:241-244
  // Error case - we should only here if all other supported cases fail
  // In dev we would crash on assert before this point
  result = {.topLeft = 0, .topRight = 0, .bottomLeft = 0, .bottomRight = 0};
  LOG(ERROR) << "Unsupported CornerInsets type";
```

后果是确定的：**任何合法的四元素 CornerInsets 数组都会被清零并打一条
"Unsupported CornerInsets type"**。注释「we should only be here if all other supported
cases fail」对前两个分支（Float / map）成立（它们都有 `return`），对 vector 分支不成立。
另外三个转换器的数组分支也接受**多余元素**（用 `>=` 而不是 `==`），超出部分被丢弃；
`react_native_expect` 在 Release 下不生效，所以「数组长度不是 2/4」只有 LOG 没有中断。

**GEO-8**：`Point` 的 map 分支不校验未知 key（`Size`/`EdgeInsets` 会 LOG + expect）；
四个转换器的数组分支都用 `>= N`（多余元素静默丢弃、短数组清零 + LOG）；
`CornerInsets` 的**向量分支赋值后没有 return**，必然落入 `:241-244` 的无条件清零 +
`LOG(ERROR)`，即合法 4 元素数组永远得到全零。

### 2.9 布局原语与基类接口

`LayoutPrimitives.h` 只有三个枚举（`:21-41`）：

- `DisplayType { None=0, Flex=1, Contents=2, Grid=3 }`；
- `PositionType { Static=0, Relative=1, Absolute=2 }`；
- `LayoutDirection { Undefined=0, LeftToRight=1, RightToLeft=2 }`。

`LayoutableShadowNode`（`packages/react-native/ReactCommon/react/renderer/core/LayoutableShadowNode.h:33`）把接口分成两半：
**必须实现**的纯虚函数是 `layoutTree`（`:86`）、`layout`（`:113`）、`dirtyLayout`
（`:154`）、`getIsLayoutClean`（`:155`）；**带默认实现**的是 `measureContent`（`:93`）、
`measure`（`:100`）、`getTransform`（`:126`，默认 Identity）、`getContentOriginOffset`
（`:136`，默认 `{0,0}`）、`baseline`（`:160`，默认 0）、`canBeTouchTarget`（`:162`，
默认 false）、`canChildrenBeTouchTarget`（`:163`，默认 true）。

`LayoutInspectingPolicy`（`:42-54`）有 4 个 bool：`includeTransform{true}`、
`includeViewportOffset{false}`、`enableOverflowClipping{false}`、
`clipSpecifiedAncestor{true}`——其中最后一个的注释说明 IntersectionObserver 会把它设成
false（先裁到 root 之前，再与 rootMargin 扩大的 root 相交矩形求交）。

**GEO-9**：布局原语是 3 个枚举（DisplayType 4 值 / PositionType 3 值 /
LayoutDirection 3 值）；`LayoutableShadowNode` 的纯虚只有 layoutTree/layout/
dirtyLayout/getIsLayoutClean 四个，measure/measureContent/transform/contentOffset/
baseline/touch-target 都有默认实现；`LayoutInspectingPolicy` 默认
includeTransform=true、includeViewportOffset=false、enableOverflowClipping=false、
clipSpecifiedAncestor=true。

### 3.1 normalizeEventType：三分支字符串变换

```cpp
// packages/react-native/ReactCommon/react/renderer/core/EventEmitter.cpp:19-38
static bool hasPrefix(const std::string& str, const std::string& prefix) {
```

### 3.2 setEnabled：计数器 ±1，但 eventTarget 不会重建


### 3.4 dispatchUniqueEvent 不调用 EventLogger

### 3.5 EventListenerContainer：在 shared_lock 里执行回调

```cpp
// packages/react-native/ReactCommon/react/renderer/core/EventListener.cpp:14-32 (节选)
bool EventListenerContainer::willDispatchEvent(const RawEvent& event) {
  std::shared_lock lock(mutex_);

  bool handled = false;
  for (const auto& listener : eventListeners_) {
    handled = (*listener)(event);
    if (handled) {
      break;
    }
  }
  return handled;
}

void EventListenerContainer::addListener(
    std::shared_ptr<const EventListener> listener) {
  std::unique_lock lock(mutex_);
  eventListeners_.push_back(std::move(listener));
}
```

两个边界：

1. **读锁内跑用户回调**：整个循环都持着 `shared_lock`，回调里如果调用
   `addListener`/`removeListener`（要 `unique_lock`），同一线程会等自己持有的读锁 →
   自死锁。回调里再发事件也会重入 `willDispatchEvent`（`shared_mutex` 非递归，
   但同一线程可重复加共享锁？标准未要求，多数实现会死锁或未定义）。
2. **不拒绝空 listener**：`addListener` 没有 `if (!listener) return`，把空
   `std::function` 放进 vector，下一次 `(*listener)(event)` 直接抛
   `std::bad_function_call`，且异常会穿过 `EventDispatcher::dispatchEvent` 的调用栈。

`removeListener`（`:34-42`）按 `shared_ptr` 相等性查找，删除一个拷贝也有效。

**EVT-5**：`EventListenerContainer::willDispatchEvent` 在 `shared_lock` 内**执行用户
回调**并提前 break；`addListener` 用 `unique_lock` 但不拒绝空 `std::function`
（下次调用抛 `std::bad_function_call`）；在回调内增删 listener 会自死锁。

### 3.6 EventQueue：unique 只回溯到「最近一个同 target」

```cpp
// packages/react-native/ReactCommon/react/renderer/core/EventQueue.cpp:25-57 (节选)
if (rawEvent.isUnique) {
  auto repeatedEvent = eventQueue_.rend();
  for (auto it = eventQueue_.rbegin(); it != eventQueue_.rend(); ++it) {
    if (it->eventTarget == rawEvent.eventTarget) {
      // It is necessary to maintain order of different event types
      // for the same target. ...
      if (it->isUnique && it->type == rawEvent.type) {
        repeatedEvent = it;
      }
      break;                      // ← 遇到第一个同 target 就停
    }
  }
  if (repeatedEvent == eventQueue_.rend()) {
    eventQueue_.push_back(std::move(rawEvent));
  } else {
    *repeatedEvent = std::move(rawEvent);   // ← 原地替换
  }
} else {
  eventQueue_.push_back(std::move(rawEvent));
}
```

去重窗口是「**队尾往回、最近一个同 target 的事件**」：

- 如果最近一个同 target 事件是 unique 且 type 相同 → 原地替换（保持位置）；
- 如果最近一个同 target 事件是别的 type，或不是 unique → `break` 后直接 push_back。
  注释的目的是保留「同 target 不同 type 的先后顺序」：A1、B1 在队列里时再来 A2，
  不能把 A2 排到 B1 前面。
- 因此 unique 事件的去重**不跨类型、也不跨中间插入的其它事件**，重复副本可能堆积
  （例如 A1、B1、A2unique 会产生 A1、B1、A2，而不是合并 A1/A2）。

**EVT-6**：`EventQueue::enqueueEvent` 的 unique 去重从队尾回溯，**遇到第一个同
eventTarget 的条目就 break**；只有该条目同样 unique 且 type 相同才原地替换，否则
push_back。去重不跨类型、不跨中间事件，注释说明这是为保持同 target 不同 type 的
先后顺序。

### 3.7 state 更新只在队尾同 family 时合并

`enqueueStateUpdate`（`EventQueue.cpp:64-83`）对 state 队列只做一种合并：

### 3.11 EventBeat 的 owner 过期路径会卡死后续异步节拍

`induce()`（`EventBeat.cpp:48-93`）是一个三态机：`isEventBeatRequested_`（有请求）、
`isBeatCallbackScheduled_`（已调度一次 beat）、`isSynchronousRequested_`（本次要同步）。
关键代码：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/EventBeat.cpp:59-83 (节选)

  // An asynchronous beat is already scheduled but has not run yet. A
  // synchronous request must not be stranded behind it ...
  if (!isSynchronousRequested_) {
    return;
  }
}
isBeatCallbackScheduled_ = true;

auto beat = std::function<void(jsi::Runtime&)>(
    [this, ownerBox = ownerBox_](jsi::Runtime& runtime) {
      auto owner = ownerBox->owner.lock();
      if (!owner) {
        return;                       // ← 直接返回
      }
      isBeatCallbackScheduled_ = false;

      }

```

owner 过期时 lambda 直接 `return`，**`isBeatCallbackScheduled_` 保持 true**。后果：
之后任何**异步**请求走到 `induce()` 都会在 `:59-66` 被早退（已调度 + 非同步），

会让这个 EventBeat 进入「只响应同步 flush」的退化状态。

另外 `isEventBeatRequested_ = false` 在调度**之前**就置位（`:57`），而
`isBeatCallbackScheduled_ = false` 在回调**执行时**才置位（`:79`）——两个标志的
复位时机不同，前者允许 beat 期间继续累积请求，后者防止重入调度。

**EVT-11**：`EventBeat` 的 beat lambda 在 owner 过期时直接 return，
`isBeatCallbackScheduled_` **不复位**；之后异步请求在 `induce()` 的

能恢复一次；`isEventBeatRequested_` 在调度前置 false，`isBeatCallbackScheduled_`
在回调执行时才置 false。

   `getType()`**。所以 `DynamicPointerEvent::getType()` 继承自 `DynamicEventPayload`，
   返回 `EventPayloadType::ValueFactory`。

后果在 `UIManagerBinding.cpp:80`：`if (eventPayload.getType() ==
EventPayloadType::PointerEvent)` 的 pointer 专用分支（`interceptPointerEvent`）对
JNI 动态 pointer payload **不可达**——它们会走 `:124` 的 `asJSIValue` 通用路径。
只有 C++ 侧 `PointerEvent`（`components/view/PointerEvent.cpp:48` 返回
`EventPayloadType::PointerEvent`）能进那个分支。

**EVT-13**：`DynamicEventPayload::create` 用 `payload.find("pointerId")` 判别 pointer
类型、不做 `isObject()` 检查；`DynamicPointerEvent` 不 override `getType()`，所以动态
pointer payload 的 `getType()` 也返回 `ValueFactory`，导致
`UIManagerBinding.cpp:80` 的 `getType()==PointerEvent` 专用分支不可达，只能走通用的
`asJSIValue` 路径。

### 3.14 extractValue：空容器静默跳过、数组下标 `std::stoi` 无 catch

```cpp
// packages/react-native/ReactCommon/react/renderer/core/DynamicEventPayload.cpp:37-53
std::optional<double> DynamicEventPayload::extractValue(
    const std::vector<std::string>& path) const {
  auto dynamic = payload_;
  for (auto& key : path) {
    auto type = dynamic.type();
    if (type == folly::dynamic::Type::OBJECT && !dynamic.empty()) {
      dynamic = folly::dynamic(dynamic[key]);
    } else if (type == folly::dynamic::Type::ARRAY && !dynamic.empty()) {
      dynamic = folly::dynamic(dynamic[std::stoi(key)]);
    }
  }
  if (dynamic.type() == folly::dynamic::Type::DOUBLE) {
    return dynamic.asDouble();
  } else if (dynamic.type() == folly::dynamic::Type::INT64) {
    return static_cast<double>(dynamic.asInt());
  }
  return std::nullopt;
}
```

这是给「事件驱动原生动画」用的数值提取（`packages/react-native/ReactCommon/react/renderer/core/EventPayload.h:41-47` 的注释：

> Used to extract numeric values from the event payload based on property path
> names as they will exist in JavaScript.

四个边界：

1. 先做 `auto dynamic = payload_` 的**深拷贝**，后续 `dynamic[key]` 只在副本上操作；
2. object/array 的 `!dynamic.empty()` 为 false 时**两个分支都不进**，循环继续但对同一个
   值反复判断——空容器不会报错，只是最终 `nullopt`（静默）；
3. object 缺 key：folly 的 `operator[]` 在非常量副本上会插入 null 再返回引用，下一轮
   `type` 变成 NULL，同样静默到 `nullopt`；
4. array 的 key 直接 `std::stoi(key)`，**没有 try/catch**：非数字路径段会抛
   `std::invalid_argument`，越界数字抛 `std::out_of_range`，两者都会穿过
   `extractValue` 的调用方（EventEmitter 的 extract 链）。

最终只有 `DOUBLE` 与 `INT64` 被接受，`Bool`/`String`/`Null` 一律 `nullopt`。

**EVT-14**：`extractValue` 在 payload **副本**上沿 path 下钻；object/array 为空时
两个分支都跳过、不报错；缺 key 在副本上插 null 后静默到 `nullopt`；数组下标用
`std::stoi` 且无 catch（非数字/越界会抛异常穿出）；只接受 DOUBLE/INT64。

### 3.15 DynamicPointerEvent：hitPath 是可选拷贝

`DynamicPointerEvent`（`DynamicPointerEvent.cpp:14-27`）在构造时读
`payload_["hitPathForEventListener"]`：只有 ARRAY 才初始化
`optional<vector<Tag>>` 并逐项 `item.asInt()` 转成 `Tag`；其它类型保持 `nullopt`。
`getHitPathForEventListener()` 返回 `const optional<vector<Tag>>&`，即从 payload 拷贝
出来的独立一份，不是引用原 dynamic。

两个注意点：`payload_["..."]` 在非常量 `payload_` 上会**插入**缺失的 key（副作用），
`asInt()` 对非 INT64 元素会抛 folly 的 TypeError——错误处理完全交给调用方。
`pointerId` 的存在性由 `DynamicEventPayload::create` 保证（EVT-13），构造函数本身
不重复检查。

**EVT-15**：`DynamicPointerEvent` 构造时只认 `hitPathForEventListener` 为 ARRAY 的
情况，逐项 `asInt()` 填 `optional<vector<Tag>>`（其它类型为 nullopt）；
`getHitPathForEventListener()` 返回拷贝的 const 引用；缺失 key 的 `operator[]` 会在
payload 上插入 null，`asInt()` 对非整数元素抛 TypeError。

### 3.16 ValueFactoryEventPayload：惰性求值，返回 null 可取消事件

`ValueFactory` 只是一个类型别名：`std::function<jsi::Value(jsi::Runtime &)>`
（`packages/react-native/ReactCommon/react/renderer/core/ValueFactory.h:18`）。`ValueFactoryEventPayload`（`.h:17-27`、`.cpp:14-26`）把它
存起来，在 `asJSIValue(runtime)` 时才调用——即**事件真正要发给 JS 的那一刻**才求值：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/ValueFactoryEventPayload.cpp:14-21
ValueFactoryEventPayload::ValueFactoryEventPayload(ValueFactory factory)
    : valueFactory_(std::move(factory)) {}

jsi::Value ValueFactoryEventPayload::asJSIValue(jsi::Runtime& runtime) const {
  return valueFactory_(runtime);
}

EventPayloadType ValueFactoryEventPayload::getType() const {
  return EventPayloadType::ValueFactory;
}
```

这带来两个语义：factory 里抛的 JS 异常会直接打断 dispatch（`UIManagerBinding.cpp:124`
处没有 try/catch）；factory 返回 null 时 `dispatchEventToJS` 会**取消事件**
（`UIManagerBinding.cpp:126-129` 的 `if (payload.isNull()) return;`）。

基类 `EventPayload`（`packages/react-native/ReactCommon/react/renderer/core/EventPayload.h:23-53`）本身很薄：虚析构 + 4 个 default 的
拷贝/移动操作 + 纯虚 `asJSIValue`/`getType` + 默认 `nullopt` 的 `extractValue`。

**EVT-16**：`ValueFactory` 是 `std::function<jsi::Value(jsi::Runtime&)>`；
`ValueFactoryEventPayload` 在 `asJSIValue` 时才惰性调用 factory（异常直接打断
dispatch；返回 null 会被 `UIManagerBinding::dispatchEventToJS` 解释为取消事件）；
`getType` 返回 ValueFactory；`EventPayload` 基类的 4 个特殊成员全 default，
`extractValue` 默认 `nullopt`。

### 3.17 管线协议：EventLogger / EventPipe / ReactEventPriority

`EventLogger.h`（`:20-51`）定义事件计时协议：

- `EventTag = unsigned int`，`EMPTY_EVENT_TAG = 0`（`:20-21`）；
- `onEventStart(name, target, optional timestamp)` 返回本次事件的唯一 tag（`:36-40`）；
- `onEventProcessingStart(tag)` / `onEventProcessingEnd(tag)` 只收发 tag
  （`:45`、`:50`）。这三者就是 Event Timing API 的挂钩，`EventDispatcher` 与
  `EventQueueProcessor` 分别在入队前和处理前后调用（EVT-4/EVT-8 已记录两处调用差异）。

`EventPipe.h`（`:24-32`）是两个函数类型：

```cpp
// packages/react-native/ReactCommon/react/renderer/core/EventPipe.h:24-32
using EventPipe = std::function<void(
    jsi::Runtime &runtime,
    EventTarget *eventTarget,
    const std::string &type,
    ReactEventPriority priority,
    const EventPayload &payload,
    HighResTimeStamp eventTimestamp)>;

using EventPipeConclusion = std::function<void(jsi::Runtime &runtime)>;
```

`EventPipe` 是 6 参（runtime、**裸指针** target、类型、React 优先级、payload 引用、
时间戳）。`EventPipeConclusion` 只收 runtime——`EventQueueProcessor` 每批事件只调
一次（`:127`），用来做「一批事件处理完」的收尾（例如刷新 pointer 相关状态）。

`ReactEventPriority.h`（`:18-45`）是 4 值枚举 `Default/Discrete/Continuous/Idle`，
外加一个 constexpr `serialize()` 转底层整型。注意它和 `RawEvent::Category`（6 值）
是两套不同的枚举：EventQueueProcessor 负责把后者映射成前者（EVT-9）。

**EVT-17**：`EventLogger` 有 3 个纯虚（onEventStart 返回 unsigned tag、
EMPTY_EVENT_TAG=0；processing start/end 只收 tag）；`EventPipe` 是 6 参
`std::function`（target 为裸指针、payload 为 const 引用），`EventPipeConclusion`
只收 runtime 且每批只调一次；`ReactEventPriority` 是 4 值枚举 + constexpr
`serialize()`，与 `RawEvent::Category`（6 值）相互独立、由处理器做映射。
