# 82 · 调度层：两个 RuntimeScheduler 分叉在七处语义相反，以及 SurfaceHandler 的无锁读

> **模块**：A1 · `ReactCommon/react/renderer/scheduler/`（9 个代码文件 / **1,588** 行）
> + `ReactCommon/react/renderer/runtimescheduler/`（17 个 / **2,235** 行）
> = **26 个文件 / 3,823 行**
>
> **基线**：react-native @ `9b131e42`（submodule `react-native/`，本文路径基准 = 该 submodule 根）
>
> **前置**：[09 文档](./09-渲染器核心与差分算法.md) 讲 ShadowTree 的差分；[53 文档](./53-渲染器核心与Yoga的数值边界.md) 讲布局数值。
> 本文讲的是「谁来驱动这些差分」：`Scheduler` 把 UIManager 的回调转给平台，
> `RuntimeScheduler` 决定 JS 任务何时跑、跑完做什么。
>
> 本文记录 **26** 条结论，其中四条是核心：
> ① **【核心】两个 `RuntimeScheduler` 实现在 `scheduleRenderingUpdate` 上语义完全相反** —— Legacy 立即执行、Modern 只入队，而 Modern 的头文件还承诺「未启用时立即执行」；
> ② **【核心】Legacy 的 `getShouldYield()` 完全不看任务队列** —— 它只回答「有没有别的线程在等运行时」，所以排队中的任务不会让 JS 让出；
> ③ **【核心】`SurfaceHandler` 的 `Parameters` 组声称「读只要 shared lock」，却有 4 处读写都在锁外**；
> ④ **【核心】Modern 里一个任务抛错会清空整个队列**，而 Legacy 只上报不清队列。

## 3. 【核心 SCH-1】`SurfaceHandler` 的头文件前后矛盾：一处说「只能移动」，一处把移动也删了

`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:28-39` 的类注释：

> Represents a running React Native surface and provides control over it.
> The instances of this class are movable only.

而同一文件 `:71-77`：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:71-77
  /*
   * Not moveable or copyable
   */
  SurfaceHandler(SurfaceHandler &&other) noexcept = delete;
  SurfaceHandler(const SurfaceHandler &SurfaceHandler) noexcept = delete;
  SurfaceHandler &operator=(SurfaceHandler &&other) noexcept = delete;
  SurfaceHandler &operator=(const SurfaceHandler &other) noexcept = delete;
```

四个特殊成员全 `= delete`，所以**既不可拷贝也不可移动**。注释 `:30` 的「movable only」是旧版本残留（早期版本确实只删了拷贝）。

即使删掉这四行，类也仍然不可移动 —— 两个成员 `mutable std::shared_mutex linkMutex_` / `parametersMutex_`（`:196`、`:202`）本身就不可移动。`SurfaceManager` 因此把它**按值**存进 `unordered_map`（`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:81`），依赖 `try_emplace` 的原地构造（`:32`）绕开移动。

**判定：注释错误，非代码缺陷。** 但 `packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:47-49` 的 `Status::Unregistered` 注释也依赖「moved-from」这个概念（"Newly created, moved-from, or already-unregistered"）—— 既然不可移动，"moved-from" 分支永远不会出现。

## 4. 【核心 SCH-2】`Parameters` 组有 4 处读写完全在锁外

`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:165-171` 给出的契约：

> Parameters can be changed independently from controlling the running state...
> **Changing parameters requires acquiring a unique lock; reading needs only a shared lock.**

而实现里有 4 处既不取 `parametersMutex_`：

| # | 位置 | 操作 | 字段 |
| --- | --- | --- | --- |
| 1 | `packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:27-30` | **写** | `contextContainer` |
| 2 | `packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:64-69` | 读 | `displayMode` |
| 3 | `packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:203-212` | 读 | `surfaceId`、`contextContainer` |
| 4 | `packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:238-242` | 读 | `surfaceId`、`contextContainer` |

第 1 处最直接：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:27-30
void SurfaceHandler::setContextContainer(
    std::shared_ptr<const ContextContainer> contextContainer) const noexcept {
  parameters_.contextContainer = std::move(contextContainer);
}
```

对比同文件里其他写入者：`setSurfaceId`（`:141-144`）、`setProps`（`:151-159`）、`constraintLayout`（`:219-229`）、`setDisplayMode`（`:101-110`）**全部**取 `std::unique_lock lock(parametersMutex_)`。唯独 `setContextContainer` 没有。

第 2/3/4 处不是笔误而是**结构问题**：`start()`（`:37-77`）整个函数持有 `linkMutex_` 的 unique lock，然后在 `:43` 调 `getLayoutConstraints()`（会取 `parametersMutex_` 的 shared lock）—— 说明锁的嵌套方向是 `link → parameters`。既然 `measure()` / `constraintLayout()` 也已经持有 `linkMutex_`，作者就顺手省掉了 parameters 锁。代价是：

- `setContextContainer`（无锁写）与 `measure`（无锁读）在不同线程并发时是**数据竞争**（`std::shared_ptr` 的读写在 C++ 里不是原子的）；
- 而如果补上锁，就会出现第二条嵌套方向 `link → parameters`（已存在）之外的 `parameters → link`（不新增，因为这几处已经持有 link）。

**判定：真实的线程安全缺陷（1 处写 + 3 处读）。** 修法不是简单加锁：`setContextContainer` 需要取 unique lock，其余三处把 `parameters_.x` 改成先拷贝一份 `Parameters` 快照再读。

## 5. SCH-3 `measure()` 的「返回零尺寸」承诺不成立

`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:129-133`：

> Measures the surface with given layout constraints and layout context.
> **Returns zero size if called on the stopped or unregistered surface.**

实现（`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:191-198`）：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:194-198
  std::shared_lock lock(linkMutex_);

  if (link_.status != Status::Running) {
    return layoutConstraints.clamp({.width = 0, .height = 0});
  }
```

`clamp` 不是「返回 0」，而是「把 0 夹进约束区间」。当调用方传入带 `minWidth` / `minHeight` 的约束时（`LayoutConstraints` 支持最小尺寸），停止状态下的 surface 会 **返回 minWidth × minHeight**，而不是 0。

调用链上这会被 `SurfaceManager::measureSurface`（`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:107-118`）原样返回，再经 `SurfaceHandler` 的 JSI 绑定交给 JS `measureInWindow` / `onLayout` 一类路径。

**判定：注释与实现不一致（低危）。** 要么注释改成「clamp 到给定约束」，要么实现改成返回 `Size{}`。

## 6. 【核心 SCH-4】`SurfaceManager::stopSurface` 会对不存在的 surface 执行 `erase(end())`

`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:46-65`：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:46-65
void SurfaceManager::stopSurface(SurfaceId surfaceId) noexcept {
  bool surfaceWasRunning = false;
  visit(surfaceId, [&](const SurfaceHandler& surfaceHandler) {
    surfaceHandler.stop();
    scheduler_.unregisterSurface(surfaceHandler);
    surfaceWasRunning = true;
  });
  if (!surfaceWasRunning) {
    LOG(WARNING)
        << "SurfaceManager::stopSurface tried to stop a surface which was not running, surfaceId = "
        << surfaceId;
  }

  {
    std::unique_lock lock(mutex_);

    auto iterator = registry_.find(surfaceId);
    registry_.erase(iterator);
  }
}
```

`visit` 在找不到 key 时会直接 return（`:146-150`），所以 `surfaceWasRunning` 保持 `false`，只打一条 WARNING。**但下面的 erase 照做**：`registry_.find(surfaceId)` 返回 `end()`，而 `unordered_map::erase(iterator)` 传入 `end()` 是**未定义行为**（libstdc++ 的 `_M_erase` 会对 `end()` 上的节点做指针运算）。

触发条件很普通：

| 场景 | 结果 |
| --- | --- |
| 连续调用 `stopSurface(id)` 两次 | 第二次 `visit` 找不到 → `erase(end())` → UB |
| `stopSurface` 一个从未 `startSurface` 的 id | 同上 |
| `~SurfaceManager` 之后有人再调 | 同上 |

`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.h:24-28` 的类注释说它「supposed to be used during the transition period only」—— 过渡期 API 也没有为重复调用做防护。

**判定：真实缺陷（UB），修法是 `if (iterator != registry_.end()) registry_.erase(iterator);`**

## 7. SCH-5 `isSurfaceRunning()` 实际判定的是「已注册」

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:74-77
bool SurfaceManager::isSurfaceRunning(SurfaceId surfaceId) const noexcept {
  std::shared_lock lock(mutex_);
  return registry_.contains(surfaceId);
}
```

而 `startSurface` 的顺序是**先入表、后启动**：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:30-43
  {
    std::unique_lock lock(mutex_);
    auto [it, _] = registry_.try_emplace(surfaceId, moduleName, surfaceId);
    it->second.setContextContainer(scheduler_.getContextContainer());
  }

  visit(surfaceId, [&](const SurfaceHandler& surfaceHandler) {
    surfaceHandler.setProps(props);
    surfaceHandler.constraintLayout(layoutConstraints, layoutContext);

    scheduler_.registerSurface(surfaceHandler);

    surfaceHandler.start();
  });
```

`registry_` 在 `:32` 就插入，`start()` 在 `:42` 才调用。中间任何一步抛异常（`setProps` / `constraintLayout` / `start` 都会走 `folly::dynamic` 与 JSI）都不会回滚注册表 → `isSurfaceRunning(id)` 之后**永远返回 true**，而该 surface 的 `Status` 仍是 `Registered`。

`SurfaceHandler` 自己的 `getStatus()`（`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.cpp:32-35`）能区分三态，`SurfaceManager` 这里退化成了两态。

**判定：语义漂移（中危）。** 名词是 running，实现是 registered。

## 8. SCH-6 `Scheduler` 析构的两级兜底：assert 在生产里失效，剩下的路径自认可能死锁

`packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:223-258`：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:223-239
  // Then, let's verify that the requirement was satisfied.
  auto surfaceIds = std::vector<SurfaceId>{};
  uiManager_->getShadowTreeRegistry().enumerate(
      [&surfaceIds](const ShadowTree& shadowTree, bool&) {
        surfaceIds.push_back(shadowTree.getSurfaceId());
      });

  react_native_assert(
      surfaceIds.empty() &&
      "Scheduler was destroyed with outstanding Surfaces.");

  if (surfaceIds.empty()) {
    return;
  }

  LOG(ERROR) << "Scheduler was destroyed with outstanding Surfaces.";

  // If we are here, that means assert didn't fire which indicates that we in
  // production.
```

后半段的补救：

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:249-257
  for (auto surfaceId : surfaceIds) {
    uiManager_->getShadowTreeRegistry().visit(
        surfaceId,
        [](const ShadowTree& shadowTree) { shadowTree.commitEmptyTree(); });

    // Removing surfaces acquires mutex waiting for commits in flight; in
    // theory, it can deadlock.
    uiManager_->getShadowTreeRegistry().remove(surfaceId);
  }
```

三件事值得记：

1. **注释直接承认可能死锁**（`:254-255` "in theory, it can deadlock"）。`remove` 要等飞行中的 commit，而此时正在析构线程里。
2. 析构函数**无条件** `LOG(WARNING)`（`:188-189`），`SurfaceManager::~SurfaceManager` 也是（`packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceManager.cpp:19-20`）—— 正常释放也会在日志里留下一条 WARNING。
3. 生产构建下 assert 不生效，所以「`Scheduler` 析构时还有 surface」这条约束在 release 里**没有强制**，只靠这条补救路径。

**判定：已知风险，代码自陈。** 记下来是因为它解释了「为什么有的 crash 日志里只有一条 `Scheduler was destroyed with outstanding Surfaces.` 然后进程没了」——最后一行日志是对的，但下一行可能死锁在 `remove`。

## 9. SCH-7 三类 UI 回调的线程模型不一致

`Scheduler` 实现 `UIManagerDelegate` 的多个回调，其中：

| 回调 | 位置 | 执行方式 |
| --- | --- | --- |
| `uiManagerDidDispatchCommand` | `packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:330-347` | 包进 `runtimeScheduler_->scheduleRenderingUpdate(...)` —— **延后到渲染步骤** |
| `uiManagerDidSendAccessibilityEvent` | `packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:349-358` | 直接调 `delegate_->schedulerDidSendAccessibilityEvent` |
| `uiManagerDidSetIsJSResponder` | `packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:363-371` | 直接调 |
| `uiManagerDidUpdateShadowTree` | `packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:381-386` | 直接调 |
| `uiManagerDidFinishReactCommit` | `packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:419-438` | 包进 `scheduleRenderingUpdate`，里面再 `promoteReactRevision()` |

同一个 abstract 接口上的五个方法，三个同步、两个异步。而 `scheduleRenderingUpdate` 在两个分叉上语义相反（见 RTS-2）：Legacy 下同步执行，Modern 下推到 tick 末尾。**所以「command 是否延后」取决于架构**：

| 架构 | `dispatchCommand` 的实际时机 |
| --- | --- |
| bridge（Legacy 分叉） | 立即执行（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:198-200`） |
| bridgeless（Modern 分叉） | 当前任务结束后的 `updateRendering` 阶段 |

**判定：行为事实，且是「同一份 C++ 在两种架构下时序不同」的典型样本。**

## 10. SCH-8 两个 metrics reporter 的开启条件不对称

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/Scheduler.cpp:49-60
  if (ReactNativeFeatureFlags::enableBridgelessArchitecture() &&
      ReactNativeFeatureFlags::cdpInteractionMetricsEnabled()) {
    cdpMetricsReporter_ =
        std::make_unique<CdpMetricsReporter>(runtimeExecutor_);
    performanceEntryReporter_->addEventListener(cdpMetricsReporter_.get());
  }

  if (ReactNativeFeatureFlags::perfIssuesEnabled()) {
    cdpPerfIssuesReporter_ =
        std::make_unique<CdpPerfIssuesReporter>(runtimeExecutor_);
    performanceEntryReporter_->addEventListener(cdpPerfIssuesReporter_.get());
  }
```

## 15. 【核心 RTS-3】Legacy 的 `getShouldYield()` 不看任务队列

Legacy（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:115-117`）：

```cpp

  return runtimeAccessRequests_ > 0;

```

Modern（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:130-137`）：

```cpp

  markYieldingOpportunity(now_());

```

差异是结构性的：

| 问题 | Legacy | Modern |
| --- | --- | --- |
| 有没有别的线程在等运行时？ | ✅（`runtimeAccessRequests_ > 0`） | ✅（`syncTaskRequests_ > 0`） |
| 队列里有没有更高优先级的任务？ | ❌ **完全不看** | ✅（`top() != currentTask_`） |

`unstable_shouldYield` 直接转发到这里（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeSchedulerBinding.cpp:109-122`）。React 的 Scheduler 包用 `shouldYield()` 决定是否把长任务切片，所以在 Legacy 下：

- 只要没有别的线程抢运行时，`shouldYield()` **永远返回 false**；
- 于是 `while (!shouldYield()) { workLoopConcurrent(); }` 这类循环一旦进入就不会主动让出；
- 队列里堆着 Immediate 优先级的任务也不会让当前 Normal 任务提前中止。

**判定：Legacy 分叉的行为差异（非缺陷，是「旧实现只支持单一优先级」的遗留）。** 但它的后果在 bridge 架构下真实存在：JS 长任务不会因为排队任务而让出。

三个量：

| --- | --- | --- | --- |

| 每 10 ms 调一次 `shouldYield` | 200 ms | **≤10 ms** | ❌ **不上报** |

第二行就是 React 的**并发渲染**：`workLoopConcurrent` 每处理一个 fiber 就调 `shouldYield()`。也就是说**越规范地让出，越不会被记成 long task**；而报表里的 `duration` 又和触发它的那个量无关。

## 20. 【核心 RTS-8】`unstable_scheduleCallback` 声明 3 个参数，只读 2 个

## 23. 【核心 RTS-11】`isPerformingWork_` 没有 RAII，错误处理器一抛就永久卡死

Legacy（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:242-269`）：

```cpp
// packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:242-269
void RuntimeScheduler_Legacy::startWorkLoop(jsi::Runtime& runtime) {
  TraceSection s("RuntimeScheduler::startWorkLoop");

  auto previousPriority = currentPriority_;
  isPerformingWork_ = true;
  try {
    while (!taskQueue_.empty()) {
      auto topPriorityTask = taskQueue_.top();
      auto now = now_();
      auto didUserCallbackTimeout = topPriorityTask->expirationTime <= now;

      if (!didUserCallbackTimeout && getShouldYield()) {
        // This currentTask hasn't expired, and we need to yield.
        break;
      }

      executeTask(runtime, topPriorityTask, didUserCallbackTimeout);
    }
  } catch (jsi::JSError& error) {
    onTaskError_(runtime, error);
  } catch (std::exception& ex) {
    jsi::JSError error(runtime, std::string("Non-js exception: ") + ex.what());
    onTaskError_(runtime, error);
  }

  currentPriority_ = previousPriority;
  isPerformingWork_ = false;
}
```

`onTaskError_` **在 catch 块内**被调用（`:261`、`:264`）。如果它抛异常（默认实现走 `handleJSError(..., isFatal=true)`，宿主可能抛），那么：

- `currentPriority_ = previousPriority`（`:267`）不执行 → 优先级泄漏；
- `isPerformingWork_ = false`（`:268`）不执行 → **永久为 true**。

而 `scheduleWorkLoopIfNecessary` 的第一道门就是它：

```cpp
// packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:232-233
void RuntimeScheduler_Legacy::scheduleWorkLoopIfNecessary() {
  if (!isWorkLoopScheduled_ && !isPerformingWork_) {
```

`isPerformingWork_` 一旦卡住，后续所有 `scheduleTask` 都不再调度 work loop → **JS 任务永远不执行**，且没有任何日志。

对照 Modern：同一个模式的标志用了 RAII（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:453-454`）：

```cpp
// packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:453-454
  performingMicrotaskCheckpoint_ = true;
  OnScopeExit restoreFlag([&]() { performingMicrotaskCheckpoint_ = false; });
```

**判定：核心缺陷（异常安全）。** 同一份代码库在 Modern 里用了 `OnScopeExit`、在 Legacy 里没用。

## 24. RTS-12 `executeNowOnTheSameThread` 的计数器在 executor lambda 内递减

Modern（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:152-179`）：

```cpp
// packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:152-179
void RuntimeScheduler_Modern::executeNowOnTheSameThread(
    RawCallback&& callback) {
  TraceSection s("RuntimeScheduler::executeNowOnTheSameThread");

  static thread_local jsi::Runtime* runtimePtr = nullptr;

  auto currentTime = now_();
  auto priority = SchedulerPriority::ImmediatePriority;
  auto expirationTime = currentTime + timeoutForSchedulerPriority(priority);
  Task task{priority, std::move(callback), expirationTime};

  if (runtimePtr != nullptr) {
    // Protecting against re-entry into `executeNowOnTheSameThread` from within
    // `executeNowOnTheSameThread`. Without accounting for re-rentry, a deadlock
    // will occur when trying to gain access to the runtime.
    return executeTask(*runtimePtr, task, true);
  }

  syncTaskRequests_++;
  executeSynchronouslyOnSameThread_CAN_DEADLOCK(
      runtimeExecutor_, [&](jsi::Runtime& runtime) mutable {
        TraceSection s2("RuntimeScheduler::executeNowOnTheSameThread callback");

        syncTaskRequests_--;
        runtimePtr = &runtime;
        runEventLoopTick(runtime, task);
        runtimePtr = nullptr;
      });
```

四处值得记：

1. **函数名自带 `_CAN_DEADLOCK`**（`:171`）—— 与 SCH-6 的「in theory, it can deadlock」同一种自我声明。
2. **`syncTaskRequests_--` 在 lambda 内部**（`:175`）。如果 `runtimeExecutor_` 因为运行时已销毁而**丢弃**这个块（executor 的常见实现是「runtimes 活着才执行」），计数器永远不减 → `getShouldYield()` 永远返回 true（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Modern.cpp:135`）→ JS 侧 `shouldYield()` 恒真 → 并发渲染的 work loop 每次一进去就让出。Legacy 的 `runtimeAccessRequests_` 是同一模式（`packages/react-native/ReactCommon/react/renderer/runtimescheduler/RuntimeScheduler_Legacy.cpp:139` 增、`:145` 减）。
3. **`runtimePtr = nullptr` 没有 RAII**（`:178`）。`runEventLoopTick` 抛异常（见 RTS-6）时不会复位；不过它是 `thread_local`，线程复用时会拿到一个**悬垂的 Runtime\***，下一次重入判定（`:163`）就会走到错误分支。
4. **`syncTaskRequests_++` 在调用 executor 之前**（`:170`），所以从递增到递减之间，`getShouldYield()` 对所有线程都返回 true —— 这正是设计意图（让出给同步访问）。

**判定：计数器泄漏是真实风险（条件：executor 丢弃块）；`runtimePtr` 的悬垂是次级风险。**
