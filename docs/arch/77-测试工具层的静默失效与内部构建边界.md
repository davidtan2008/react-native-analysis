## 2. 【核心 TST-1】`shuffle` 按值传参 —— 注释说的「in place」从未发生

### 2.1 实现与注释

```cpp
// packages/react-native/ReactCommon/react/test_utils/Entropy.h:92-99
  /*
   * Shuffles `std::vector` in place.
   */
  template <typename T>
  void shuffle(T array) const
  {
    std::shuffle(array.begin(), array.end(), generator_);
  }
```

**注释明写「in place」，但签名是 `void shuffle(T array)` —— 按值传参。**

`std::shuffle` 打乱的是**形参这份副本**；调用方的数组**一个字节都没变**。

### 2.2 唯一调用方与它想做的事

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:103-111
static inline std::shared_ptr<ShadowNode> messWithChildren(const Entropy &entropy, const ShadowNode &shadowNode)
{
  auto children = shadowNode.getChildren();
  children = cloneSharedShadowNodeList(children);
  entropy.shuffle(children);
  return shadowNode.clone(
      {ShadowNodeFragment::propsPlaceholder(),
       std::make_shared<const std::vector<std::shared_ptr<const ShadowNode>>>(children)});
}
```

函数名 `messWithChildren`、调用点 `entropy.shuffle(children)` —— **意图明确**：把子节点顺序打乱，制造「子节点顺序不应影响渲染结果」这类测试场景。

### 2.3 后果

**`messWithChildren` 返回的子树，子节点顺序与输入完全一致。** 这个「随机化」工具**从未产生任何随机化效果**。

**判定：历史承诺（注释描述的能力不存在）** —— 与 71 文档 KKK-3、76 文档 CLI-8 同型：**注释/命名承诺的行为与实现不符**。

### 2.4 修法与影响面

改成 `T &array`（或 `std::vector<T> &array`）即可。**但要注意**：改完之后 `messWithChildren` 才会真正产生随机顺序 —— 这会**改变现有测试的行为**（原本恒等的断言可能开始失败）。**这属于「让工具名副其实」的修正，而不是纯 bug 修复。**

## 3. 【核心 TST-2】`random<T>()` 无参重载返回 `bool`

### 3.1 三个重载的返回类型

```cpp
// packages/react-native/ReactCommon/react/test_utils/Entropy.h:52-74
  template <typename T>
  bool random() const
  {
    T result;
    generateRandomValue(generator_, result);
    return result;
  }

  template <typename T, typename Arg1>
  T random(Arg1 arg1) const
  {
    T result;
    generateRandomValue(generator_, result, arg1);
    return result;
  }

  template <typename T, typename Arg1, typename Arg2>
  T random(Arg1 arg1, Arg2 arg2) const
  {
    T result;
    generateRandomValue(generator_, result, arg1, arg2);
    return result;
  }
```

| 重载 | 返回类型 |
| --- | --- |
| `random<T>()`（无参） | **`bool`** ← 与另两个不一致 |
| `random<T>(arg1)` | `T` |
| `random<T>(arg1, arg2)` | `T` |

### 3.2 `T = int` 时会发生什么

无参版走的是：

```cpp
// packages/react-native/ReactCommon/react/test_utils/Entropy.h:81-84
  void generateRandomValue(Generator &generator, int &result) const
  {
    result = generator();
  }
```

`result` 是一个**随机的 `int`**，但 `random<int>()` 的返回类型是 `bool` → **`return result;` 把它转成 `true`/`false`** → **调用方拿到的 `int` 只可能是 0 或 1**。

### 3.3 受影响的调用点

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:143-145
  if (entropy.random<bool>(0.1)) {
    viewProps.zIndex = entropy.random<int>();
  }
```

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:195-196
    viewProps.zIndex = {};
    ...
    viewProps.zIndex = {entropy.random<int>()};
```

**`zIndex` 的「随机化」实际只能取 0 或 1 两个值** —— 而 `zIndex` 是个没有天然上界的 `int`，测试原本想覆盖各种层叠值。

### 3.4 未受影响的调用点（对照）

| 调用点 | 用的重载 | 是否正确 |
| --- | --- | --- |
| `entropy.random<bool>()` | 无参 → `bool` | ✓ 恰好对 |
| `entropy.random<bool>(0.1)` | 一参 → `bool` | ✓ |
| `entropy.random<int>(0, 1024)`（`:228`） | 二参 → `int` | ✓ |
| `entropy.random<int>(1, count - 1)`（`:89`） | 二参 → `int` | ✓ |
| `entropy.random<int>()`（`:144`、`:196`） | 无参 → **`bool`** | ✗ **只得到 0/1** |

**判定：缺陷（重载返回类型不一致）。** 修法是把无参版改成 `T random() const`。

### 3.5 附带：`T result;` 是未初始化的局部变量

三个重载都是 `T result;` → **在传给 `generateRandomValue` 之前未初始化**。当前所有重载都会赋值，因此实践上无害；但这是**依赖被调函数内部行为**的写法 —— 若将来新增一个「不总是赋值」的重载，就是读取未初始化值。

**判定：结构脆弱（当前无害）。**

## 4. TST-4 `distribute()` 的边界桶不可达

```cpp
// packages/react-native/ReactCommon/react/test_utils/Entropy.h:105-121
  template <typename T>
  std::vector<std::vector<T>> distribute(std::vector<T> items, double deviation) const
  {
    std::normal_distribution<> distribution{0, deviation};

    auto deviationLimit = int(deviation * 10);
    auto spreadResult = std::vector<std::vector<T>>(deviationLimit * 2);
    std::fill(spreadResult.begin(), spreadResult.end(), std::vector<T>{});

    for (const auto &item : items) {
      auto position = int(distribution(generator_) + deviationLimit);
      position = std::max(0, std::min(position, deviationLimit * 2));

      if (position < spreadResult.size()) {
        spreadResult[position].push_back(item);
      }
    }
```

### 4.1 桶数与钳位上界相等

| 量 | 值（`deviation = 3`） |
| --- | --- |
| `deviationLimit` | `int(3 * 10)` = **30** |
| `spreadResult.size()`（桶数） | `deviationLimit * 2` = **60** |
| 钳位上界 | `deviationLimit * 2` = **60** |

**钳位允许的最大索引 60，而合法索引只有 0…59** → `position == 60` 的元素被 `if (position < spreadResult.size())` **静默丢弃**。

### 4.2 可达性

`position = int(normal(0, deviation) + deviationLimit)`，要让 position 达到 60 需正态偏离达 `deviationLimit = 30` 个标准差（σ = deviation = 3）→ **约 10σ**。

**判定：结构脆弱（边界处理不自洽 —— 钳位上界应取桶数减一；实际触发需约 10σ 偏离，接近不可达）。** 值得记录的是**边界语义不自洽**这一事实本身。

## 5. 【核心 TST-5】`findRandomShadowNode` 的随机区间基于一个错误前提

### 5.1 问题代码

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:84-90
static ShadowTreeEdge findRandomShadowNode(
    const Entropy &entropy,
    const std::shared_ptr<const ShadowNode> &rootShadowNode)
{
  auto count = countShadowNodes(rootShadowNode);
  return findShadowNodeWithIndex(rootShadowNode, entropy.random<int>(1 /* Excluding a root node */, count - 1));
}
```

注释说 `1 /* Excluding a root node */` —— **作者以为 `count` 含根节点**，所以从索引 1 开始取。

### 5.2 但 `countShadowNodes` **不统计根节点**

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:59-66
static int countShadowNodes(const std::shared_ptr<const ShadowNode> &rootShadowNode)
{
  auto counter = int{0};

  traverseShadowTree(rootShadowNode, [&](const ShadowTreeEdge &edge, bool &stop) { counter++; });

  return counter;
}
```

而 `traverseShadowTree` 的回调**只对子节点触发**：

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:36-57
static bool traverseShadowTree(
    const std::shared_ptr<const ShadowNode> &parentShadowNode,
    const std::function<void(const ShadowTreeEdge &edge, bool &stop)> &callback)
{
  auto index = int{0};
  for (const auto &childNode : parentShadowNode->getChildren()) {
    auto stop = bool{false};

    callback(ShadowTreeEdge{childNode, parentShadowNode, index}, stop);

    if (stop) {
      return true;
    }

    if (traverseShadowTree(childNode, callback)) {
      return true;
    }

    index++;
  }
  return false;
}
```

**→ `count` = 后代节点数（不含根）。**

### 5.3 双重后果

| | 说明 |
| --- | --- |
| **① 区间本就漏一个** | 后代索引是 **0 基**（`index` 从 0 递增），合法区间是 `[0, count-1]`；代码取 `[1, count-1]` → **第 0 个后代永远选不到** |
| **② count ≤ 1 时构造出非法区间** | `count == 0`（只有根）→ `uniform_int_distribution<int>(1, -1)`；`count == 1`（一个后代）→ `uniform_int_distribution<int>(1, 0)` → **两者都是 min > max** |

**C++ 标准对 `uniform_int_distribution(a, b)` 在 `a > b` 时的行为未作规定**（属未定义行为）。libstdc++ 的实现会交换两端，因此**大概率不崩，但取到的索引与调用方预期无关**。

### 5.4 可达性

`count ≤ 1` 意味着树只有根或只有一个后代 —— **在单元测试里是很小的树**。而 `findRandomShadowNode` 是 `alterShadowTree` 的必经之路：

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:244-252
static inline void
alterShadowTree(const Entropy &entropy, RootShadowNode::Shared &rootShadowNode, ShadowNodeAlteration alteration)
{
  auto edge = findRandomShadowNode(entropy, rootShadowNode);

  rootShadowNode = std::static_pointer_cast<RootShadowNode>(rootShadowNode->cloneTree(
      edge.shadowNode->getFamily(),
      [&](const ShadowNode &oldShadowNode) { return alteration(entropy, oldShadowNode); }));
}
```

**判定：缺陷（区间构造的前提与被调函数的语义不符）** —— 且后果不止是「少选一个节点」，还包括**小树上落入未定义行为**。

## 6. TST-6 `alterShadowTree` 在空 alterations 列表时同样构造非法区间

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:254-261
static inline void alterShadowTree(
    const Entropy &entropy,
    RootShadowNode::Shared &rootShadowNode,
    std::vector<ShadowNodeAlteration> alterations)
{
  auto i = entropy.random<int>(0, alterations.size() - 1);
  alterShadowTree(entropy, rootShadowNode, alterations[i]);

```

`alterations` 为空时 `alterations.size() - 1` 是 `size_t` 的下溢 → 转成 `int` 得到 **-1** → `uniform_int_distribution<int>(0, -1)` → **min > max（未定义行为）**；随后 `alterations[i]` 还会**越界访问空 vector**。

**判定：缺陷（无空列表防护）。**

## 7. TST-7 `traverseShadowTree` 是无深度限制的递归

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:50-52
    if (traverseShadowTree(childNode, callback)) {
      return true;
    }
```

**每层递归一帧，无深度上限。** 影子树的深度由被测代码决定 —— 一个构造出极深树的测试会让这个辅助函数**自身栈溢出**。

**与 64 文档 DDD-2 对照**：那篇记录的是 `getTextContentInShadowNode` 的**无深度限制递归**，并实测出「1MB 栈 ≈ 13,750 层」的崩溃阈值。**这里是同一形态的第二处实例** —— 只不过位置在**测试工具**里，因此触发者是测试作者而非线上用户。

**判定：结构脆弱（当前树深度由测试构造，实践中很浅）。**

## 9. TST-9 `findShadowNodeWithIndex` 越界时静默返回空边

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:68-82
static ShadowTreeEdge findShadowNodeWithIndex(const std::shared_ptr<const ShadowNode> &rootNode, int index)
{
  auto counter = int{0};
  auto result = ShadowTreeEdge{};

  traverseShadowTree(rootNode, [&](const ShadowTreeEdge &edge, bool &stop) {
    if (index == counter) {
      result = edge;
    }

    counter++;
  });

  return result;
}
```

索引越界时**返回默认构造的 `ShadowTreeEdge`** —— 其成员全是默认值：

```cpp
// packages/react-native/ReactCommon/react/test_utils/shadowTreeGeneration.h:29-34
class ShadowTreeEdge final {
 public:
  std::shared_ptr<const ShadowNode> shadowNode{nullptr};
  std::shared_ptr<const ShadowNode> parentShadowNode{nullptr};
  int index{0};
};
```

**→ `shadowNode == nullptr`，而调用方 `alterShadowTree` 会立刻 `edge.shadowNode->getFamily()` → 空指针解引用。**

**判定：缺陷（越界无信号，静默返回可解引用的空值）。** 与 TST-5 叠加：**小树上 `findRandomShadowNode` 会先撞上非法区间，再撞上这个空返回。**

```cpp
      shadowNode.getComponentDescriptor().cloneProps(parserContext, oldProps, RawProps(folly::dynamic::object()));

  if (entropy.random<bool>(0.1)) {
    viewProps.nativeId = entropy.random<bool>() ? "42" : "";
  }
```

**`cloneProps` 返回的是 `const` props**（`std::shared_ptr<const ViewProps>`），这里用 `const_cast` 把它变成可写，然后直接改字段。

**理由可以理解**（测试要制造 props 变体），但这**绕过了渲染器赖以成立的 props 不可变性契约** —— 若 `cloneProps` 返回的是**共享**的 props 对象（而非新对象），这次修改会**污染其它节点**。

**判定：结构脆弱（依赖「`cloneProps` 必然返回新对象」这一未被断言的假设）。**

## 11. TST-11 `EXPECT_EQ` 写在头文件的辅助函数里


**判定：结构脆弱（约束本身正确，断言归属不理想）。**

```cpp
  static time_point time_;
```

### 12.2 两个定义点

| --- | --- |
| **同一二进制** | **重复定义 → 链接错误**（multiple definition of `MockClock::time_`） |

**→ 全局命名空间污染**，且与本目录的风格不一致。

### 12.5 附带：没有 reset，跨测试状态泄漏

`MockClock` 只有 `now()` 与 `advance_by()` —— **没有任何重置手段**。`time_` 是**静态成员**，在同一二进制内**跨测试共享** → 一个测试推进了时钟，后续测试看到的起点就不是 0。

**判定：缺陷（静态成员定义重复 + 全局命名空间 + 缺少 reset）。**

## 13. 【核心 TST-13】`MockSurfaceHandler` 的 `getSurfaceId` mock 无效

### 13.1 mock 声明

```cpp
// packages/react-native/ReactCommon/react/test_utils/MockSurfaceHandler.h:16-22
class MockSurfaceHandler : public SurfaceHandler {
 public:
  MockSurfaceHandler() : SurfaceHandler("moduleName", 0) {};

  MOCK_METHOD(void, setDisplayMode, (DisplayMode), (const, noexcept));
  MOCK_METHOD(SurfaceId, getSurfaceId, (), (const, noexcept));
};
```

### 13.2 基类的两个方法，一个是虚的、一个不是

```cpp
// packages/react-native/ReactCommon/react/renderer/scheduler/SurfaceHandler.h:104-109
  virtual void setDisplayMode(DisplayMode displayMode) const noexcept;
  DisplayMode getDisplayMode() const noexcept;

#pragma mark - Accessors

  SurfaceId getSurfaceId() const noexcept;
```

| 方法 | 基类是否 `virtual` | mock 是否生效 |
| --- | --- | --- |
| `setDisplayMode` | **是** | ✓ 生效（真正 override） |
| `getSurfaceId` | **否** | ✗ **不生效** |

### 13.3 「不生效」的确切含义

`MOCK_METHOD` 在派生类里声明的是**一个新的虚函数**（gmock 生成的 mock 方法本身是 virtual），它**遮蔽（hiding）**了基类的同名非虚函数 —— 但**不构成 override**。

因此：

| 调用形式 | 实际执行 |
| --- | --- |
| `mockSurfaceHandler->getSurfaceId()`（静态类型是派生类） | **mock**（返回 gmock 默认值 0，除非设了期望） |
| `surfaceHandler->getSurfaceId()`（静态类型是基类 `SurfaceHandler*`） | **基类的真实实现** → 返回构造时传入的 `surfaceId` |

而这个 mock 的构造器恰好把 surfaceId 固定为 0：

```cpp
// packages/react-native/ReactCommon/react/test_utils/MockSurfaceHandler.h:18
  MockSurfaceHandler() : SurfaceHandler("moduleName", 0) {};
```

→ **默认情况下两条路径都返回 0**，差异只在测试设了 `EXPECT_CALL` 且通过派生类型调用时才显现。

### 13.4 附带：这个头文件全仓无人引用

实测 `MockSurfaceHandler` 在 `.cpp` / `.h` / `.mm` / `.m` 中**除头文件自身外零命中**。

**判定：缺陷（对非虚方法做 mock）** + **附带事实：该头文件目前是死代码**。两者叠加 —— **它既无效也没人用**，因此修起来没有兼容性负担。

## 14. 【核心 TST-14】`ShimRCTInstance.reset` 会把 swizzle 撤销

### 14.1 交换实现

```objc
// packages/react-native/ReactCommon/react/test_utils/ios/RCTSwizzleHelpers.m:12-17
void RCTSwizzleInstanceSelector(Class targetClass, Class swizzleClass, SEL selector)
{
  Method originalMethod = class_getInstanceMethod(targetClass, selector);
  Method swizzleMethod = class_getInstanceMethod(swizzleClass, selector);
  method_exchangeImplementations(originalMethod, swizzleMethod);
}
```

**`method_exchangeImplementations` 是对合的** —— 对同一对 Method 调用两次，回到原状。

### 14.2 `init` 里交换三个 selector

```objc
// packages/react-native/ReactCommon/react/test_utils/ios/Shims/ShimRCTInstance.mm:18-35
- (instancetype)init
{
  if (self = [super init]) {
    _initCount = 0;
    RCTSwizzleInstanceSelector(
        [RCTInstance class],
        [ShimRCTInstance class],
        @selector
        (initWithDelegate:
            jsRuntimeFactory:bundleManager:turboModuleManagerDelegate:moduleRegistry:parentInspectorTarget:launchOptions
                            :devMenuConfiguration:));
    RCTSwizzleInstanceSelector([RCTInstance class], [ShimRCTInstance class], @selector(invalidate));
    RCTSwizzleInstanceSelector(
        [RCTInstance class], [ShimRCTInstance class], @selector(callFunctionOnJSModule:method:args:));
    weakShim = self;
  }
  return self;
}
```

### 14.3 `reset` 里**又交换了同样三个 selector**

```objc
// packages/react-native/ReactCommon/react/test_utils/ios/Shims/ShimRCTInstance.mm:37-51
- (void)reset
{
  RCTSwizzleInstanceSelector(
      [RCTInstance class],
      [ShimRCTInstance class],
      @selector
      (initWithDelegate:
          jsRuntimeFactory:bundleManager:turboModuleManagerDelegate:moduleRegistry:parentInspectorTarget:launchOptions
                          :devMenuConfiguration:));
  RCTSwizzleInstanceSelector([RCTInstance class], [ShimRCTInstance class], @selector(invalidate));
  RCTSwizzleInstanceSelector(
      [RCTInstance class], [ShimRCTInstance class], @selector(callFunctionOnJSModule:method:args:));
  _initCount = 0;
  _invalidateCount = 0;
}
```

**→ 交换第二次 = 还原。**

### 14.4 后果

| 时刻 | RCTInstance 的三个方法指向 |
| --- | --- |
| `init` 之后 | shim 的实现（**拦截生效**） |
| **`reset` 之后** | **RCTInstance 的原始实现（拦截失效）** |

而 `reset` 的**表面效果**是 `_initCount = 0; _invalidateCount = 0;` —— **计数归零看起来像「重置成功」**，但实际上**shim 已经不再拦截**。

**→ reset 之后创建的 `RCTInstance` 会走真实实现（真的初始化、真的 invalidate），而 `initCount` / `invalidateCount` 永远停在 0。** 测试断言「`initCount == 1`」会**失败**；断言「`initCount == 0`」会**误通过**。

**判定：缺陷（`reset` 的副作用与它的名字/意图相反）。** 正确做法是 `reset` **不**再交换，只重置计数；若确实需要撤销 swizzle，应提供**独立的 `un-swizzle` 函数**（见 TST-16）。

## 16. TST-16 `RCTSwizzleInstanceSelector` 的两个隐患

### 16.1 无空指针检查

```objc
// packages/react-native/ReactCommon/react/test_utils/ios/RCTSwizzleHelpers.m:12-17
void RCTSwizzleInstanceSelector(Class targetClass, Class swizzleClass, SEL selector)
{
  Method originalMethod = class_getInstanceMethod(targetClass, selector);
  Method swizzleMethod = class_getInstanceMethod(swizzleClass, selector);
  method_exchangeImplementations(originalMethod, swizzleMethod);
}
```

若 `selector` 在任一 class 上**不存在** → `class_getInstanceMethod` 返回 `NULL` → `method_exchangeImplementations(NULL, m)` → **崩溃**。

**判定：缺陷（无 `NSAssert` / 返回值检查）。**

### 16.2 `class_getInstanceMethod` 沿继承链查找

该 API 的语义是「在类**及其父类**中查找实例方法」→ 若 `targetClass` 自己没实现该方法而**父类实现了**，交换的是**父类的 Method** → **该父类的所有子类都受影响**，而不只是 `targetClass`。

对测试工具而言，这意味着**swizzle 的影响范围可能超出预期**。

### 16.3 没有 un-swizzle 辅助函数

本目录只提供 `RCTSwizzleInstanceSelector`，**没有对应的还原函数**。想还原只能**再交换一次**（这正是 TST-14 的成因）。

**判定：结构脆弱（缺少显式的还原通道，导致 `reset` 走了「再交换一次」这条歧路）。**
