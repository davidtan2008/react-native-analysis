## 2. 数据结构层：五种哨兵与一个口径裂缝

### 2.1 【核心 MOU-1】`ShadowViewMutation::Type` 是 2 的幂枚举，字段自带三种哨兵

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowViewMutation.h:86-92`：

```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/ShadowViewMutation.h:86-92（压缩）
enum Type : std::uint8_t {
    Create = 1, Delete = 2, Insert = 4, Remove = 8, Update = 16,
};
```

五个值全是 2 的幂，形式上允许按位组合，但 `type` 只有一个字段且全库未见组合用法。字段哨兵值（`ShadowViewMutation.h:96-100`）：`parentTag` 默认 `kNoTag`（= −1，`packages/react-native/ReactCommon/react/renderer/core/ReactPrimitives.h:24`）、`index` 默认 −1、构造器语义（`ShadowViewMutation.cpp:14-71`）：

| 类型 | parentTag | index | 空 child |
| --- | --- | --- | --- |
| Create / Delete | `kNoTag`(−1) | −1 | new / old 侧留空 |
| Insert / Remove | 真实父 tag | 真实下标 | old / new 侧留空 |
| Update | 调用方传入 | **恒 −1**（`ShadowViewMutation.cpp:69`） | 无 |

**MOU-1** 由此带出一个冷知识：根 Update 传的 parentTag 是 `{}`（= **0**，`Differentiator.cpp:1379-1383`），而 `StubViewTree` 的 Update 分支判「无父可查」用的正是 `mutation.parentTag != 0`（`stubs/StubViewTree.cpp:211`）——同一文件里 Create/Delete 用 `kNoTag`、Update 用 `0`，两套哨兵并存。

### 2.2 MOU-2 `mutatedViewIsVirtual()` 只在 Android 有逻辑，且机制自述 DEPRECATED

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowViewMutation.cpp:73-87`：`#ifdef ANDROID` 之外 `viewIsVirtual` 恒 false；Android 上要求 old/new 两侧 `layoutMetrics` **都**等于 `EmptyLayoutMetrics` 才算 virtual（注释解释 Insert 的 old 侧、Remove 的 new 侧恒空，必须两边都看）。头文件注释 `ShadowViewMutation.h:102-106` 明说该机制 **DEPRECATED**（"it is highly recommended that you NOT make use of this in your platform"）。现役调用方只有两处：`LayoutAnimationKeyFrameManager` 9 处与 `StubViewTree` 2 处（`stubs/StubViewTree.cpp:97`、`:142`）。

### 2.3 【核心 MOU-3】`ShadowView` 的 `operator==` 与 `std::hash` 口径不对称

| 口径 | 包含 | 不包含 |
| --- | --- | --- |
| `operator==`（`packages/react-native/ReactCommon/react/renderer/mounting/ShadowView.cpp:34-51`） | surfaceId, tag, **componentName**, props, eventEmitter, layoutMetrics, state（7） | componentHandle, traits |
| `std::hash`（`packages/react-native/ReactCommon/react/renderer/mounting/ShadowView.h:63-79`） | surfaceId, **componentHandle**, tag, props, eventEmitter, layoutMetrics, state（7） | componentName, traits |

`componentName ↔ componentHandle` 一一对应（handle 是 name 的散列），所以两者实际等价；但 `props/eventEmitter/state` 在 `==` 里是 **shared_ptr 指针相等**（`std::tie` 顺序见 `:35-50`），值为孪生但对象不同即不相等——Update 变异的判据因此是「对象身份」而非「值相等」。这套哈希口径还被写进了自检：`StubViewTree` 的 Update 分支断言 StubView 转回 ShadowView 后哈希必须与 mutation 里的新 ShadowView 一致（`stubs/StubViewTree.cpp:218-222`），等于把「StubView 保真全部哈希相关字段」变成运行时不变量。

### 2.4 MOU-4 `MountingTransaction`：号从 1 起、moved-from 即 UB、const 方法返回可变引用

## 3. 提交管线：`ShadowTree::commit` 的两种模式

### 3.1 【核心 MOU-6】flag 关闭时是 `while(true)` 无界重试，护栏在 release 是空操作

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:320-333`：

```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:320-333（压缩）
} else {
    while (true) {
      attempts++;
      auto status = tryCommit(transaction, commitOptions);
      if (status != CommitStatus::Failed) {
        return status;
      }
      // After multiple attempts, we failed to commit the transaction.
      // Something internally went terribly wrong.
      react_native_assert(attempts < 1024);
    }
}
```

`tryCommit` 返回 Failed 的唯一常规原因是「持锁重读时 `currentRevision_.number` 已被其他线程改掉」（`:427-429`）。若一个线程反复提交而本线程的 transaction 回调总是追赶不及，这里就是**无限忙循环**：注释自认「Something internally went terribly wrong」，但唯一的护栏 `react_native_assert(attempts < 1024)` 在 release 是空操作。取消路径（`Cancelled`）不受影响，第一次出现即返回。

### 3.2 MOU-7 flag 开启时：最多 3 次无锁尝试，随后持锁独占再试一次

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:26` 定义 `MAX_COMMIT_ATTEMPTS_BEFORE_LOCKING = 3`；开启 `preventShadowTreeCommitExhaustion()` 时（`:307-319`）最多空转 3 次，然后**先拿 `revisionMutexRecursive_` 的 `std::unique_lock` 再调用 `tryCommit`**——此时任何并发的 `sharedRevisionLock()` 读（同为该 recursive_mutex 的 `unique_lock`，见 MOU-8）都被挡住，一次成功。该 flag 只把「不设上界的自旋」换成「3 次 + 落锁」，不改变 tryCommit 自身语义。

### 3.3 【核心 MOU-8】两把互斥锁并存；锁选择每次调用重读 flag；新路径的「共享锁」其实是互斥锁

三处事实：

- `ShadowTree.h:170-171`：`std::shared_mutex revisionMutex_` 与 `std::recursive_mutex revisionMutexRecursive_` **同时**是成员；六个状态成员（`commitMode_` / `currentRevision_` / `currentReactRevision_` / `reactRevisionToBePromoted_` / `queuedReactRevisions_` / `promotedReactRevisions_`）的注释全部只写「Protected by `revisionMutex_`」（`:172-177`）。
- 锁选择函数 **每次调用都重读 feature flag**（`ShadowTree.cpp:642-658`）：
```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:642-650（压缩）
inline ShadowTree::UniqueLock ShadowTree::uniqueRevisionLock(bool defer) const {
  if (ReactNativeFeatureFlags::preventShadowTreeCommitExhaustion()) {
    return ... {revisionMutexRecursive_} ...;
  } else {
    return ... {revisionMutex_} ...;
  }
}
```
- 最新路径的「共享锁」是 `std::unique_lock<recursive_mutex>`（`ShadowTree.h:180-181` 的 `SharedLock` variant 第二臂）——即**递归互斥锁上的排他锁，没有任何读并发**。注释宣称的 `revisionMutex_` 保护在新路径上由另一把锁承担，头文件注释过时。

另外 `tryCommit` 内部在 react 分支上有一处**手动改锁状态**：用 `std::visit([](auto& l){ l.lock(); })` 把 variant 里的锁再锁一层，以便在作用域外写 `currentReactRevision_`（`ShadowTree.cpp:455-462`，MOU-10）。

### 3.4 MOU-9 revision 编号规则与 CAS 失败语义

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:427-433`：主分支 commit 若发现 `currentRevision_.number != oldRevision.number` 立即 `Failed`（CAS 语义）；成功时新号是：

- 非 react 分支：`currentRevision_.number + 1`；
- react 分支：`oldRevisionForStateProgression.number + 1`——以状态推进基线为计数起点，不是当前主分支号，也不是 react 分支自己的号（`ShadowTree.cpp:431-433`）。两套计数可交错推进，这正是 §6 中 push 侧只认更大号 revision 的背景。

### 3.5 MOU-10 react 分支的提交收尾：锁内写 `currentReactRevision_`、锁外回调

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:465-475`：主分支提交成功后先 `shadowTreeDidCommit`（`:465-466`，带受影响 layoutable 列表）再按 commitMode 决定 `mount()`；react 分支提交成功后**不 mount**，只 `scheduleReactRevisionPromotion()`（`:468-469`），最终经 `shadowTreeDidFinishReactCommit` 通知 JS 侧（`:620`）。

## 4. ReactRevisionMerge：props 积累保证分叉出的两条合并路径

### 4.1 MOU-11 `isPropsUpdatesAccumulationGuaranteed()`：Android 看开关，其他平台恒 true

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:41-47`：

```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:41-47（压缩）
inline bool isPropsUpdatesAccumulationGuaranteed() {
#ifdef __ANDROID__
  return ReactNativeFeatureFlags::enableAccumulatedUpdatesInRawPropsAndroid();
#else
  return true;
#endif
}
```

该谓词在 `promoteReactRevision` / `mergeReactRevision` / `scheduleReactRevisionPromotion` 三处各读一次（`ShadowTree.cpp:504`、`:523-537`、`:575`、`:611`），把「React 分支修订如何并回主分支」劈成两条路径。

### 4.2 【核心 MOU-12】两条 merge 路径：只并最新一个 vs 逐个全并，且 state reconciliation 只放行最后一个

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:494-570`（`mergeReactRevision`）：

- 积累保证为 true：`reactRevisionToBePromoted_` 里**只有最新的一个**（`promoteReactRevision` 每次覆盖赋值，`:588-591`），merge 用一次 `std::exchange` 取出（`:509-510`），单次 commit（`:523-536`）。
- 为 false：`queuedReactRevisions_` 累积**每一个** react 修订（`scheduleReactRevisionPromotion:611-618`），promote 时整队搬入 `promotedReactRevisions_`（`:599-604`），merge 时 **for 循环逐个 commit**（`:538-556`）。
- 逐个路径上 `enableStateReconciliation` 仅在**最后一个** revision 为 true（`:540`、`:550`）；两条路径的 commit 都声明 `mountSynchronously = true`、`source = ReactRevisionMerge`（`:531-535`、`:551-552`）。
- merge 的 transaction 函数**完全忽略 oldRootShadowNode**——直接拿 promoted revision 的根克隆返回（`:526-530`、`:544-548`），「合并」语义实为「覆盖 + 让 state reconciliation 收尾」。
- 成功合并后，若 `currentReactRevision_` 就是刚合并的根，则清空之（`:558-569`）。

注意 `progressRootLayoutInfo`（`:199-223`）为该路径兜底：React / ReactRevisionMerge 来源的 commit 若 JS 分支根的 `layoutConstraints`/`layoutContext` 与主分支基线不一致，则**用主分支的 props 克隆根节点、children 保留 JS 分支的**（`:215-219`）——布局元数据回滚到主分支视角，防止 React 分支在并发布局变化时把过期约束写进根。

## 5. 同步性契约：谁在什么锁下动 mounted 标志，谁同步挂载

### 5.1 【核心 MOU-13】`updateMountedFlag` 全程持 `EventEmitter::DispatchMutex()`；ReactRevisionMerge 跳过置位以防计数双增

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:435-441`：

```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:435-441（压缩）
{
  std::scoped_lock dispatchLock(EventEmitter::DispatchMutex());
  updateMountedFlag(
      oldRevision.rootShadowNode->getChildren(),
      newRootShadowNode->getChildren(),
      commitOptions.source);
}
```

被调用方自行跳过 mounted 置位：`commitSource == ReactRevisionMerge` 时 `shouldUpdateMountedFlag = false`，注释解释这些标志在 React 分支提交时已置过，再置会让 EventEmitter 的**加性计数器双增**（`packages/react-native/ReactCommon/react/renderer/mounting/updateMountedFlag.cpp:32-36`）。

### 5.2 MOU-14 Suspended 模式的提交「进树不入挂载」；切回 Normal 时同步补挂一次

三段事实（`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp`）：

- 主分支 commit 成功后 `else if (commitMode == CommitMode::Normal) mount(...)`（`:470-472`）——**Suspended 时不 push revision、不通知 delegate**，修订只停留在 `currentRevision_`；
- `setCommitMode(CommitMode::Normal)` 时在锁内换模式并读出当前 revision（`:271-283`），锁外若 revision 不是 `INITIAL_REVISION` 则 `mount(revision, true)` **同步**补挂（`:285-289`）；初始 revision 被显式排除（注释：initial revision never contains any commits）；
- `mount()` 本身 = `mountingCoordinator_->push(revision)` + `shadowTreeDidFinishTransaction`（`:487-492`）。

### 5.3 MOU-15 `commitEmptyTree` 与 `notifyDelegatesOfUpdates` 恒同步

`packages/react-native/ReactCommon/react/renderer/mounting/ShadowTree.cpp:623-640`：清空树用**默认 CommitOptions**——而 `mountSynchronously` 的默认值是 `true`（`ShadowTree.h:59-70`），所以卸载 React 树的最后一步是同步挂载；`notifyDelegatesOfUpdates` 直接传 `true`（`:638-640`）。react 分支提交则被断言禁止同步（`react_native_assert(!isReactBranch || !commitOptions.mountSynchronously)`，`:348-353`）——「JS 分支 commit 永不同步」有专门断言把守。

## 6. `MountingCoordinator`：从 revision 到 transaction 的编队

### 6.1 【核心 MOU-16】`push` 静默丢弃过时 revision；同名号重复只在 debug 被抓

`packages/react-native/ReactCommon/react/renderer/mounting/MountingCoordinator.cpp:39-52`：

```cpp
// packages/react-native/ReactCommon/react/renderer/mounting/MountingCoordinator.cpp:43-48（压缩）
react_native_assert(
    !lastRevision_.has_value() || revision.number != lastRevision_->number);
if (!lastRevision_.has_value() || lastRevision_->number < revision.number) {
  lastRevision_ = std::move(revision);
}
```

条件不满足时直接丢弃——release 无日志、无计数。这是「只认更大号」线路的收口：Suspended 期间积压的旧号修订在这里被自然淘汰（也意味着 Suspended 期间多次 commit 的中间态永远不可见）。`revoke()`（析构时调用，`ShadowTree.cpp:263-265`）清空 base/last 两 revision，使后续 pull 返回空（`MountingCoordinator.cpp:54-62`）。

### 6.2 MOU-17 `pullTransaction` 全程单锁；线程契约要求消费方同线程串行

### 6.3 【核心 MOU-18】override 委托：弱引用遍历 + 空事务合成全套假 telemetry + 号再自增

### 6.4 【核心 MOU-19】introspection 自检：两棵对照树都不依赖差分器，override 事务只回放不比对

## 11. stubs：自检树的三个细节

### 11.1 MOU-32 stubs 无条件编译进目标；两种建树；排序器是「故意拷贝的简化版」

- CMake 把 `stubs/*.cpp` 无条件 glob 进 `react_renderer_mounting`（`packages/react-native/ReactCommon/react/renderer/mounting/CMakeLists.txt:11-15`）——区分只在调用点（MountingCoordinator 用 `#ifdef`；测试直接用）。
- `buildStubViewTreeUsingDifferentiator`：克隆一棵空树 children 的根，对「空树 vs 全树」跑一次完整差分（`packages/react-native/ReactCommon/react/renderer/mounting/stubs/stubs.cpp:96-109`）——差分器的全桶逻辑都被驱动到。
- `buildStubViewTreeWithoutUsingDifferentiator`：手写前序遍历直接产 Create+Insert（`:73-94`），其 `reorderInPlaceIfNeeded` 注释自认「intentionally copied from Differentiator.cpp」且**无条件** stable_sort（`:30-36`）——与 8.1 的生产版「全 0 跳过」行为不同：stubs 版会多付一次排序，但语义不受影响（键都是 orderIndex）。建树入口同样 `reserve(256)`（`:76`）。

### 11.2 【核心 MOU-33】回放的硬不变量；release 下不变量破坏会沿 `registry_[tag]` 的 operator[] 滑向空指针

`packages/react-native/ReactCommon/react/renderer/mounting/stubs/StubViewTree.cpp:49-235`（`mutate`）为五类变异各设断言：

- **Create**：parentTag 必为 `kNoTag`、old 侧必空、new 侧 props 必非空；tag 不允许重复（`:54-56`、`:64-70`）。
- **Insert**：child 的 `parentTag` 必已是 `kNoTag`（即先 Remove 再 Insert，`:121`）；`index ≥ 0 && size ≥ index`（`:122-125`）。
- **Remove**：`size > index` 且 **`children[index]` 的 tag 恰等于被移除 tag**（`:179-184`）——下标与内容双重校验；child 当前父 tag 必须匹配（`:164`）。
- **Update**：新旧 tag 相同且非 0、props 非空；`parentTag != 0` 时要求 tree 中记录的父一致（`:203-214`）；随后断言 StubView↔ShadowView 哈希一致（MOU-3）。
- **Delete**：parentTag 必为 `kNoTag`、new 侧必空（`:84-85`）。

这些断言在 release **全部失效**：`hasTag` 失败后 `registry_[tag]` / `registry_[parentTag]` 走 `unordered_map::operator[]`（`:71`、`:88`、`:112`）——**静默插入 `nullptr` StubView 条目**，下一次解引用（`->update` 等）即崩；`getStubView` 的 `.at()`（`:37-43`）则直接抛 `std::out_of_range`。introspection 在 release 的定位是「断言即文档」而非兜底：它抓 bug 的能力止于 debug。

### 11.3 MOU-34 `StubViewTree::operator==` 不比树形——自检的已知盲区

`packages/react-native/ReactCommon/react/renderer/mounting/stubs/StubViewTree.cpp:270-303`：先比 registry 大小，再逐 tag 比 StubView；而 StubView 的相等只看 **props + layoutMetrics** 两字段（`stubs/StubView.cpp:42-59`，verbose 日志需另开 `STUB_VIEW_TREE_VERBOSE` 宏）。合起来：两棵**子树顺序不同 / 父指针不同**但同名同 props 指标的树会判等。Mounting 不变量里结构正确性主要靠 11.2 的 Insert/Remove 断言与「回放后 registry 尺寸一致」间接保护，纯重排（两子互换）且 props 不变时该自检**抓不到**——好在真实挂载顺序会体现在 index 上（Remove 精确匹配 `children[index]`），弥补了 == 的盲区。Sibling 字段 `parentTag{kNoTag}` 默认值在 `stubs/StubView.h:43`；`update()` 不更新 children/parentTag（`stubs/StubView.cpp:30-40`），树形完全由 StubViewTree 掌管。
